Why the compile was paid per build, and why it need not be

assemble asked tile_evaluator for a kernel on every call, and tile_evaluator built a fresh closure every time, so jax.jit — which caches per function object — never saw the same function twice. A caller sweeping a winding pack through positions therefore paid a hundred seconds per POSITION for a build that takes thirty milliseconds.

Nothing about a scan requires that. The pair list and the quadrature nodes are constants of the PLAN and are closed over; the geometry — target coordinates, section edges, weights, norms — is an argument. Moving a section changes argument values at fixed shapes, which is precisely the case a compiled kernel is for. So the fix is a memo on (plan, batched, kernel), bounded at eight entries because each holds an executable and its device buffers, with forget_evaluators to release them — which is also what a measurement of the compile needs, and what the benchmark uses.

assemble additionally takes an evaluator a caller already holds. It is rarely needed now that the memo exists, and it is checked: an evaluator built for another plan, another kernel or the other mapping is refused, because building something other than what was asked for is worse than refusing.

A geometry scan, measured through the build loop

The same 64 hexagonal cells at four positions 13 mm apart in R — a fifth of a cell — each position a whole build through assemble into its own zarr store. One H200, four tiles of 32×32, median of three fresh processes:

quadrature, one H2002.20 s0.050 s1

The CPU row is the control that says reuse costs nothing per build: 8.20 s a position against the 8.14 s a standalone build of the same operator takes. The device rows are the prize — 27 ms is 6.7 µs/pair against the kernel's own 5.5, the difference being one zarr store created per position rather than any arithmetic. Eight positions: 102 s warm against 813 s cold.

Across a process boundary

The same build twice, in two fresh processes sharing one on-disk cache. A hit is counted from JAX's /jax/compilation_cache/cache_hits event, not inferred from the clock — a slow filesystem would otherwise be indistinguishable from a compile:

kernel / devicecold compilewarm compile hitscache written
closed, H200101.89 s 8.45 s0 then 32.8 MB
quadrature, H2001.36 s0.23 s0 then 3 0.17 MB
quadrature, 16 CPU cores1.33 s0.57 s 0 then 30.17 MB

Three executables per build, all three hits, and JAX's own counter reports 91.2 s of compile saved. What the cache cannot skip is the 8.45 s that remains: tracing the reduction and lowering it to HLO is how the cache KEY is computed, so it happens before any lookup can. That splits the two mechanisms cleanly — the persistent cache removes 92 % of a cold closed-form compile and the warm evaluator removes the rest.

The cache is on by default at ~/.cache/nova/kernels (or XDG_CACHE_HOME), bounded at 2 GiB with JAX evicting least-recently-used entries, and refused outright by NOVA_COMPILATION_CACHE=off — which every timing child of the benchmark now sets, so a compile figure is always a compile and never a disk read. A directory the caller already chose, through JAX_COMPILATION_CACHE_DIR or an earlier call, wins over the default. A whole test run leaves 5.7 MB in it; the tiled-backend suite goes from 95 s to 26 s on a second run because of it.

The build size at which the device beats a sixteen-core host pool falls from 7.2 M pairs to 0.60 M with the cache warm, and to nothing at all with the evaluator warm, where the device is a flat 3.5× the pool at any size. A single per-block build in a fresh process is still the wrong shape for the device — 0.4 s against 8.5 s at twenty thousand pairs — but that is now the cost of a cold START, not a cost the build repeats.

A measurement that lied, and how it was caught

The new jax-positions variant was dispatched by a startswith("jax-") test that already existed for jax-scan/jax-vmap, so it silently ran the SCAN kernel and reported 193.2 µs/pair for a mapped build. It was caught because that figure sat 0.2 % from the recorded scan rate — a per-build overhead invented out of nowhere is less believable than a dispatch that matched too early. Variants are now matched most specific first, and an unknown one still raises.

What is next

The compile is now paid once; making it smaller is the separate question, and the attribution says how much is there. The graph is 27,947 HLO operations per edge and exactly linear in the corner count; the recursions are 31 % of it, so rolling every one into a scan is worth about 1.45× and no more. The other 69 % is the harmonic-series coefficient algebra, which shrinks quadratically with the moment stack's length — 42 orders carried where the numerators reach nine — and that length is the residual-cost rung's subject rather than this one's. With reuse landed, both are now optimisations of a start-up cost rather than of a per-build one, which is a lower priority than it looked when the compile was paid every time.
