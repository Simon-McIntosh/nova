§1 — Objective

Make the construction of every biot interaction operator a parallel, batchable, shardable computation. The target-source pair space is embarrassingly parallel — each coupling entry is an independent kernel evaluation — yet today's assembly is RAM-limited and batched naively on the CPU: nova/biot/solve.py partitions sources into fixed ≤500-element chunks purely "so the interaction matrices stay bounded", each chunk builds a dense block in host memory, and nothing exploits the independence of the pairs beyond numpy's internal vectorisation. That design set a hard wall for exact thick-section coupling: the brute-force polygon kernel cost ~4.3 ms per pair against ~0.4 µs for a point filament (~10,000× clean; ~44 h per all-pairs 2000-cell matrix on a contended login node) — which is why the hexagonal plasma mesh shipped point-coupled (physics-spine-adoption, 2026-07-25) despite a measured +7.2% median / +18% max error on cell self-flux terms.

Two hard constraints frame the design:

  • CPU viability is non-negotiable. GPUs cannot be guaranteed for local work or CI, so the assembly must remain correct and usefully fast on a multicore CPU; the GPU is an accelerator for the same code path, not a requirement.
  • Build once, cache forever. Interaction matrices are pure geometry: computed once per machine/grid signature and cached (the zarr operator store tier from nova-spine-refactor). Steady-state solve throughput is therefore unaffected by build cost — but the first build at MAST-catalog scale must finish in under ~20 minutes.

Done well, this unlocks: the thick hexagonal plasma-section coupling as the default (gated also on the nova-3d-native §2 zeta fast path), exact polygon coupling for wall-clipped cells and — later — conductor turns, and a first-solve budget compatible with the mast-catalog-gpu-solve goal.

§3 — Research questions

  1. Assembly survey. Inventory how every operator class is built today (Solve/Matrix tier, segment generators, the ≤500-source chunking, intermediate array shapes, peak RAM per build) and identify what is shared vs kernel-specific. Where exactly does the RAM limit bind, and what is the actual arithmetic intensity per kernel?
  2. Tiling and sharding. Tile the (target, source) pair space with the tile size derived from a memory budget; evaluate tiles in parallel (multiprocessing / threads + nogil numba on CPU; device batches on GPU) and accumulate into the zarr store chunk-aligned. What tile geometry balances kernel launch overhead, cache locality, and store chunking?
  3. One kernel, two backends. Can the polygon/cylinder/zeta kernels run as a single fixed-shape code path (JAX with vmap on GPU, jitted on CPU; or numba parallel-CPU + a JAX GPU twin pinned by parity test)? The CPU baseline must not regress for existing operators; the same source must serve both, or the pair must be pinned by tolerance-gated equivalence.
  4. Principled near/far. Derive the cutoff from the section's second-moment (finite-area) error bound as a function of distance-in-section-sizes, per component (ψ, BR, BZ — the quadrature study shows flux-only bounds mislead), with the error budget set relative to sensor noise and solver tolerance — not the compute budget. Sweep with PolySection.configured against the exact-everywhere reference; the shipped default stays exact-everywhere until this bound exists.
  5. Re-cost after zeta. The nova-3d-native §2 fast path (10–30× on the quadrature hot spot) lands first; every cost line in §2 is re-measured before any cutoff or backend decision is locked.
  6. Budget check. Demonstrate a MAST-catalog-scale first build (≈2000×2000-cell plasma operator plus sensor rows) under ~20 min on one GPU node and report the CPU-only figure alongside it; both go in BASELINE.md.

§ Decisions

Kernel backend strategy: one JAX code path serving CPU and GPU, or numba parallel-CPU with a JAX GPU twin pinned by parity tests?

Near/far criterion form: per-component second-moment error bound (distance where the finite-area correction falls below a stated tolerance), or exact-everywhere retained once the accelerated build makes it affordable?

Locked on measured evidence (2026-07-25, archive/biot-operator-assembly-s3-landed.html): a BARE centroid filament never converges to the section for a full ring — the error flattens onto an (a/R0)^2 floor (~2e-5 per plasma cell, verified to 3000 section radii), so hybrid_greens' far field carries a ~1e-4 floor no switch value fixes. The cutoff is therefore per-component AND requires a quadrupole-corrected far field: second-moment corrected filament reaches 1e-6 beyond ~6 section radii (B-limited; psi at 3.6) and 1e-8 beyond ~16. Adopted scheme (to implement): three fixed-shape bands — 16x48 inside 2.2 contour radii, 8x24 to 6.8, corrected filament beyond (~1% of exact-everywhere nodes). Distances measured to the section CONTOUR. Shipped default stays exact-everywhere until the banded scheme lands with its per-component gates.

Tiling scheme: memory-budget-derived square tiles streamed to zarr-aligned chunks, or target-major strips matching today's row blocks?

Prototype measured (nova/biot/tiledassembly.py): budget-derived tiles with padded fixed shapes hold RAM at ~48 B/pair + ~1.5 MB fixed block (vs 267 B/pair today, and plan-bounded rather than problem-bounded), stream tile->zarr chunk-aligned, and scale 8.8x at 16 cores. Budgets >=4 MB/worker cost nothing; 1 MB forces the quadrature block down and costs 1.6x. Target-major strips would reproduce today's target-axis RAM fragility (13 GB/chunk at 100k targets).
