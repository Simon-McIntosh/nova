What this run does not settle

This run completed all four certificate rows and never aborted; it exited 1 on CERTIFICATE_IDENTITY_GATE=FAIL, a bit-identity verdict that is not this node's subject. So the abort itself was not reproduced, and the mapping hypothesis is neither confirmed nor retired by this measurement: the honest reading is a near-miss that leaves the hypothesis live and narrows it to a small margin.

Two concrete reasons the aborting job got further than this one, both stated as measurements rather than as inference:

  • Job 1274080 ran with --certificate-panel-dir set, so it rendered a poloidal flux panel for each completed row; this run omitted the flag because the driver refuses a panel directory outside the checkout's docs/ tree. Rendering panels compiles further programs inside the same process, and nothing in this run returns mappings to the kernel between rows, so the omitted panels are the most likely source of the extra margin.
  • A first attempt at this measurement, job 1274141, ran with the panel directory and died after 100 s on a path-validation error in the panel writer, not in a compile, having already reached 24718 mappings in 100 s. That is 38% of the limit in the first eighth of the run, which is consistent with the step pattern in the figure.

The direct continuation is one allocation of the same driver with a panel directory under the checkout's docs/ tree, which is the configuration that aborted, and which this node's write fence did not include.

Verdict

The limit was reached in run 1. The last sample stood 11383 mappings short of 65530, but the fourth program load — a step this process performed three times, each adding 16789–17620 mappings — cannot complete from there without the count crossing the cap: 54147 + 16789 = 70936, 5406 mappings above it, and the process died inside exactly that step with LLVM refusing memory; run 2 completed the same four loads only because it returned 16178 mappings to the kernel before the fourth, which run 1 did not, so its fourth load began 35250 lower.

The crossing itself is inferred, not observed, and the inference is quantitative rather than a reading off the same series: run 1's last sample fell 0.78 s before the refusal and its next tick never came, while run 2 measured a 17618-mapping rise inside one 0.2 s interval, so the 11383-mapping gap is traversable in about 0.13 s — a fifth of the interval that missed it. The 1.0 s tick was coarser than the process's own allocation burst, so a series at that tick cannot decide this question in either direction; the second run exists because of that, and its role is to supply the step size and its duration.

What ran. One all_debug allocation, job 1274197, node 98dci4-clu-3141, --cpus-per-task=8 --mem=64G --time=00:59:00, with TMPDIR=/tmp exported in the submit environment and again inside the payload, JAX_PLATFORMS=cpu, and the shared root interpreter (/home/ITER/mcintos/Code/nova/.venv/bin/python) invoked directly — uv was never called on the compute node. Why the shape is the remedy. One certificate program load adds 16789-17620 mappings measured five times across two earlier runs, against a kernel limit of 65530. That is room for three loads and no more, and the certificate asks for four; the run that completed did so only because it happened to return sixteen thousand mappings to the kernel before its fourth load. What the four children show, and what they do not. The largest sampled peak is 40,756 of the kernel's 65,530 — 62% of the cap — and the smallest is 24,750; the mean is 36,338. Every child finished with tens of thousands of mappings of room left, and the aborting job's failure mode is unavailable to them by construction: it died inside a fourth load from 54147 mappings because one process had already loaded three rows' programs, and a child here starts from an empty address space rather than inheriting its predecessors' load.

The evidence does not say each child loads one program, and the receipt records that plainly. A row's own solve, state write and panel render loads more than one program for the larger rows: the peak of a child minus its own starting count is roughly one load for the smallest row and roughly two for the largest. The receipt's within_one_program_load flag tests a peak against 2 × 16789 = 33578 — twice the cost of one load — and reads false for moderate-rotation-conventional-static, strong-rotation-compact-static, diverted-single-null and true for the rest, so the per-child series are reported against the one-load figure honestly rather than as a claim that no child crossed it. "Run each row in its own process" is a bound on what a process accumulates, not on what a row costs; a reader who takes the flag as the remedy's claim will read it wrong, which is why the flag and the caveat travel together.

The two rows the aborting job never reached — strong-rotation-compact-static and diverted-single-null — completed here, each in its own process, each writing its own terminal state.
