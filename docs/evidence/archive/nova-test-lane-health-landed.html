§2 item 1 — the catalog scan in a thread-starved process

Commit 459cecce, merged to main.

The diagnosis, and what it ruled out

A monolithic pytest -m "slow or not slow" run collected 5,769 tests, parked at 76% for about 18 minutes in the eighteenth catalog-geometry test, and never emitted counts. Two independent py-spy snapshots put the main thread in threading.Thread.start(), reached from ThreadPoolExecutor.map in scan_catalog, before any executor worker thread was created — reached from tests/test_mast_catalog_geometry.py::test_catalog_scan_resumes_from_atomic_fingerprint_checkpoint. The same test passed from a fresh process in 16.79 s.

The negative result is what makes the diagnosis usable. A limit probe on the compute node reported RLIMIT_NPROC=770063 and pids.max=max, so this is not a configured process or cgroup PID ceiling, and it is not slow catalog logic. What remains is accumulated suite-process native-thread starvation: by that point in suite order the process can no longer start a thread, and any code path that must start one to make progress stops forever. Ruling out the two cheap explanations is what redirected the fix from "raise a limit" to "stop requiring a thread".

The repair and its pin

A workers=1 scan now fingerprints inline without constructing a ThreadPoolExecutor at all; workers>1 stays inside a context manager whose exit deterministically shuts its threads down. The regression test replaces ThreadPoolExecutor with a failing sentinel, so both the initial and the resumed one-worker scan prove zero executor-thread dependency by construction rather than by timing — a test that cannot pass if the dependency returns.

The monolithic run: parking site cleared, a second wall behind it

Commits 80c3b507 and a5e1245c. The repair works and the lane still does not finish. Both halves of that sentence are the result.

What is proven: in a single process, in true suite order, tests/test_mast_catalog_geometry.py completed 18 of 18 and pytest continued past the 97% mark. The former Thread.start() parking site is passed, so §2 item 1 is demonstrated end to end rather than only on the ordered subset.

What stopped it: a native abort — Fatal Python error: Aborted, exit 134 — after 33 min 44 s, inside tests/test_topology_boundary.py::test_x_mask_excludes_cells_beyond_null_heights while JAX compiled and loaded an indexed slice (backend_compile_and_load → compile_or_get_cached → pjit → lax.slice). This is a different mechanism from the thread starvation, at a different site, and it is not a Python-level failure that pytest could report.

No counts are claimed, for two independent reasons, and both are recorded rather than glossed. Pytest emitted no final summary, so there is nothing honest to bank. And the run executed against the mutable primary checkout, which advanced from d4ce244d to cb70bdf8 mid-run as this session pushed — so even a completed count would not have named one tree. The method needs a frozen worktree at a fixed SHA, which is the more useful finding of the two: a lane measurement taken against a moving checkout cannot be attributed however cleanly it finishes.

The run's diagnostic value was recovered rather than discarded: it mapped the six true-order failure positions to exact tests/test_biotsavart.py::test_axial_vertical_field ids with their operands, which is what let the attribution node prove the pole split caused them. It made no repair, correctly — changing the tree it was measuring would have destroyed the measurement.

The abort is memory pressure, and it is the deadlock's sibling

Commit eb242d80. Three candidate causes were separated by experiment rather than argued, each run as its own child process with its exit status recorded:

Independently, the preserved monolithic crash stack symbolizes as llvm::report_fatal_error → llvm::RuntimeDyldImpl::emitSection → xla::cpu::JitCompiler::TaskDispatcher, and the linked JAX library carries the section-emission fatal Unable to allocate section memory!. Cause: exhausted native compiler resources during CPU-JIT acquisition, not erroneous slice semantics.

This is the same failure as the catalog deadlock, at a different call site. That one parked forever in threading.Thread.start() with no worker thread created; this one aborts in pthread_create with Resource temporarily unavailable. Both are a long-lived suite process that can no longer obtain a native thread — one blocks, one dies, and the earlier probe already established it is not a configured ceiling (RLIMIT_NPROC=770063, pids.max=max). Treating them as two bugs would mean fixing call sites one at a time as the lane grows; they share an accumulating owner that has not yet been named.

No test-local workaround was applied, deliberately. Changing the host-side slice moves the abort to the next JAX compilation, and jax.clear_caches() released only about 2.5 MB of the measured 892 MB — neither is a bounded repair, and either would have hidden the lane-level pressure behind a green test.

Two candidate failures were investigated and correctly not banked. tests/test_datasource.py::test_shared_attributes failed only under git archive with InvalidGitRepositoryError and passed in a real git worktree — an artefact of the measurement method. A test_a_compiled_kernel_outlives_the_process_that_produced_it failure came from a replacement harness setting JAX_COMPILATION_CACHE_DIR, and was replaced by a clean 37.87 s exact-test pass. Both distinctions matter: a lane baseline that banks its own instrumentation errors teaches every later reader to distrust it.
