The twenty-edit stride sweep at revision a3f2429b is device-independent

Verdict. The twenty-edit coil-edit sweep at revision a3f2429b converges 4 of 20 on a Tesla P100 exactly as it does on the H200: every edit carries the same converged flag, the same termination reason, the same trip count, and the same vertical-centroid qualification. The drop from the banked 10 of 20 to 4 of 20 therefore follows the revision, not the device. The per-edit warm wall does move with the device (median 3117.1 ms on the P100 against 2060.6 ms on the H200, 1.51x), so the revision change is the cause of the convergence loss and the device is the cause of the wall difference.

Run. One titan allocation, job 1275968 on 98dci4-gpu-0002.iter.org (partition titan, --gres=gpu:1 --cpus-per-task=4 --mem=64G --time=02:00:00, no reservation), admitted off the H200 measurement host only because the run named its reason in NOVA_COIL_EDIT_OFF_HOST_PROVENANCE. The root interpreter was invoked directly with PYTHONPATH set to the worktree and TMPDIR=/tmp; uv was never invoked. Receipt: titan-coil-edit-latency.json — source_revision a3f2429b, device Tesla P100-PCIE-16GB, twenty edits, elapsed 817.2 s, converged_edit_count 4, median warm wall 3117.1 ms.

Configuration caveat, recorded because it changes how the drop reads. The brief for this run specified "no vertical current-centre constraint". At revision a3f2429b that configuration is unreachable through the driver's command line: run() sets constraint_pairs unconditionally to the prepared vertical-centroid row (benchmarks/coil_edit_latency.py:2456), the row was introduced by the commit that imposes the vertical current-centre on the coil-edit sweep, and the documented unconstrained fallback ("when no rows are supplied") can only be reached by changing source, which is outside this node's write scope. This run is therefore the plain driver invocation with the six declared output arguments and no constraint switch — the same invocation the H200 receipt at this revision was produced by. It is centroid-constrained, and so is the H200 receipt: all twenty of its edits carry a vertical_centroid row. That matched configuration is what makes the same-revision comparison below valid. The banked 10-of-20 receipt (revision d3849192, job 1273580) is the unconstrained one — its edits carry no vertical_centroid row at all — so the 10-to-4 drop spans a configuration change as well as the response-kernel port, and this node does not split those two.

The maximum boundary displacement is 0.151322961309616 m on both, agreeing to the last displayed digit. The only quantity that moves is the wall.

What this record does not establish. That the drop originates in the vertical current-centre row rather than in the response-kernel port: both landed between d3849192 and a3f2429b, and the unconstrained cell cannot be produced at a3f2429b without a source change. The claim this record does support is narrow and sufficient for the question asked: at revision a3f2429b the convergence outcome is a property of the revision, reproducible to the flag on a second device with a different fp64 rate, and the device moves only the wall.
