The four support_read contradictions, resolved

The line map reports read 0/96, read_batch 0/208, read_and_book 0/27 and bank_program 0/11 body lines on both routes, while the device trace attributes kernels to each. The resolution is in the call sites, not in the trace: the routes read topology through Topology.read_qualification, the flux-map null census, and reach support_read only on the bank-solve arm, whose slice-profile bank fixture is absent from shared storage at this revision. The device trace therefore measures a compiled program whose Python body the routes never enter, which is exactly the shape the line map reports. The two implementations compute the same quantity and agree to the tolerances above, so the contradiction is not a correctness defect but a duplicate that only one arm currently exercises.

How further candidates were found

The scan reads the 210 route modules the line map records as executing at least one line, with function names discovered by scripts/iron_operator_bound/reuse_check.py's definitions(), called once per route module. The driver authors no second name-discovery pass: it walks each module itself only to carry each definition's body for the digest, its statement count and its source text for the ratio, and it compares the two discovery sets module by module, exiting nonzero with the module named if they differ. They agree over all 210 modules at this revision (definitions.agrees: true in the scan). callers() is not used, because the route cross-check counts named calls statically and the near-identity pass needs each definition's source, which callers() does not return; the body-digest, shared-name and near-identity grouping is therefore the driver's own. It reports 314 function names defined in more than one route module, mostly dunders, overrides and per-geometry kernels that are genuinely distinct per shape. Grouping by an AST digest of the body (docstring stripped) finds 45 exact-body groups spanning two or more modules. Restricting to one name defined in two modules with at least two statements leaves seven: subgroup, choose and update_columns, which are the storage-group-mode, extreme-selection and plot-columns entries, and tree_unflatten, _tensor_bernstein, ids and canonical_bytes, each carrying a decision. tree_unflatten (two statements, digest 53265adb1b2b), ids (3c31a9ac3efd) and canonical_bytes (ff3e299965f3) are two-line protocol adapters over a registry key: the body identity is what the protocol requires at each host, so each host keeps its own copy and no lines are removable. _tensor_bernstein (three lines, digest c05b0ba4f9ac) is a tensor-product Bernstein basis repeated between nova/equilibrium/flux_surface_extraction.py and nova/linalg/tensor_spline.py; it is measured in the seventh entry below, and the extraction copy is the removable one. A near-identity pass at 0.85 over the shared names finds 79 pairs, 42 of them exact; besides the seven above it recovers get_mode and the two _argm*_exact wrappers of the existing entries, and flags Aphi (cylinder against polysection), _first_residual (polygonanalytic against polygonarc) and for_member (ensemble against window_batch), all three measured in the seventh entry below.

One further candidate carries its decision without a comparison. nova/biot/polygonanalytic.py defines against_arctan twice, a local closure in terms and again in flux_and_moment_terms, with identical bodies; it is one module's internal repetition reached from one route, so there are not two implementations to compare. Keep both as they stand — hoisting the closure to one module-private helper is an optional local cleanup that removes no route implementation, and it is not a candidate this register would remove. The remaining shared names are Biot-Savart kernels that differ per geometry (arc, bow, polybow, beam, line), which is the correct shape for a per-shape kernel rather than a duplicate.
