Deleting the library modules no route reaches

The measured line map records, for every module, the lines executed by the forward route, by the inverse route, and by either. A module that both routes leave at zero can still be load-bearing, because a test, a driver or another library module may import it without running it, so the map alone never licenses a deletion. Each candidate was therefore offered to a static importer scan, and a module is removed only when the scan finds no importer anywhere and no package initialiser re-exports it.

The scan reads the map at revision 09ef90e40148bf724669e8fc2c7c3a823134f5b8 and the census at revision 2653ef0c9b5fa5b9, deletes nothing, and writes one receipt; this record and its machine-readable twin docs/evidence/fragments/code-reuse-and-hot-path/unreached-module-delete.json are composed from it. Twenty-four modules were removed in commit 104c8b67, 3029 lines in total, and one is held back by name.

How a module is cleared for deletion

All four conditions must hold, and the scan refuses with the failing condition named when any one does not.

  1. Unreached. The map shows it measured and executing zero lines on both routes.
  2. Unimported. No importer exists in nova/, tests/, apps/, the census-kept files under benchmarks/ and scripts/, or /home/ITER/mcintos/Code/imas-ambix. The scan resolves absolute imports, relative imports at every level against the importing file's own package, importlib.import_module and __import__ string arguments, and a bare sibling import against the importing file's directory and any sys.path that file inserts. A mention only counts at a token boundary, so nova.biot.geometry inside geometryparameters is not an import.
  3. Not re-exported. No package initialiser imports it, so nova.package.Name cannot be reached through a package attribute.
  4. Not owned. It is not under nova/imas, and no plan in the sprints that own this work names it or its directory. A plan's own text is read for the module path, its dotted name and its directory; ownership that comes only from a shipped plan that has already landed does not block a deletion here.

The importer relation is then closed transitively: a module imported only by modules that are themselves deletable is deleted with them, and a module imported by any module that survives is refused with that importer's name. No candidate in this population reached deletion through the transitive path, so every accepted module has zero importers outright.

Held back and named

nova/utilities/ANSYS.py (227 lines) is unreached and unimported, and it is left in place. The measured line map's own driver, scripts/prototypes/hot_path_map/job.sh, names it as the map's negative control, and the map refuses to write when that module carries no coverage entry. Deleting it would make the landed map record irreproducible, so the deletion is refused with that reason recorded.

Two packages are left holding nothing but an empty initialiser, nova/field/ and nova/thermalhydralic/twente/. The scan refuses a package initialiser as a deletion candidate whatever its size, because removing one changes the import semantics of anything that reaches the package by name, so both were kept deliberately rather than overlooked. Neither initialiser is referenced outside its own package.

Live runs

Thirty-two live crew worktrees were read at the time of the scan; each one's staged changes, changes against its own head and changes against main were parsed as importers. No deleted module is imported by any of them, so nothing was held back on that ground.

Controls

Negative control one. A module the map records as reached is offered for deletion and is refused by the first condition: nova/equilibrium/forward.py, accepted by neither check, refused as reached by a route (union 506 lines). The refusal rests on the map alone, so it proves the map is consulted before any importer reasoning.

Negative control two. An unreached module whose only importer is imas-ambix is refused. No candidate in this population has an ambix importer in its real importer set, so the check is exercised by injecting one: with imas_ambix/live_import_probe.py importing the otherwise deletable nova/datachain/ccfe_uda.py, the verdict flips from ACCEPT, unreached and unimported (33 lines) to REFUSE, imported by ambix imas_ambix/live_import_probe.py. The control is synthetic and marked as such in the receipt; it demonstrates that an ambix importer is sufficient to refuse, and it is not evidence that any real ambix importer exists.

The plan asks for a suite delta. The repository's default CPU lane is itself measurement-heavy: a full run of the not-slow selection collected 10943 tests and completed five of them in the first four minutes, so a two-arm full execution could not finish inside the node's deadline. Rather than claim a suite result that did not run, the gate was chosen to test the only failure mode a pure file deletion can produce, and it was run as one job per arm on all_debug with scripts/nova_lane/run.sh --rungs cpu --force-submit --wait.
