Carrier adjacency indices and tables share one integer dtype

The carrier adjacency sweep read `left, right` straight from the caller's edge array and scattered them into int32 tables (neighbours, counts). Under extended precision the caller's edge array is int64, so the scatter traced int64 -> int32 and JAX raised FutureWarning: scatter inputs have incompatible types, which a later JAX makes a hard error. _carrier_adjacency now casts its edge array once to CARRIER_INDEX_DTYPE (int32) and builds both tables at that dtype, so the indices and every table they scatter into carry one integer dtype. Carrier vertex indices are bounded by the mesh size, so the narrow integer is exact.

The two capacity tests are marked filterwarnings("error::FutureWarning"), so the warning fails them durably. At the dispatch base both fail under the mark (base-repro.log, EXIT=1); after the change both pass (head-carrier-adjacency.log, EXIT=0). The negative control restores edges.astype(jnp.int64) in _carrier_adjacency, which fails both tests on the same FutureWarning (negative-control.log, EXIT=1).
