Requalify the fine certificate carriers on the repaired kernel

The carrier cache identity hashed the fixture module and the coupling-assembly module, so a carrier assembled by an earlier version of the packed polygon moment kernel reused the same cache group and the near-edge repair could not invalidate a warm-load. builder_revision now hashes the coupling-assembly source and the packed polygon moment kernel it contracts through, and no longer hashes the fixture's own bytes.

Which files the identity now hashes

The carrier semantic identity's builder_revision field is the digest of exactly two files:

  • scripts/analytic_oracle_fixtures/coupling_build.py — the coupling-assembly module the docstring names;
  • nova/biot/polygonanalytic.py — the packed polygon moment kernel the assembly contracts through, resolved through the same POLYGONANALYTIC_SOURCE constant the exterior identity already used.

measure.py's own bytes were dropped from the digest: editing the fixture changes how a carrier is measured, not the blocks a carrier carries, so it must not invalidate every cached carrier.

Two notes on how these rows were produced. The extracted trees refuse the row through their own positive-control pin, which is a caller-supplied expectation for exactly this case, arm and rung: the row is written before that assertion and carries completed: true, so the value is a real measurement, but the process exits nonzero and the pin is not a check on the attribution. And the row driver requires a GPU even for the legacy arm, so all of these rows ran on the H200 lane; the fleet allocation carries no card.

Not completed in this run

Three items of the followup's done-when are not measured in this record and are carried as follow-ons rather than reported as met:

  • The host-against-device block agreement. The 5,000-cell host carrier exists on the repaired kernel, but no device build was produced alongside it in this run, so the 1e-12 block agreement is not reported. The rebuild submitted for that purpose found the host carrier a cache miss when the device platform was enabled, so it was still assembling the host blocks when this record was written; the host carrier the row driver persisted was built with the CPU platform alone, and the two carrier cache groups are not interchangeable.
  • The 10,000-cell rung, both carrier and rows. The 5,000-cell host assembly took about 2,077 to 2,122 s in job 1284720, and the 10,000-cell host assembly did not finish before that job's 2.5-hour ceiling: the run left a lock beside the 5,000-cell store and no 10,000-cell store. That path is not required for the rung. The device coupling builder is what the finest rungs are built with, and a 10,000-cell run on that builder, re-running the legacy, exact and read rows on both certificate cases, is submitted as --time 02:30:00 with its store written under the GPFS oracle cache root rather than the tracked tree. Its build wall is reported in the manifest's follow-ons once the job lands. This repository has no evidence-root resolver in nova/database/filepath.py to resolve through, so the store is placed on the existing GPFS cache root /work/projects/imas_gpu/analytic_oracle_cache and named there.
  • The three-revision attribution. Measured, and it excludes both candidate merges — see the section below. The value did not move at any of the three revisions named, so the merge that moved it lies later in history than acaea2c9c.
