Certificate fixtures published by identity into shared storage

The certificate booking gate composes a carrier machine and a clipped exterior for every analytic case and resolution, and rebuilt both from scratch on every run. The six parametrizations spend nearly all of their wall on those two builds, and the fixtures are identical between runs, so the repeated work bought nothing. Both are now addressed by the identity the fixture sources already define and published whole through the shared content store under the shared operand root, so a run that follows a first one loads the objects the first one published. A source change that moves any one identity input addresses a different object rather than reloading a stale fixture.

The cache layout and the identity key

The key is the identity, and it is not a new identity. The fixture module already computed one for its own in-run cache, and the misuse of it is what the earlier node in this plan repaired: fixture.cache_identity names the carrier's closed-form constants, the requested cell count, the wall node count and the wall, and fixture._exterior_cache_identity keys the exterior on the carrier's own semantic key, the analytic state digest and the support arm. The store digest is the SHA-256 of that identity's canonical JSON, taken over json.dumps(identity, sort_keys=True, separators=(",", ":")), and it is rendered as "sha256:" + hexdigest. Because every input a fixture depends on is inside the hashed object, a source change that moves any one of them computes a different digest and addresses nothing, rather than finding the object built by the previous revision.

The layout is one directory per kind, then the content store's own digest tree: <root>/<kind>/sha256/<digest>/ holding fixture.nc and the store's manifest.json. The root is certificate_fixtures.fixture_root(), which is nova.database.filepath.operand_cache_root() suffixed with certificate-fixtures - the shared operand root on the GPFS evidence mount - unless NOVA_BOOK_FIXTURE_ROOT names a private one, which is how a unit test or a scratch probe keeps its objects out of the shared tree. This is the point of the node: the two fixture kinds were previously written under a temporary root that the run removed on exit, so the next run began cold however recently a peer had built the same object. The kind roots are disjoint, and the booking helper asserts that the store the carrier resolved under lies beneath the carrier's kind root, so a build that landed anywhere else fails loudly rather than quietly publishing over a certified record.

Who publishes, and why that is safe on GPFS

One owner per fixture. cached_carrier owns the carrier object and cached_exterior owns the exterior object, and each is the only writer of its own key: no caller composes one and publishes it, and neither helper stages an object the other could name. Each reads before it builds - a hit returns the loaded dataset and a receipt recording hit: true with the load wall, a miss builds, publishes, and returns a receipt recording hit: false with the build wall - so one row's receipt says on its face which of the two happened without consulting the store.

Publication is delegated to nova.database.content_store.publish_files, which is the existing primitive for this and not a second mechanism invented here. The dataset is serialised to a private staging directory inside the kind root, then the store renames it onto its digest, without replacement where the filesystem admits that and with a plain rename where it does not. Two concurrent publishers of one key therefore resolve to one visible object instead of interleaving writes into it, and a reader sees the whole object or none of it. That is the property an in-place group write on the same root does not have, and it is the reason the fixtures are published through the store rather than written where the in-run cache wrote them. The store also verifies each declared file's content digest before the object becomes visible, so a returned dataset is the one that was published under that key, and a directory left without a manifest reads as a miss rather than a partial fixture.

A publisher killed between the payload write and the rename leaves its .pending- staging directory behind. The store never sees such a directory as an object, so it cannot be read as one, but nothing reaps it either; one was observed on the shared root after a cancelled run and was removed by hand. It is a leak of dead bytes, not a correctness fault, and it is recorded here rather than repaired.

The negative control: a moved identity misses

A cache that is only ever read on a hit proves nothing; the question is whether a moved input misses. tests/test_current_book_fragments.py::test_certificate_fixture_is_addressed_by_the_carrier_identity publishes the carrier fixture under the identity the current sources compute, points the fixture root at a private temporary directory, and then perturbs exactly one identity input - the discretisation's requested cell count - and asks for the perturbed identity. It asserts two things and not one: that the published identity resolves to the object just written, and that the moved identity resolves to no entry at all. Both hold. A cache keyed on anything coarser than the full identity - the case name, the discretisation without the wall, a revision stamp - would return the original object for the perturbed request, and this control would be the test that failed.

That last clause is measured rather than asserted. On the delivered tree the control passes in 12.05 s. With fixture_digest temporarily coarsened so it hashes the identity with discretisation.requested_cells removed - the one input the control perturbs - the same test fails in 12 s with AssertionError: a moved identity loaded the fixture published under the original, exit status 1, on the same node id the head arm does not fail. The coarsened key resolves the moved request to the object published under the original identity, which is exactly the stale load the control exists to refuse. The mutation was reverted before the final commit and the file is identical to HEAD.

Two runs of the gate: the first builds, the second loads

Job 1287655 ran the six analytic certificate parametrizations twice in one allocation, as two sequential runs in fresh processes and never as an array, on the queue's H200 reservation (98dci4-gpu-0003, one card reported as CudaDevice(id=0), four cores, 100 GB). The first run is cold: it builds each carrier and exterior fixture and publishes it. The second is warm: every fixture is already under the shared root, so it loads. Both runs ran the same six node ids from tests/test_current_book_fragments.py, on the same card, in binary64, each printing its resolved tree, its imported fixture module, its device list and its fixture root in the log header. Neither was sharded, and the fixture root is the shared operand root, so the objects the first run published outlived the process that wrote them and were read by a different process in the same allocation.

Both runs reached the same verdict: six passed, none failed, exit status zero. Run 1 took 10,750.76 s of pytest wall (2:59:10; 2:59:23 by /usr/bin/time) and run 2 took 891.00 s (0:14:51; 15:22.33 by wall clock), so the whole gate is 12.1 times faster the second time and the job completed in 3:15:39 with GATE_EXIT=0. No row changed status between the runs and no row was added: the six ids are the same six in the same order, and the two logs differ only in the walls.

The booking gate now reaches the owners the rest of the tree reaches

The first version of this node left two implementations of the same fixture standing. certificate_fixtures.py carried its own build-and-publish flow for the booking gate, and scripts/analytic_oracle_fixtures/measure.py carried cached_machine and cached_fixture_exterior for every other caller, so the gate's carrier and the carrier the other 99 call sites measure against were produced by different code that had to agree by maintenance rather than by construction. The two owners now take the store as an argument, certificate_fixtures.py keeps only the content-store backend the owners cannot express - where an object lives, and how it is made visible whole to a concurrent reader on the GPFS operand root - and its forked flow and build bodies are deleted. cached_carrier and cached_exterior are four-line callers that pass carrier_store() and exterior_store() and return what the owners return, so the booking gate's fixtures come from the same identity, builder, encode, decode and receipt logic every other caller uses.

No existing caller changes behaviour. The store argument defaults to the backend each owner used before, and of the 69 cached_machine and 34 cached_fixture_exterior call sites across scripts/, tests/ and benchmarks/, exactly four name a store: the two backend helpers above and the two calls inside the new hit-path test. cache_identity, builder_revision, the source-path and builder-function manifests, the dataset encode and decode, build_machine, _exterior_cache_identity and EXTERIOR_CACHE_SCHEMA are unchanged, so the digests and therefore the six carrier and six exterior objects published on 2026-10-16 and 2026-10-17 remain the objects this tree addresses. The root now holds eight of each, not six: the titan gate's cold rows published a device-specific pair, carrier/sha256/d8a93f1d… and exterior/sha256/ea7155ca…, on 2026-10-18. The twelve original entries are untouched and no digest moved.

The hit path is now measured by a negative control rather than by a receipt field. tests/test_current_book_fragments.py::test_second_call_loads_the_published_carrier wraps the content store in a store that raises if a builder reaches publish twice for one key, calls cached_machine twice on one identity, and asserts the second call loaded. Forcing the load path to be bypassed fails that test with the refusal text; the mutation was reverted and the test re-runs green. The same test asserts the published key against a digest recomputed in the test body rather than read back from the store.

The gate was re-run on the single-owner tree, on titan, and the six verdicts and twelve load walls in the table above remain those of the earlier H200 tree - not because the new run failed to report, but because the rows it measured are titan numbers and belong beside the H200 ones rather than replacing them. Four rows reported and all four passed; the two 5,000-cell rows did not, and neither verdict is a failure of the change. The H200 attempt, job 1287904, could not start - 98dci4-gpu-0003 is the partition's only node and it is drained - so the gate moved to titan, where three submissions were spent before one ran: the first cancelled from PENDING because a later commit moved the tree's head past the revision the payload pins, and the second failed in one second with exit status 127 because the payload's prelude had been staged on the login node's local scratch, which a compute node cannot see. The third, job 1288657, ran on one P100 and ended on its two-hour wall with four rows through. Its rows are cold on that device: the published store is addressed by a device-bound identity, so a P100 resolves each row to a different digest than the H200 did and builds rather than loads, which is why every row's hit flag is false and why its load walls are the miss path returning. The per-row walls, labelled as titan numbers, and the two unmeasured 5,000-cell rows - one cut by the lane's per-test bound, one left without a receipt by the job's two-hour wall - are in the fixture-owner-store-argument fragment. Moving the exterior behind the shared store did cost one receipt field - load_seconds - which book.py reads when it composes a row; the first attempt after the move failed all six rows with KeyError and is repaired, and the failure is kept rather than replaced.

CPU suite delta

The three scan tests and the vectorised booking test ran CPU-only, one fresh process per module per arm, on the fleet allocation in place, with JAX_PLATFORMS=cpu, configure_dtypes() called before any array and jax_enable_x64 asserted true. The delta is measured against the orientation base and never against absolute green: both arms ran the same three modules in the same allocation, so the number that matters is the failures the head adds, and it adds none. tests/test_current_book_vectorised.py passes 6 in both arms (97.71 s at base, 74.05 s at head); tests/test_single_site_krylov.py passes 5 in both (29.03 s and 11.91 s); tests/test_solve_trips_are_a_scan.py reports 4 failed and 12 passed in both arms, with the same four ids in each - test_active_trip_body_is_lowered_once[2], [5], test_newton_step_body_is_lowered_once[2], [5] - so the four are pre-existing at the base revision and are not attributable to this node. The scan tests now import the leading-axis helper from tests/jaxpr_scans.py in place of three local copies, and each keeps the assertion it made before.
