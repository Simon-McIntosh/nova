Why the 500-cell coarse-tie census exhausts any memory it is given

Blocked outside this node's write scope. The 500-cell census id does not exhaust memory by growing a cache, a host array or a per-call retrace. It exhausts memory inside a single XLA CPU compilation of the batched jet-assembly kernel jax.jit(jax.vmap(_source_jets, in_axes=(0, None))), declared at scripts/prototypes/read_route/jets.py:321 with _source_jets at scripts/prototypes/read_route/jets.py:229. That compile allocates host memory at about 300 MB/s in its first phase and plateaus only above 100 GB, which is why the id fills a 96 GB, 128 GB or 256 GB cgroup cap alike. The cost is independent of the cell count: the same compile reached 79.0 GB at the 250-cell machine. The 250-cell arm passes because its jet operand is already published in the content-addressed operand store, so it never compiles; the 500-cell arm has no published operand and does. The fix belongs to scripts/prototypes/read_route/jets.py and the unrolled graph generator nova/biot/polygonanalytic.py — neither is a path this node may write, and kernel.py is not implicated.

One sbatch job on --partition=sirius (--time=02:00:00 --cpus-per-task=12 --mem=128G, job 1290521, node 98dci4-clu-5008) ran the 500-cell id and, for comparison, the 250-cell id, each in a fresh process, with resident memory sampled every 10 s from a sidecar thread and a stage marker printed around build, make_sampler, warm and each census offset. The 250-cell arm completed in 34 s with a peak of 1798.6 MB: its stages were build 1474.3 MB (served from the operand cache, JET_CACHE load_seconds=0.024), warm(37) +219.1 MB, and +2.2 MB / +4.8 MB for the two census offsets. The 500-cell arm printed STAGE build only after its compile completed; no later stage marker was reached within the job. Logs: logs/stage-memory-250.log, logs/stage-memory-500.log, logs/stage-memory-250.tsv in the run directory.

The stage that grows without bound is tie_probe.build at its build_jets call. A sub-step replica (scratch/build_stage_probe.py, logs/build-stage-500.log) printed certificate_case 666.5 MB, machine_load 708.0 MB, geometry cells=551 verts=(551, 12, 2) 770.9 MB, field_convention 780.1 MB, initial_read 1263.5 MB, sample_flux 1264.5 MB, booked 1276.1 MB, reference 1543.6 MB, triangle_rule points=(551, 18, 2) 1549.6 MB, build_values 1607.6 MB, coupling 1607.6 MB — every step flat — and then grew from 1607.6 MB at t=11.8 s to 108601 MB at t=990 s with no further marker, all of it inside build_jets. The JAX runtime named the compile itself: E1020 ... slow_operation_alarm.cc:73] [Compiling module jit__source_jets for CPU] Very slow compile?.

Measured growth rate, 500-cell arm: 308.4 MB/s over 30–90 s, 298.5 MB/s over 100–200 s, 90.0 MB/s over 300–600 s, 15.5 MB/s over 600–900 s, reaching 118620 MB at t=1340 s and still rising. The deceleration is the compile finishing its passes, not a plateau the cap can sit under. The 250-cell arm's warm loop never grew: +219.1 MB over 37 sampled states.

The compile cost does not depend on the cell count, so "500 cells" is not the variable that matters — the operand cache is. Running the identical batch-4 compile directly, bypassing the operand cache, at the 250-cell machine's 282 cells grew at 300.3 MB/s (30–90 s) and 298.3 MB/s (100–200 s), reaching 79042 MB at t=320 s before the run was stopped; at the 500-cell machine's 551 cells the same compile grew at 275.7 MB/s and reached 49206 MB, where the job's own --mem=48G cap killed it. Logs: logs/jet-scale-250.log, logs/jet-matrix-500.log. A 48 GB cap kills the compile at 250 cells; a 128 GB cap lets the 500-cell arm reach further before the same fate. This is the whole surface of the reported behaviour.

Mechanism. build_jets (scripts/prototypes/lean_map/jets.py) calls build_jet_matrix (scripts/prototypes/read_route/jets.py:288), whose assemble closure compiles jax.jit(jax.vmap(_source_jets, in_axes=(0, None))) once and then invokes it in a batch-4 loop over the machine's nodes. _source_jets builds its rows from nova.biot.polygonanalytic.packed_analytic_moments, a fully unrolled expression graph over the polygon sides and its _NODES = 128 contour-reduction nodes, and differentiates it with jax.jacfwd; the whole graph is then vmapped over the batch. XLA's CPU compiler allocates host memory through the reduction of that graph, and the allocation is what the sampled RSS measures — the count of live JAX arrays stays fixed at 129 across the whole growth, so no array, cache entry or host buffer accumulates in the Python process. The 250-cell id is protected only by a prior publication of its jet operand: read_operand returns the stored matrix and persist serves it, so the 250-cell arm's load_seconds is 0.024 and no compile runs.

Read this against the node contract, which permits writes only to scripts/prototypes/fast_map_production/tie_probe.py and scripts/prototypes/read_robustness/census.py. The compile lives in scripts/prototypes/read_route/jets.py; the graph it compiles is generated in nova/biot/polygonanalytic.py. Neither file is a write path of this node, and neither is kernel.py, the file the contract anticipates. tie_probe.build reaches the compile only through build_jets, which takes no batch, node-count or graph-size knob this node could pass; there is no edit inside this node's scope that removes it. Publishing a jet operand for the 500-cell machine would let the id pass under 64 GB, but the matrix would then be served from exactly the same cache as the 250-cell arm and the >100 GB compile would remain for any reader with a cold operand store — a test that passes by disabling the thing it is testing.

Reproduce: NOVA_ANALYTIC_ORACLE_CACHE=/home/ITER/mcintos/.local/share/nova/0.11.0 JAX_PLATFORMS=cpu PYTHONPATH=<worktree> /home/ITER/mcintos/Code/nova/.venv/bin/python scratch/stage_memory_probe.py --cells 500 --cache $NOVA_ANALYTIC_ORACLE_CACHE --sample-log /tmp/s.tsv. The 250-cell arm of the same probe, in a fresh process, completes with a 1.8 GB peak; only the 500-cell arm enters the compile because only the 250-cell machine's jet operand is published. The negative control declared for this node — revert the fix; the 500-cell id must again exceed 64G — is not exercisable here, because no fix was applied and no test path is in this node's write scope.

Follow-on work for the file's owner: the unrolled packed_analytic_moments graph (_NODES = 128 reduction nodes, sides polygon edges) differentiated by jax.jacfwd and vmapped inside one jit is what XLA is asked to compile. A bounded fix is to hoist the Hessian so the unrolled graph is compiled once per node family rather than per evaluation, to reduce the reduction node count in the differentiated expression, or to publish the 500-cell machine's jet operand so the id is served from the store. None of those is this node's call.
