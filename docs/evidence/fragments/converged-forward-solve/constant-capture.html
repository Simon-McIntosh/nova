Operands are program arguments, not captured constants

The Newton factor programs were compiled from jax.linearize over concrete operands. A linearization taken over concrete values embeds every operand array as a literal in the jaxpr it returns, and the solve then compiles one factor program per correction with jax.jit(factor). Each compiled program therefore carried its own copy of the window rows and the interior jets, so the copies multiplied with every step: the cut-cell split node measured 84.36GB total of captured constants when the limited 550 cold solve lowered, with float64[10,16,1177600] (1.51 GB) repeating about twenty-five times. The report's frames name the wall-events step at topology.py:2847, reached through program.py:46 (FusedField.evaluate) and fixed_points.py:294 (CachedField.evaluate) — the path along which the closed-operand window rows are read.

The tangent map built by operand_tangent in scripts/prototypes/fast_map_production/solver.py now takes the operands as arguments, so the lowering reads them as program parameters and one compiled program serves every correction. The same treatment covers the one-off read and booking programs, which had closed over the field and the reading.

tests/test_solve_operand_capture.py pins the distinction by measuring the constant bytes of a lowered tangent program. Its positive control linearizes over a concrete operand and requires the instrument to see at least half that operand's bytes as constants, so a green result cannot come from an instrument that never reports a capture.
