content-store-gpfs — content-store publication on parallel filesystems

The operand cache now publishes on GPFS. nova/database/content_store.py:publish_files probes the cache root and selects a directory-rename primitive the filesystem admits: the existing renameat2 RENAME_NOREPLACE where it is supported, and plain renameat where it is not. The default-on operand cache in scripts/prototypes/lean_map/values.py, scripts/prototypes/lean_map/jets.py and scripts/prototypes/read_route/jets.py is unchanged; it calls the same publish_files seam and gains GPFS support from the owner.

Strategy

The probe runs the operation itself. A private directory is renamed onto a name it alone owns with RENAME_NOREPLACE; success selects the no-clobber primitive, an unsupported-flag error (EINVAL, ENOSYS, EOPNOTSUPP, EPERM) selects plain renameat. The private directory is removed either way. The probe is the primitive the publication path then uses, so a root that rejects the flag is never published to with it.

Where no-clobber rename is unsupported, publication relies on the POSIX rename(2) rules that every parallel filesystem implements: a plain renameat moves the completed pending directory into place atomically, and a rename of a directory onto an existing non-empty directory fails with EEXIST. A committed entry always holds at least its completion marker, so a loser is never able to replace a winner and is told it lost by the error itself.

A reader never sees a partial entry: files are written under a private pending name (.<digest>.<token>), each file is fsynced, the pending directory is fsynced, the whole directory is renamed into place atomically, and manifest.json — the completion marker naming every file and its digest — is written last inside it. The object root descriptor is fsynced after the rename. A crash before the rename leaves only a hidden pending directory.

Two concurrent publishers of one content-addressed key both succeed and leave one valid entry: both build their own pending directory, the first rename wins, the second receives EEXIST and returns the winner after verifying it. A publisher of different content under the same key is impossible by construction — the key is the digest of the manifest, which names each file's digest and size — and a contradictory publisher is refused: its source files fail the declaration check before the pending directory is written, and a destination already carrying a different manifest fails verify_directory_files.

The GPFS mounts are POSIX, so plain renameat is atomic and the non-empty-destination EEXIST rule holds; the repository notes GPFS lacks atomic no-clobber create, and the strategy relies on no cross-node O_EXCL. The publication path does not depend on the unsupported no-clobber rename on these mounts.

Checks

tests/test_content_store.py runs in fresh processes with JAX_PLATFORMS=cpu on the fleet allocation in place, over a GPFS cache root (NOVA_CONTENT_STORE_GPFS_ROOT, defaulting to the GPFS home). The four base tests and the concurrent-thread test are unchanged.

  • publish then verified read returns the files;
  • two concurrent fresh-process publishers of one key leave one verified entry and both return it;
  • a crash before publication completes leaves no visible entry;
  • a corrupted file is refused on read;
  • a destination without its completion marker is not served.

Head arm: 10 passed. Base arm (base content_store.py, same test file): 4 failed, 6 passed — the four failures are exactly the newly added GPFS publication checks, which the base module cannot satisfy on a GPFS root.

The declared negative control mutates _create_private_directory so the pending directory is named the digest, publishing files directly at the destination. The crash check then fails: 9 failed, 1 passed, with test_gpfs_crash_mid_publish_leaves_no_visible_entry among them. This is the mutation the check exists to catch; the mutation was reverted and the tree is clean.
