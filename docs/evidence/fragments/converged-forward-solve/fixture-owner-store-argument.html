The analytic fixture owners take a store and own the whole fixture

The certificate booking gate cached its carrier machine and clipped exterior through a build-and-publish flow that lived in certificate_fixtures.py and composed the fixtures itself, while measure.py held a second, older flow that built the same objects for every other caller. Two implementations of one fixture, one of them exercised only by the booking gate. The two owners in measure.py - cached_machine and cached_fixture_exterior - now take the store as an argument and own the identity, the build, the publication and the receipt; certificate_fixtures.py keeps only the content-store backend the owners cannot express, and its forked flow and build bodies are deleted.

One owner, and what each module keeps

The split is by capability, not by convenience. scripts/analytic_oracle_fixtures/measure.py owns everything that is a property of the fixture: cache_identity and _exterior_cache_identity define the key, _dataset and _from_dataset encode and decode it, and the two owners build it on a miss, look up the receipt fields, and return (fixture, receipt) with hit, semantic_key, load_seconds, build_seconds and the object's store. scripts/prototypes/support/certificate_fixtures.py keeps only the two things the owners cannot state for themselves: where an object lives, and how it becomes visible to a deleted-fence reader - the content store's rename-onto-digest on the GPFS operand root. It supplies that through ContentStoreFixtureStore and names it as the booking gate's backend.

What was deleted is the fork. The module previously carried its own _load_or_build, its own dataset encode and decode, its own digest, its own publication and its own receipt, and book.py called that path for both fixtures. That flow is gone; cached_carrier and cached_exterior are now four-line callers that pass carrier_store() and exterior_store() to the owners and return what the owners return. The booking gate's fixtures are therefore produced by the same code every other caller reaches, which is the point of the node: a divergence between the gate's fixture and the fixture the rest of the tree measures against is no longer expressible.

The interface is narrow on purpose. FixtureStore.session(identity) returns a context manager over a FixtureSession, which carries a key, a location, a lock_wait, a load() and a publish(data). Two backends satisfy it and they genuinely differ: ZarrFixtureStore writes an in-place group under a file lock, and ContentStoreFixtureStore publishes through the content store's rename-onto-digest and takes no lock. The store is not a path, because a path cannot express the second - it names where an object lives but not how it is made visible as a whole to a concurrent reader, and on the shared GPFS root that difference is the safety property. Both owners default to their previous backend when no store is passed, so not one existing caller changes behaviour.

The negative control: a builder that raises on the second call

A test that asserts hit is True measures the receipt, not the load path - a receipt field can be right while the fixture was rebuilt behind it. The control declared for this node was "a builder that raises on the second call fails the hit-path test when the load path is bypassed", and that is what the test does. tests/test_current_book_fragments.py::test_second_call_loads_the_published_carrier wraps the real content store in _RefusingSecondBuild, whose session raises RuntimeError("a builder reached the store twice for <key>") if publish is reached a second time for one key. The test then calls cached_machine twice on one identity with that store and asserts the cold call built (hit is False, build_seconds > 0), the warm call loaded (hit is True, build_seconds == 0), that the store was asked to publish exactly once, at exactly the key the owner reported as its semantic_key, and that the two calls returned the same nodes.

The control was run red. With the loaded dataset forced to None inside cached_machine - so session.load() could never return and the second call had to build again - the test fails in 73.78 s with exit status 1 and the refusal text, and the logged key is the identity digest. The mutation was reverted byte-exactly (cmp silent, git status --short and git diff --stat both empty) and the test then passes in 42.87 s. A load path that is bypassed therefore fails this test rather than passing it with a plausible receipt, which is the property the fence asks for. The red log is logs/negative-control-hit-path.log in the run directory.

The identity test carries its own independent computation, because a store that hashed nothing and echoed its own key back would agree with itself. test_certificate_fixture_is_addressed_by_the_carrier_identity recomputes the digest in the test body as hashlib.sha256(json.dumps(identity, sort_keys=True, separators=(",", ":")).encode()).hexdigest() and asserts the published module's fixture_digest equals "sha256:" + independently_computed - not that the two agree by being read from the same place. It then perturbs exactly one identity input and asserts the moved identity resolves to no entry, while the unperturbed one resolves to the object just written.

The receipt repair: an owner that forgot what it had just done

Moving the exterior behind the shared store cost the owner one receipt field and the gate found it immediately. book.py reads exterior_cache["load_seconds"] when it composes a row, and the owner's returned receipt had lost that key in the move; the row raster is written before the row dictionary, so the first warm gate - job 1287897 - produced four rows that each wrote their npz and no JSON, then died with KeyError, and was cancelled by explicit id. The repair at f629e1dc3 is three lines: record load_seconds on the hit branch, and return it. The failed attempt is kept beside the record as logs/h200-certificate-gate-1287897-failed.log with its raw log rather than being replaced, because what it measured is the cost of the move.

Nothing else moved. cache_identity, builder_revision, CARRIER_SOURCE_PATHS, CARRIER_BUILDER_FUNCTIONS, the dataset encode and decode, build_machine, _exterior_cache_identity and EXTERIOR_CACHE_SCHEMA are byte-identical to the base revision, so the identities and therefore the published digests are unchanged and the six carrier and six exterior objects written on 2026-10-16 and 2026-10-17 remain the objects this tree addresses. The published store was not deleted or rebuilt.

The certificate gate: the H200 route closed, the rows ran on titan

The gate runs tests/test_current_book_fragments.py::test_analytic_certificate_moments - the six analytic certificate rows - as one job, and reads each row's verdict, carrier_cache_hit, exterior_cache_hit and both load walls from the row JSON. Four measured rows are reported below and two are not, and the reason the two are missing is a property of the rung rather than of the change. The H200 was the intended rung and it is closed. Job 1287897, the first attempt, died on the receipt defect above and was cancelled by id. Job 1287904, the resubmission, was queued on the reservation and could not start: 98dci4-gpu-0003 is the partition's only node and it is MIXED+DRAIN+RESERVED with reason Kill task failed, the drain timestamp falling in the same second as the cancellation of the first job. Whether the two are related is not established here, and clearing a drain is an operator action, so the node was left untouched and the gate moved down the ladder.

Three submissions were made on titan and the third ran. The first, 1287964, was queued and then cancelled from PENDING - no running task - because a later docs commit moved HEAD past the revision the payload pins, and the payload compares the pin against the worktree and exits 42 on a mismatch. The second, 1287971, started and failed in one second with exit status 127: its payload prelude had been staged under the fleet node's local /tmp, which a compute node cannot see, so the job died before pytest was reached. That was a defect in how this node laid out its own script rather than a defect in the gate, and the fix was to stop using node-local scratch for anything a compute node must read; the prelude now sits beside the run manifest on the shared filesystem, and the failed log is kept beside the record as logs/titan-certificate-gate-prelude-failed.log rather than replaced. The third, job 1288657, ran on 98dci4-gpu-0002 with one P100 card: --partition=titan --gres=gpu:1 --mem=96G --time=02:00:00, one job carrying all six rows, TMPDIR set to /tmp at submit and again in the payload, and the lane's own --timeout 3600 replacing the repository's 300 s per-test bound so that a slow device is not reported as a failed assertion. Its header confirms the tree served was this worktree, the fixture root resolved to the published store, and the backend was gpu on [CudaDevice(id=0)]. The gate did not run warm, and the reason is a property of the fixtures rather than a defect in the run. Every one of the four rows reports carrier_cache_hit and exterior_cache_hit false, so the owners built both fixtures instead of loading them; the load walls of about 0.0002 s are the miss path returning, not the cost of a warm read, and must not be quoted as one. The fixture identity hashes a wall array that is computed marginally differently on each device, so the six carrier and six exterior objects published from the H200 are not addressable from a P100: the same logical row resolves to a different digest here and therefore addresses a different object. This is the same mechanism the CPU probe above hit, and it means the warm-load claim cannot be witnessed on titan by a single run. It is witnessed where it was measured: by the earlier gate's two sequential runs on one H200, where all six rows flip from build to load with identical digests, and by the in-process hit-path test with its reverted negative control. A second titan run would now be warm, because this run stored what it built; that run is not part of this node and the rows were not resubmitted. One consequence belongs to the operator rather than to this record: because the miss path publishes what it builds, each of the four measured rows wrote its own carrier and its own exterior into the shared root, so the store gained four pairs - d8a93f1d… and ea7155ca… at 08:13, 5ef93876… and 4827bc29… at 08:18, 508bd54b… and d29c0da0… at 08:34, b88609b1… and f3bc1d21… at 08:54, all on 2026-10-18 - taking the root from six of each to ten of each. Nothing was deleted or overwritten and the twelve original entries are untouched, but the store is no longer exactly what it was, and whether device-specific objects belong in it is a decision this node does not own.

The CPU rung cannot substitute for this gate at all. scripts/prototypes/support/book.py::measure raises RuntimeError("certificate rows require the GPU measurement lane") when jax.default_backend() is not gpu, so the row is not producible on all_debug. A CPU probe of the carriers does not stand in either, and the reason is worth recording because it first read as a cache defect: the wall array the carrier identity hashes is computed marginally differently on the host than on the device, so a CPU probe computes a wall digest that matches neither the published fixtures nor another CPU run of a different revision, deterministically, at HEAD, at the base commit and at the revision of the predecessor node. CPU suite delta

The CPU arm is per-module fresh processes, CPU-only (JAX_PLATFORMS=cpu, configure_dtypes() before any array, jax_enable_x64 asserted true), on the fleet allocation in place, with -m 'not slow' and test_analytic_certificate_moments deselected as the GPU-only row. Twenty-seven modules are covered, chosen because they reach the two owners, the booking module, the fixture backend or the identity, and each module runs against the base revision (ad3c3f77e) and the head in its own process with its own --basetemp, so concurrent modules cannot delete one another's temporary trees. The delta is the added failures, module by module, never absolute green.

Both arms ran all twenty-seven modules. Five failures are present in the base arm and are therefore pre-existing rather than added: test_the_closed_form_boundary_is_the_production_boundary_read, test_solve_path_prefix_slices_do_not_feed_the_null_census, test_the_reduced_oracle_is_a_seconds_class_roundoff_fixed_point, test_cold_seed_receipts_keep_one_fixed_branch_axis_under_vmap and test_reduced_hex_request_receipt_records_absent_raster_flux - the last of these failing in both arms. tests/equilibrium/test_topology_read.py reached the driver's 1800 s per-module bound in both arms and returns no verdict in either, which bounds the gate rather than differing between arms. One module was red in the head arm alone and is resolved: tests/test_forward_support_clip_mode.py passed three at the base in 381.09 s and reported one failed and two passed at the head in 438.74 s, the failure being test_operator_clip_modes_apply_through_with_clip_mode hitting pytest-timeout's 300 s per-test bound rather than asserting. Re-run on the head arm alone, with the other arm no longer competing for the allocation, the module passes three in 397.92 s with exit status zero, so the red was contention between the two arms. Added failures against the base: zero.
