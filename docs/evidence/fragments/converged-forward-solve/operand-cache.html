operand-cache — cached Biot-Savart operands by default

Persistence is the default on both builders, and both now publish through the repository's content store rather than a private one. scripts/prototypes/lean_map/values.py:build_values caches its flux-block matrix and scripts/prototypes/lean_map/jets.py:build_jets persists through scripts/prototypes/read_route/jets.py:build_jet_matrix, both keying with nova.database.content_store.sha256_bytes, publishing with publish_files and reading through verified_object_root. One key is one directory <root>/<kind>/sha256/<digest>/ holding matrix.npy and a manifest.json naming the kind, the shape, the wall the entry's builder recorded, and the sha256 and size of the published file. The exterior stays runtime-only: it depends on the field and the reference moments and is cheap to pose once the matrix is in hand. Publishing to the shared operand root is blocked: the store refuses to risk a half-visible object and neither GPFS mount on this machine supports the no-clobber directory rename it requires, so a build on the production root aborts at publication after the assembly it has already paid for. Two checks the repair round owed are also outstanding and are recorded below rather than papered over: the 2,098-cell load wall has no corrected number, and the jet default-on guard has not run at the head revision.

What changed

  • nova/database/filepath.py gains operand_cache_root(), returning OPERAND_CACHE_ROOT = /work/projects/imas_gpu/sophelio/evidence/operands unless NOVA_OPERAND_CACHE overrides it. Both caches resolve their directory through it, which removes the literal conforming-jets path from the jet builder.
  • build_value_matrix builds the (target, cell, moment) flux blocks only on a miss and stores the completed matrix on a hit. Its key is a SHA-256 over the Gauss point coordinates, the cell centres, each cell polygon's vertices and vertex count, the bytes of scripts/analytic_oracle_fixtures/coupling_build.py and the bytes of nova/biot/polygonanalytic.py.
  • build_jet_matrix takes persist=True by default and keys on the unique node coordinates, the traced coupling operand leaves, the jets module source and the polygon-kernel source, matching the key the existing conforming-jets entries carry.
  • The node's own store is gone. store_operand, load_operand, operand_digest and operand_cache_directory re-implemented a content-addressed publication that nova.database.content_store already owns, so they are deleted and the builders call the store instead: the key is sha256_bytes over the joined chunks, the entry is published by publish_files, which verifies a private directory's declared files and renames it into place with RENAME_NOREPLACE, and a reader resolves verified_object_root and verified_destination and treats an absent entry as a miss rather than an error. Two builders of one key cannot interleave, and a partial entry is never visible. The same seam is what nova/imas/machine_artifact.py and nova/database/layer_fetch.py already use.
  • The receipt prices only what the calling process paid. build_seconds is the miss assembly, publish_seconds the publication, load_seconds a hit's wall from opening the entry to a device-resident matrix, and matrix_ready_seconds the wall that got the matrix ready either way. stored_build_seconds carries the wall the entry's own builder recorded as a separately named field, so a hit no longer reports a peer's assembly cost as its own; assembly_seconds, which did exactly that, is removed.

Measured load against build

Each row builds the matrix once and then reloads it, on one process, with the cache empty before the first call. The build column stands as measured. The load column was priced by the superseded protocol, which timed opening an entry rather than getting a matrix onto the device, and it is retained only as the record of what was run before the receipts were corrected; the ratio in the last column inherits that and is not a claim about the current load_seconds. All four rows of the diverted sweep at 282, 551 and 2,098 cells ran as one job (job 1287218) on the H200 reservation gpu_0003_grpA with one GPU, which completed in 24 m 53 s. Every operand reports cache_hit false on the first call and true on the second, so the load reported is a second call reading the entry the first call wrote, and the build reported is that same call's build. The 2,098-cell row is the one that makes the case: the value matrix takes 13.3 minutes to reassemble and 3.7 ms to load, and the jet matrix 4.5 minutes against 3.5 ms.

The load figure was priced by the superseded protocol, which timed opening the entry and not reading it: the matrix is memory-mapped and streamed from GPFS as it is consumed, so the old number prices the open alone. Under the corrected receipt the load figure runs to a device-resident matrix, so it carries the transfer the old figure omitted. What it still skips is the kernel compile that dominates a jet build, which is the saving that matters to a reader that only needs the matrix. The 2,098-cell row was the one scheduled for re-measurement under the corrected definition, and it has no corrected number: that job built the value matrix and died at the publish step.

Checks

  • tests/test_operand_cache.py on CPU over a four-cell hex carrier: default-on persistence, a hit with the stored build time preserved, a miss on a perturbed polygon vertex, a miss on a flipped source byte, and bitwise equality between the loaded matrix and the built DenseValues.matrix. Two further arms are marked slow: two concurrent processes building one key, and the default arm of build_jet_matrix.
  • The two-process arm passed alone on CPU (1 passed in 60.03s): two spawned children build one key concurrently, both exit zero, the matrices they built are equal byte for byte, the stored matrices are equal byte for byte, and the stored matrix equals the built one. A reader therefore never sees a half-written matrix — the completion marker is absent until the rename lands.
  • The fast gate at the head revision 07d03d9d6 reads 4 passed, 2 deselected in 19.14s, exit 0 (pytest tests/test_operand_cache.py -m 'not slow'). Its cache root is pytest's tmp_path, which is node-local, so this green is evidence about the store's publication path on a filesystem that supports the no-clobber rename and says nothing about the shared GPFS root where the store refuses to publish.
  • The jet default-on guard has not run at the head revision. The arm is marked slow because its build is a kernel compile, so it is outside the recorded gate, and the job that was to run it explicitly was submitted while the worktree still stood at 7eb4234f3, before the content-store migration landed at 07d03d9d6; its log records that earlier revision and could not be cited for head, and the job was cancelled rather than reported. What the arm covers — that build_jet_matrix publishes on its default arm and that a second call loads the entry bitwise equal — is therefore covered at head by inspection of shared code paths only, not by a run.
  • The declared mutation drops the geometry and source chunks from values_digest, so a perturbed coordinate or source byte can no longer move the key; the run turned 2 failed, 2 passed, 2 deselected, failing exactly test_values_miss_on_a_perturbed_node_coordinate and test_values_miss_on_a_perturbed_source_byte, with the digest assertion printing the same key on both sides of the perturbed coordinate. The mutation was reverted and the gate rerun green.

Publication is blocked on the shared root

publish_files lands an entry by renaming a verified private directory into place with RENAME_NOREPLACE, and refuses to publish at all where the filesystem rejects that operation, because the alternative is an object that is briefly half-visible. Measured on this machine with a direct probe of the store's own entry point: /work/projects/imas_gpu/sophelio/evidence/rename-probe and ~/.cache/nova/rename-probe both raise ContentStoreError: the cache filesystem does not support atomic no-clobber directory rename, while a directory under /tmp publishes. Both shared mounts are GPFS (HPC_T2); only the node-local xfs root beside them supports the rename. So the operand cache, whose whole purpose is a share between processes on different nodes, has no root available to it that the content store will publish to.

The 2,098-cell re-measurement under the new receipt definition was the first victim: job 1287269 (one GPU on the H200 reservation gpu_0003_grpA, one job with its rows inside the allocation) ran 12 m 53 s, built the value matrix at 2,098 cells and then died at the publish step with that refusal, exiting 1 and writing no row. The probe that produced that three-way output is kept in the run directory as rename-probe.py with its output beside it as rename-probe.out, so the refusal can be reproduced without touching this tree.

The block is not a defect in this node's code, and it is not repairable here: the two available options both belong to the coordinator. Either the operand root moves to a filesystem that supports the no-clobber rename, which no shared mount on this machine currently does, or content_store gains a publication path the refusal deliberately withholds. Until one of those is chosen, a value or jet build on the shared root assembles its matrix and then raises, so persistence must be turned off there (persist=False) rather than left on its default.
