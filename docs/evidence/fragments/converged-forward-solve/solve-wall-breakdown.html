Where a forward solve spends its time, cold and warm

On one H200, on the published diverted single-null carrier at 550 realised cells (2,105 nodes), the three programs a Newton step calls — the topology read, the booking and the map — compile cold in 29.0 s in total, of which 21.7 s is XLA compile, 4.0 s is tracing and 1.2 s is lowering, and their first execute is 0.71 s. Warm, with every program compiled and the operand store loaded in 0.18 s, one Newton step costs 0.286 ms: 0.110 ms of topology read, 0.008 ms of booking and 0.168 ms of map, against the 1 ms target. The linear solve and the batch-width-16 arm did not complete in this run, so the step total is the three measured stages and excludes the linear solve.

Each program was compiled in a fresh process with JAX_ENABLE_COMPILATION_CACHE=false and jax.clear_caches() before the trace, so the walls below are cold. Every program recompiles when the cell count changes, because every operand's shape derives from it; none compiles once and is reused across cell counts. Same-shape reuse is what the operand-carrying route was built for, and it is measured in the cold table above: two geometries whose shapes agree compile to one program because nothing geometric is a program literal. The map is the one program that still captures host constants (the profile, the policy and the axis sign), so a change to any of those recompiles it even at an unchanged shape; the negative-control reading of the one-program clause belongs to the plan's own gate and is not taken here.

What this run did not measure

  • The linear solve. The Jacobian block program was built with a vmap whose in_axes did not match the eleven carried operands, so the step's linear-solve stage has no wall. The measured step total (0.286 ms) excludes it.
  • Batch width 16. The batched arm ran after the linear solve, so it did not run.
  • The production route's own end-to-end cold and warm walls. This receipt times the three programs the Newton step calls, not ForwardSolveProfile.solve; the operand build (0.65 s carrier load, 0.18 s jet load) is reported, the solve itself is not.
  • Recompile counting by JAX's own compile log. The counter saw no lines at the handler level, so the program count of three is the three lower().compile() calls this harness made, not an independent count.
