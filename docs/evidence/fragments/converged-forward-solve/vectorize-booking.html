Cell-batched current booking

Followup f-cfs-vectorize-booking. nova.equilibrium.current.book booked cells in a sequential jax.lax.scan with unroll=1, the bottleneck of the hot path (0.9, 2.8 and 8.1 s per step at 2,000, 5,000 and 10,000 cells on the H200). The loop is now a single jax.vmap over the cell index; the per-cell body — fragment rings, membership and normal-form conditioning, and the clipped support quadrature — is unchanged. One compiled program remains, with effects batched over cells, so the booking no longer serialises across cells. The work is committed at adeff8346 (product) and 486d369ad (test).

The test file tests/test_current_book_vectorised.py holds the pre-batching booking verbatim as _reference_book, and its own copies of _conic_rings and _normal_rings as _reference_conic_rings and _reference_normal_rings, so the oracle is independent of the product's ring builders and not only of its iteration. The booked moments, the normalization and the validity receipt are bit-identical at every rung. The 2,000 / 5,000 / 10,000-cell rungs of the done-when were not run: see the caveat below.

Negative control

Declared mutation: a padded fragment counted twice turns the vectorised identity test red by test id. Applied to _conic_rings in the product (the mutation doubles the ring batch and its live counts), the identity test fails at all three rungs and the run exits non-zero; the log is logs/negative-control.log. The control proves the test is sensitive to padding, which the first, dead slice's duplicate did not exercise — hence the whole-batch double.

Autograd

tests/test_current_book_fragments.py::test_booking_jvp_matches_central_difference runs jax.jvp of the booked moments through the vectorised book against central finite differences on the smooth, axis, boundary and support stages, and passes. This is the precondition for the moment-space Newton. The same check on the certificate carrier at 2,000 cells was staged behind the row's fixture load and was not reached; the toy-cell result is the standing evidence.

Certificate-rung measurement

The 2,000 and 5,000-cell rows were submitted as one H200 allocation (job 1284815, --time 02:00:00, rows inside the allocation) running three stages per row: the booked moments through scripts/prototypes/support/book.py::measure, a compile and device-memory probe of the booked program, and the tangent check. The base tree (7c9d86bd, the sequential scan) and this head tree (the vmap) ran in the same allocation. All sixteen stages refused before booking, on both trees, with the same assertion from book._cached_machine:

assert store.group == receipt["machine_cache"]["semantic_key"]
AssertionError

The cached certificate machine resolves to a different semantic identity than the receipt that indexes it, so the row is refused rather than measured. The identity is composed by analytic_oracle_fixtures.measure.cache_identity from the analytic case's closed-form constants, the wall discretisation and the requested cell count, so the drift is in the carrier or wall the current revision computes against the constants recorded by the earlier fixture run — not in the booked program, which the base tree refuses identically. A fixture row must therefore be regenerated from the current certificate revision before these rungs can be measured. A CPU arm of the same comparison (no CUDA backend, and measure requires one GPU) was launched in parallel and refused at the same assertion, so this is not lane-specific.

The 10,000-cell rung is not attempted: its machine is being built by the carrier-requalify node, whose cache holds a analytic_oracle_hex_machine_10000.zarr lock at 2026-10-13T19:53Z and no store yet. No second machine was built, and 10,000 cells is pending on that store. The measured 2,000-to-5,000-cell scaling could not be taken, because neither rung booked.
