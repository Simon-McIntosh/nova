Cell-batched current booking

Followup f-cfs-vectorize-booking. nova.equilibrium.current.book booked cells in a sequential jax.lax.scan with unroll=1, the bottleneck of the hot path (0.9, 2.8 and 8.1 s per step at 2,000, 5,000 and 10,000 cells on the H200). The loop is now a single jax.vmap over the cell index; the per-cell body — fragment rings, membership and normal-form conditioning, and the clipped support quadrature — is unchanged. One compiled program remains, with effects batched over cells, so the booking no longer serialises across cells. The work is committed at adeff8346 (product), 486d369ad and f2a831d4d (tests).

Identity against the sequential reference

The test file tests/test_current_book_vectorised.py holds the pre-batching booking verbatim as _reference_book, and its own copies of _conic_rings and _normal_rings as _reference_conic_rings and _reference_normal_rings, so the oracle is independent of the product's ring builders and not only of its iteration. Tiled cells are compared at 1, 64 and 200 in the default lane and at 2,000 in a test marked slow. Both programs are compiled and warmed before the wall is taken, so the two wall columns compare execution:

The booked moments, the normalization and the validity receipt are bit-identical at every rung, including 2,000 cells (4 passed in 154.12 s). The wall columns are CPU binary64 on a tiled toy fixture, and they run against the batched form: the sequential reference is 15 to 52 times faster there. The cause is the per-cell body's nested jax.lax.cond, which a vmap lowers to a batched select that evaluates every branch for every cell, where the scan takes one branch per cell. That is a property of this fixture's control flow, not of the certificate carrier: on the carrier the batched program is faster at every measured rung, see the H200 rows below. The two lanes disagree because the fixture's cells are uniform and tiny, so the batched select costs more than it saves, while the carrier's cells carry the real support work. The CPU walls are reported because they were measured, and they are not evidence about the H200.

Negative control

Declared mutation: a padded fragment counted twice turns the vectorised identity test red by test id. Applied to _conic_rings in the product (the mutation doubles the ring batch and its live counts), the identity test fails at all three rungs and the run exits non-zero; the log is logs/negative-control.log. The control proves the test is sensitive to padding, which the first, dead slice's duplicate did not exercise — hence the whole-batch double.

Autograd

tests/test_current_book_fragments.py::test_booking_jvp_matches_central_difference runs jax.jvp of the booked moments through the vectorised book against central finite differences on the smooth, axis, boundary and support stages, and passes. This is the precondition for the moment-space Newton. The same check on the certificate carrier at 2,000 cells was staged behind the row's fixture load and was not reached; the toy-cell result is the standing evidence.

Certificate-rung measurement

The 2,000 and 5,000-cell rows were first submitted as one H200 allocation (job 1284815, --time 02:00:00, rows inside the allocation) with the base tree (7c9d86bd, the sequential scan) and this head tree (the vmap). All sixteen stages refused before booking, on both trees and on a CPU arm, at one assertion in book._cached_machine:

assert store.group == receipt["machine_cache"]["semantic_key"]
AssertionError

Those stores are superseded: they carry the machine schema of the fixture run that wrote them, and no revision can rehydrate them, so they are not repaired. The rungs are measured on machines built fresh instead. One H200 allocation (--time 02:00:00) runs the two-stage pipeline into a directory under the run directory: first scripts/prototypes/support/measure.py, which builds the machine and the exterior and writes the {kind}-{cells}-fixture.json identity, with NOVA_ANALYTIC_ORACLE_BUILDER=device so the 2,000 and 5,000-cell couplings build on the device; then the booking stage. Each machine is built once and booked twice, with the base tree's current.book and with this head's, because current.py is the only file that differs between the trees, so a second machine would measure the builder rather than the booking. Each booking is taken on the analytic certificate state and on one Picard image of it, the state the flux map returns.

One H200 allocation (job 1284869, --gres=gpu:1, --time 02:00:00), built each machine once and booked it twice: once with the base tree's sequential current.book and once with this head's current.book. The 2000-cell machines realised 2098 cells (diverted) and 2105 (limited); the 5000-cell machines realised 5158 and 5167. Both arms book the same analytic certificate state, so the only difference between them is the program.

The two arms book the same state, and their booked moments agree to floating-point reassociation: at 2,000 cells the largest difference is 3.6e-12 on the cell current (4.5e-16 relative) for the limited machine and 1.4e-14 (6.2e-16 relative) for the diverted one; at 5,000 cells it is 1.8e-12 (4.4e-16) and 7.1e-15 (6.9e-16). This is the certificate carrier's counterpart of the bit-identical result on the tiled CPU fixture.

The speed-up is real at every rung, and it is paid for in device memory: the batched program's peak is 7.8 to 10.6 times the sequential program's at 2,000 cells (7.75-7.78 GB against 0.71-0.74 GB) and 7.4 to 8.0 times at 5,000 cells (22.24-23.71 GB against 2.98-3.03 GB), and it compiles 1.1 to 1.7 times slower. The measurement is taken on one device per process, so the two peaks come from the same machine load and differ only by the program. Extrapolated to the 10,000-cell rung the batched peak would be tens of gigabytes, which fits the H200's 141 GB but is the binding constraint on how far the batching scales.

The one-Picard-image state is not reported. The flux map returns its image on the operator's own sample block (5,137 flux values for the 2,098-cell diverted machine, one sample row per cell), while current.book consumes flux on the topology read's per-cell stencil (14,686 values, seven points per cell), so the image cannot be booked through this seam without the operator's own partition reconstruction. The reconstruction this node wrote failed its own check: applied to the analytic state, which it must reproduce, it disagreed with the closed-form flux at the sample points by 1.0 times the flux span for the limited machine and 0.90 times for the diverted one. A state produced by that recipe is not the Picard image, so no number from it is quoted. The follow-on job (1284869, completed after 23 minutes) booked that state anyway, for both arms on the limited 2,000-cell and diverted 5,000-cell machines, and those four walls are withheld for the same reason. sample_flux_field evaluates a per-cell flux polynomial at the requested points from a state whose own sample block sits at a reconstructed point set, so the reconstruction is an interpolant of the wrong coordinates rather than the flux map at the read's stencil. The four rows above are on the analytic state, which is the measurement that settles the cost: the booked moments agree between the arms, and the batched program is faster at both cell counts and both topologies.
