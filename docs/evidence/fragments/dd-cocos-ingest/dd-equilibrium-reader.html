Why the inverse negation goes rather than stays

The value was coupled, not internal: tests/test_pulsedesign.py::test_ids_file_cache shows psi_boundary tracking an input IDS field, so it arrives in the source read's convention. Under DD3 that is COCOS 11, whose psi is the negative of COCOS 17's, so -psi_11 was exactly the internal COCOS 17 flux and the negation was an implicit 11 → 17 conversion. The reader now performs that conversion once, so the negation would apply it twice. For a DD3 source the value handed on is unchanged (the factor is -1); for a DD4 source the sign is corrected, which is the defect the line carried.

The reader renormalises to psi_norm, and a psi sign reversal leaves (psi - psi_axis) / (psi_boundary - psi_axis) unchanged, so no normalised quantity moves and only a signed one can show the translation at all.

The one field that did not match, and the wall that was never in the way

The signed arm now passes on both conforming pulses. The field that did not match for most of the node is worth recording, because the diagnostic that settled it was a measurement rather than a candidate list.

  1. The reader's psi_boundary read -100.63715074656471 at slice 0 of CORSICA 130506/6 while the raw global_quantities.psi_boundary read 102.454, a 1.8 percent magnitude difference. psi_axis matched its raw counterpart exactly on the same read, so the factor and its sign were right.
  2. The cause was a source misattribution, not arithmetic. Parameter0D.build appends global_quantities.psi_boundary into psi_boundary, and then build_boundary_shape runs self.append("time", "psi", "boundary_separatrix", postfix="_boundary") over it, so the dataset carries boundary_separatrix.psi and the global scalar is gone. The two stored nodes differ by about 1.8 percent, which is ordinary reference data: a published boundary scalar need not equal the separatrix flux.
  3. The fix is the declared path, not the value: convention_fields now names equilibrium/boundary_separatrix/psi for psi_boundary, the node the dataset actually holds, with the reason recorded in the class docstring. Keeping both nodes as two separately named fields was the alternative and was rejected: it would have changed the reader's data model for a name no consumer and no test reads, while the declared path is a statement of provenance the record can be checked against.

The confirmation is a printed measurement rather than a reading of the code. All three numbers come from one DBEntry read at 3.41.0 for CORSICA 130506/6 slice 0: global_quantities.psi_boundary 102.454, boundary_separatrix.psi 100.63715074656471, and the reader -100.63715074656471.

A wall failure recorded earlier at this node is withdrawn, and the correction matters more than the failure did. The reader was reported as dying in nova/frame/ on the machine-description read. It does not: constructed as EquilibriumData(pulse, run, dd_version=...), it builds a DD3 pulse end to end. The KeyError was reached only by the earlier fixture, which was built around an already-opened IDS and so carried no URI and no Data Dictionary major of its own. The pre-existing nova/frame defect is real when the machine is read that way, but it was never this node's to clear, and the Wall(...dd_version=...) change landed against it stands on its own as a correctness fix rather than as the repair of a blocker.

Two defects on the way were this node's to find and are fixed, each with the line named. And one instruction in the brief was wrong, which cost most of a node's time:

  • nova/imas/scenario.py:89 stored ids_properties.homogeneous_time as the IMAS node itself, and the zarr group refuses to serialise an IDSInt0D, so a first read of an uncached pulse could not store at all. Now int(...). This is a serialisation fix the reader needs to store a pulse at all, not a sign site: it changes no quantity's value or orientation, and it carries no COCOS factor.
  • nova/imas/equilibrium.py's wall property read the machine at the latest published major rather than the pulse's. It now carries ids_dd_version.
  • The brief's version source is wrong. The written DD versions this node was told to take from tests/data-manifest.json are not there. They are in tests/test_dd_translator.py, in DD3_PULSES and NON_CONFORMING: CORSICA 130506/6 at 3.41.0, DINA 105052/1 at 3.38.1, DINA 105069/3 at 3.39.0, and DINA 105014/1 and 105013/1, both at 3.38.1.
  • The fixture's construction was the reason the machine looked like it defaulted to DD4. EquilibriumData(ids=..., filename=...) leaves the reader's own URI and major unset, and the machine read then falls back to the latest published major. The tree's own idiom, used by tests/test_database.py, is EquilibriumData(pulse, run, dd_version=...), which carries both. The earlier reading of this node's failure as a machine-major defect came from the fixture, not the reader.

A cache entry written before this change

The reader translates on build only, so a store written before this node is the one place where the translation could be silently absent. The identity that finds it is the pulse, run and Data Dictionary version, all unchanged by the reader's own convention, so the entry is found and every name in it matches while the signed quantities are the source's.

The reader now treats the recorded convention as part of what it reads, not only what it writes. EquilibriumData.load requires attrs["cocos"] to be NOVA_CONVENTION; an entry that carries none, or another, is evicted and re-raised as a cache miss, which is the existing rebuild path rather than a new one. The tests hold both sides without opening a pulse, since a stale entry is the whole subject: a store written with cocos = 11 is rebuilt, and one written with the reader's convention is served untouched. Reverting the override reddens the first and leaves the second green, which is what makes the pair discriminating; log at logs/negative-control-stale-cache-reverted.log.
