The DIII-D forward solve takes its conductor current from the corpus channels, not from the field the correction driver patched, so a corrected coil current never reaches the solved state

The cohort reads the conductor current twice and the solve uses the second read. A driver that installs a coil-current change at the build-time seam — the one the benchmark makes available, benchmarks/diiid_forward_gs_match.py:1356's external_current=_source_current(...) — changes the operator's own field by 1.56 Wb of flux and changes nothing else: the solved current vector, the solved external field and the terminal state all stay where the measured currents put them. Measured on frame 137D, the seam arm's built field fell from 6.063174 Wb to 4.502726 Wb while its terminal flux differs from the base arm by 2.0·10⁻⁵ Wb and its lower X-point by 0.0006 cm. The same solve, given the same currents through the corpus columns instead, moves the terminal flux by 1.2045 Wb and the lower X-point by 6.7 cm.

The ratio between those two numbers is the finding: the seam change is 60,000 times smaller than the change it is supposed to cause, which is the numerical noise of the fixed-point iteration, and the corpus change is the physical response the correction was trying to produce.

The conductor current is read twice, and the solve uses the second read

_build_profile passes external_current=_source_current(row, machine.physical, names, time) into ForwardProfile.from_lattice (benchmarks/diiid_forward_gs_match.py:1356), which stores it on the operator at nova/equilibrium/forward.py:694. _source_current is a module-level function, so replacing it is the only conductor-current seam a driver can reach from outside, and a replaced vector really does land in the operator.

solve_frame (benchmarks/diiid_forward_gs_match.py:2453) does not use that vector. At line 2462 it calls shipped_current_at (nova/imas/diiid_current.py:160), which reads each conductor's measured magnetics_<conductor> column out of the corpus row. At line 2471 it calls complete_profile_current_adapter, whose body (nova/imas/diiid_current.py:258) replaces the operator's external_current with resolution.current(resolution.prior_mean_a) — from the second read, overwriting the value the first read set. It then passes resolution.current(()) to _solve_registered at line 2494, and that vector is what the solve actually uses, carried on ForwardSolveRequest.current at nova/equilibrium/forward.py:2715 (seed) and :2727 (solve). _solve_wall_topology_frame (benchmarks/diiid_forward_gs_match.py:4560) repeats the same pair of calls at lines 4585 and 4591, so the same conclusion holds on that path.

One sentence carries it: a change installed at the build-time seam reaches the operator's stored field and nothing else, because the adapter replaces that field and the solve takes its current from the adapter's resolution. A change installed in the corpus row's conductor columns reaches both readers, and therefore reaches the solve.

Instrument checks

Four instrument facts are recorded because each one could have been misread as a result.

  • The positive control is the row arm, and it must move the state. It moves the terminal flux by 1.2045 Wb and the lower X by 6.7 cm. A measurement of "no change" is only a finding when a change that must appear does.
  • The seam arm's own field changed. Its pre-adapter sup falls by 1.560 Wb, so the patch reached the operator; the invariance is downstream of the build, not a patch that failed to apply.
  • Two defects in this driver were found by its own numbers. The script's distance conversion was 1000 cm/m rather than 100, so every printed arm record states ten times the measured displacement; the stored null coordinates are in metres and the distances in the tables above are read from those, and the conversion is corrected. And the cohort-control arm — solving through solve_frame itself — crashed inside _display_map → build_display_flux_map with IndexError: index 0 is out of bounds for axis 0 with size 0 on the non-converged state, which is a defect of the display map on a state that never qualified a diverted root, not of this measurement.
  • No in-process warm arm ran. The driver's warm pass is a second process against the same compilation-cache root, so the 4.1·10⁻¹³ Wb agreement is between two processes and not a program reused inside one. The persistent cache itself could never be written on any node used here, KeyError: 'getgrgid(): gid not found: 89486', so the warm state that hypothesis is about was never reached: a reused program had to be falsified by the row arm, which moves the state, and by the program key, which holds no current value at all. The two-process agreement of 4.0·10⁻⁶ Wb is the tighter statement either way: an empty persistent cache and a fresh process did not shift the state, and the compile-cache hypothesis needs a shift of the size of the control to survive.

Proposed product change

The defect is not a cache, a stale program or a fixed-boundary solve. It is that the conductor-current authority is ambiguous: two call sites read it, the second overwrites the first, and nothing states which is authoritative. A driver that patches the seam the build makes available gets a converged-looking equilibrium solved with different currents, and no receipt records the disagreement — the run's current-inputs.json names the corrected vector while the state was solved with the measured one.

Preferred: make the second read check the first. In complete_profile_current_adapter, before replacing the operator's field, compare the vector the operator already carries against the resolution it is about to install, and raise when they disagree. The comparison is exact rather than approximate, because both quantities are assembled from the same conductor order and the same turn multipliers, so matching inputs agree to the bit and a build-time override is refused with the answer raised rather than silently discarded. The adapter is the only writer the solve reads, so a build-time override is either a mistake or an override that must be declared, and the two are indistinguishable from inside the adapter; failing closed is the form that makes a future arm driver learn that instead of losing an afternoon to it.

Alternative: remove the unread field. Drop external_current=_source_current(...) from _build_profile at line 1356, making the adapter the single authority. That is a one-line change that removes the trap, but it leaves a driver with no seam at all and no error to learn from.

Either is a product change to nova/ or to the cohort. Nothing in nova/ or tests/ was modified.
