Per-layout traced-polygon vertex capacity from the level-run count

Followup f-ecq-per-layout-vertex-capacity; decision traced-vertex-capacity-for-multi-run-cells locked to per-layout-derivation. Base c00300b91, landed commit 5b84f5bcb.

traced_polygon_vertex_capacity (nova/equilibrium/separatrix_clip.py:61) now takes the number of level runs the layout presents and returns level_run_count * 128 + straight_vertex_capacity, instead of the fixed one-arc bound 128 + straight_vertex_capacity. The count is a Python integer threaded through AtomicCellMesh.traced_clip → _traced_clip → traced_polygon_vertex_capacity; it defaults to one run, so the packed shape stays a compile-time constant and every single-run row is bit-identical to the one-arc bound. vertex_capacity and refused_cell_count remain the receipt fields, unchanged.

Measured

Module gate, one fresh process, JAX_PLATFORMS=cpu, shared root interpreter, PYTHONPATH naming the worktree: 28 passed in 125.88 s, no failure added against the pre-change base for this module (log gate-module-after.log in the run directory).

A two-run layout (a saddle level function on one rectangular cell, AtomicCellMesh.support_capacity 8) declared with level_run_count=2 is admitted: refused_cells() == 0, vertex_capacity == 264, vertex_count == 260 (both 128-sample arcs realised), area == 0.75, and assert_no_refusal() returns. The same layout under the one-arc bound (level_run_count=1, capacity 136) is refused visibly: refused_cells() == 1, vertex_capacity == 136 on the receipt, TracedCapacityRefusalError raised, included 0, vertex count 0, area 0.0.

Negative control (declared: force the one-arc bound and observe the refusal return). A pytest plugin forces traced_polygon_vertex_capacity to drop the per-run multiplier; the admission test then fails with assert 1 == 0 on support.refused_cells(), EXIT=1, log negative-control-one-arc-bound.log.

Not yet demonstrated

The diverted single-null row at 110 cells (cell 9, 260 vertices, area 0.00708; derived two-run bound 2 × 128 + 34 = 290) is not measured here. Reaching it through the production route needs the layout's run count to be declared at forward_operator._profile_support, which is outside this node's write fence and is owned by a concurrent node; the derivation above is what that caller consumes. Measured through the unmodified production route the row still derives the default one-run bound (162) and refuses cell 9, so the diverted-row clause of the done-when is unmet and the production wiring is carried as a follow-on.
