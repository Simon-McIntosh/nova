Declared negative control, satisfied in both directions. Arm (a) created 1423 autotune entries under its fresh root and arm (c) created 0, so the harness reached the cache and the file-level comparison is not void. All four arms created the same 266 compile entries, and each missed all 266 on its cold pass before settling to 0 or 27 misses on the repeats, so the persistent compile cache behaves identically under every configuration measured. The cache guard's per-pass receipts are in the arm logs under the run directory's xla-autotune-arm-logs/.

What the arms found. The cold compile wall is carried by the same eight of 266 programs in every arm and sums to 76.0 to 81.0 s across them, a spread of one program's rounding; the other 258 programs record 0, which is below the guard's one-second resolution rather than a claim that they compile instantly. Steady-state solve walls overlap across all four arms (152.4 to 222.0 s) and each arm ran at a different point in a 55-minute window on a node carrying two other jobs, so no arm separates on solve wall at three repeats.

Recommendation for the fusion-autotuner decision, from (d) against (c). Arm (c) leaves the autotune directory empty; arm (d), with the fusion autotuner disabled by XLA flag, still writes 12 entries a run, so the flag closes the fusion records without closing the directory. The two arms do not separate on compile wall (76.0 against 81.0 s) or on solve wall within this measurement's scatter. Set the persistent cache's XLA caches to none, rather than passing the XLA flag: on this target keeping the autotuner costs nothing the instrument can see, the write path it opens is the demonstrated cost, and only the cache setting closes it completely. Either choice changes the runtime-versioned cache directory, because _persistent_cache_runtime_identity hashes both settings into its name, so the pin must be republished from a fresh pre-warm carrying it.
