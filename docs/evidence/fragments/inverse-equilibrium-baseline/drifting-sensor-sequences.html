Drifting sensor noise in a held ITER state: the fixture machine could not be built inside the node's wall, so neither code's sequence was measured

This node was to write 200 slices of ITER magnetics rows from one held generating state twice — once with a 1/f sequence and once with white noise of the same marginal size — and read both with the nova magnetics fit and with imas-efit, reporting the per-slice and 50-slice-mean error of the axis position, the boundary flux and q95. No sequence was measured. The blocker is upstream of the noise: the section-1 ITER fixture machine, which both codes' rows are generated from, does not build inside the node's wall on the allocation it ran on, and the sensor-row stage that follows the build exits without a traceback. What follows is the measurement of that blocker, the code that runs the study once the machine exists, and what a next run needs.

The sensor-row stage exits without a traceback

Immediately after the solve, the case evaluates its sensor rows through the section-1 helpers: _PlasmaDiagnosticSource over the cell set, _known_field_reader over the pulse's static magnetics, and _total_observations. Three processes reached that stage and exited inside it, each leaving the same two lines and no exception text:

All three were started together in the one allocation and each died at the same stage, the three deaths spread over five minutes. A fourth process, started alone after two of those had exited, passed the same stage: it sat at point for 9 min 1 s, advanced to a probe stage, and was stopped by the run's cleanup when the node's window closed, without having written rows. So the stage is survivable and the exit is not deterministic. The run's step is bounded at 144 G and the killed processes held 10 G of resident memory at the last sample, so a memory limit on the step is not the explanation; the node's own kernel log records an out-of-memory kill only for a different job's cgroup step.

The consequence is exact: rows.npz is written by the same case construction, after this stage, so no rows exist, and the imas-efit arm — which reads those rows as an IMAS magnetics pulse — was never startable. Neither code produced a slice.

What the node does deliver

A complete, smoke-tested study driver in the run directory /home/ITER/mcintos/.config/reckon/crew/runs/r-20261115T202148674467-drifting-sensor-sequences/study/, written against the section-8 route so that the measurement is a run and not designed by its author:

  • study.py — reads the ITER pulse's own 24 flux loops and 48 poloidal-field probes (position plus poloidal angle) and the case's sensor geometry; builds the generating state through the section-1 helper; writes the noise-free rows and the generating reference; shapes white noise into a coloured sequence in the Fourier domain with a flat band below a corner at 4 cycles per sequence and f^-1 above it, normalising every sensor to unit standard deviation before scaling by factor x sigma so the two sequences carry the same marginal size; runs the nova MagneticsFit on the same coefficient basis [1, -1] section 8 established as imas-efit's resolved one for this case; writes the rows as an IMAS pulse and runs the imas-efit binary through the section-8 configuration with both degrees named and both priors at zero weight; and re-reads imas-efit's stored equilibrium for axis, fluxes and q95.
  • analyse.py — merges the workers' per-slice shards, and reports per code and sequence the axis RMSE, the boundary-flux RMSE as a fraction of the flux span, the |q95| RMSE, the lag-one correlation of each, the error of the mean over 50 consecutive slices, and the ratio of that realised mean error to the receipt's own sqrt(dpsi^T Sigma dpsi / 50) mapped through a central-difference Jacobian on the shared amplitude.
  • figure.py and overlay_figure.py — the axis-against-slice panel per code and the overlaid line contours of the two codes' states on one physical level array, with both null sets, the wall, and the axis off.

The analysis and figure paths were exercised end to end on synthetic 200-slice, three-shard rows: the control discriminates by construction (lag-one about 0 on the white series, about 0.999 on the smooth series), the shard merge reproduces the 200 slices, and the figure is written. That establishes the machinery, not the measurement.

Limits and what a next run needs

No clause of the node's done-when is answered: no sequence, therefore no RMSE, no lag-one control, no threshold crossing, no covariance ratio, and no swept index or corner. The lead takes the work as blocked rather than partial.

A next run needs, in order of leverage: (1) the machine built once and published as a store both arms load, under the evidence root rather than a per-run directory, because the build — not the fit — is the wall; (2) a wall of at least four hours on a CPU allocation for the 120-cell build alone, or a GPU allocation for the build as well as the fits; (3) the sensor-row stage's silent exit diagnosed: it is the point at which the run dies, it prints no traceback, and the section-1 helper it sits in is shared with the section-6 and section-8 records, so the cause is worth knowing independently of this node.

The mesh is 120 cells, not the 500-cell section-1 reference mesh; a reader comparing costs with section 8 should hold that difference.
