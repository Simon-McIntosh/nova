Drifting sensor noise in a held ITER state: the rows exist and the generating state qualifies, but each reconstructing code stopped at a measured limit before a sequence

This node was to write 200 slices of ITER magnetics rows from one held generating state twice — once with a 1/f sequence and once with white noise of the same marginal size — and reconstruct both with the nova magnetics fit and with imas-efit, reporting per-slice and 50-slice-mean error of the axis position, the boundary flux and q95, the lag-one controls, the noise-size crossing, and the spectral-index and corner sweeps. No sequence was measured. What did land is everything upstream of the sequence, at the full 500-cell mesh. The two arms then stopped at two different measured limits: the nova arm exceeds the 16 GB of a P100 when it instantiates the CUDA graphs of the sequence stage, and imas-efit refuses the pulse because the DD 3.39 ITER machine IDS carries no error on its passive-circuit currents.

The measurement ran on the section-1 ITER fixture (tests.reference_case(), pulse 135011 run 7, slice 353, DD 3.39.0) through the section-1 helpers in tests/test_equilibrium_magnetics_fit.py at the worktree revision this fragment is committed with. The run directory holding every receipt cited below is /home/ITER/mcintos/.config/reckon/crew/runs/r-20261115T202148674467-drifting-sensor-sequences/study/.

The nova arm: the 16 GB card cannot hold the sequence stage's CUDA graphs

The case builds and solves at 500 cells on a P100 — the build and generating solve above are that run — and the sensor stages that the previous record saw exit silently now complete: point 3 min 54 s, poloidal_flux_loop 8 s, a second point stage 7 min 8 s, probe 30 s. Their silent exit was the forked worker pool, and it is gone when the pool is pinned serial (NOVA_FORCE_SERIAL_POOLS=1 sets the polygon-analytic worker count to one).

and one shard alone reproduces it, at the first request for device memory rather than at the end of the run: job 1327751's log opens with Failed to allocate device memory of 11.92GiB (12801015808 bytes): RESOURCE_EXHAUSTED: CUDA_ERROR_OUT_OF_MEMORY, walks down through 10.73, 9.66, 8.69, 7.82 and 7.04 GiB, logs Retry CUDA graph instantiation after OOM error twice, and then raises the exception above. The card is a Tesla P100-PCIE-16GB; the H200 rung of the lane could not be used because node 98dci4-gpu-0003 held 7 of its 8 cards, and the lane's H200 rung on this base fails before the payload with FileNotFoundError: 'bwrap' inside the reckon sbatch shim, so the arm was never given a device with memory to spare. No nova slice landed, therefore no per-code RMSE, no lag-one control, no threshold crossing and no sweep row.

The imas-efit arm: the binary loads, then requires an error on the passive circuits

imas-efit now loads in the lane. Its first failure was a link error — libgsl.so.25: cannot open shared object file (exit 127) — and it resolves with GSL 2.7's lib ahead of GCCcore 13.2.0, HDF5 1.14.3, netCDF and its Fortran and C++ companions, PSPLINE 2.0.1, Mamba and Blitz++ (verified by ldd reporting no missing library). The next failure is inside EFIT++ itself, identical for all eleven arms and complete in seven seconds:

[info] [phase_timing] phase=imas_read_pulse slice=NA elapsed_ms=87.856072
[error] The IDS field for data error has not been set :
efit passive circuit:
identifier=0
[error] Terminating EFIT++ ...

The split-entry route reads the pulse's magnetics and the machine's pf_passive, and it requires pf_passive.loop[0].current.data_error_upper. Reading the machine entry directly shows why that cannot be satisfied from this machine: DD 3.39's pf_passive.loop[i].current is a numeric FLT_1D — the entry holds 103 loops, homogeneous time, and loop[0].current is an IDSNumericArray with no data_error_upper member at all. So the efit arm's blocker is not the rows: the pulse it was given carries 200 slices of shaped rows, the wall read succeeds (57 points, one open unit resolved into a limiter), the pulse itself parses, and the abort is on an error field the DD does not define for the machine's passive currents. No efit slice landed, so the two-code comparison the node exists to make was not made.

What exists to run again

Every stage up to the slice is exercised end to end and receipted. In the run directory:

study.py (modes nova, efit, overlay), analyse.py, figure.py, overlay_figure.py, build_fragment.py, receipts_to_jsonl.py, and the orchestrator run_all.py --shards N --phases build,efit,nova,sweep. Each fit writes one atomic per-slice receipt as it lands and converts a slice's failure into a named failure receipt without stopping the shard, so a cut arm still reports the slices it reached.

The two fixes a next run needs are stated as the measurements above give them. The nova arm needs a card whose memory covers the sequence stage's 11.92 GiB device allocation, which a 16 GB P100 does not, or command buffers disabled in the payload's own environment; and the H200 route needs the lane's h200 rung repaired, because that rung dies before the payload (the reckon sbatch shim calls a bwrap binary that does not exist on this base), so a submission has to come from a session that is not fenced. The efit arm cannot be fixed by adding errors, because DD 3.39 gives the machine's passive currents no error field: it needs either a run in unified mode, where the pulse's own pf_passive is read and its currents can carry an error, or a passive configuration that does not read the machine's passive currents as data.

Limits

No clause of the done-when is answered: no sequence, no RMSE, no lag-one control, no noise-size crossing, no covariance ratio, no swept index or corner, and no figure. The record therefore does not claim a drift or white sequence result, and no number above is a reconstruction error.

The generating state is a held state at its own patch, not a DIII-D equilibrium, and its q95 comes from one flux-map calculator for both codes — the calculator exists, the second code never produced a map to apply it to.

A reader comparing costs should note that the machine build, not the fit, is the wall: 25 minutes of the titan allocation above produced the 500-cell machine and the generating solve together.
