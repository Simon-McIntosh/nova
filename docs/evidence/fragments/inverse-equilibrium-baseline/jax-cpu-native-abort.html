The native abort when a second known-state machine compiles in one process: what accumulates, and the release that stops it

Result. A finished machine's loaded executable is not owned by the object that built it. JAX's staging and dispatch caches hold it, so dropping the profile or the receipt frees nothing: the process keeps the machine's address-space mappings, and each CPU free-boundary solve maps about 28,500 of them. A second machine compiled on top of the first pushes the process toward the kernel's per-process mapping limit (vm.max_map_count, 65,530); when it runs out the process dies inside XLA's next allocation with Fatal Python error: Aborted and exit 134, and no Python-level handler can catch it. The known-states module now releases the finished machine's compilations before it builds the next one (nova.jax.config.release_compilation_caches), which drops the mapping count by 89% and lets two machines run through one process where the same two abort without it.

The reproduction: two cases, one process, exit 134

The unfixed tree was extracted at base e28db604e and run with the same command and interpreter as the fixed tree, on the same host, against the same per-host compilation cache:

python -m pytest -q tests/test_equilibrium_magnetics_fit_known_states.py -k 'solovev or mast'

Solov'ev passes (one dot), then the process dies compiling MAST: Fatal Python error, the shell reporting 6067 Aborted (core dumped), EXIT=134. Nothing in the log names a test failure, because the abort is native: it arrives between the first case's assertions and the second case's, which is exactly the boundary the module has to cross to run its cases in one process.

The abort site moves between runs and revisions. The previous node's runs name deserialize_executable at one revision and backend_compile_and_load at another; under this node's instrumented runs the process survived until it was killed for memory, never reaching the mapping limit because the instrumented driver generates two machines with a single program each rather than the full fit and resolve. The site is whichever native allocation comes first, which is why a fix aimed at one function would not hold.

What accumulates, measured

Mappings and resident size were sampled every two seconds from /proc/self/maps and /proc/self/status while one process generated the cases one after another. Resident size stays near 5.5–6.1 GB throughout; it is the mapping count that accumulates.

In the run without a release, the second machine's build started from the first machine's 28,544 mappings and added its own, reaching 30,246: nothing the first case finished with returned. Only the cache clear returned any of them. Clearing the caches removed 25,523 mappings in one call, 89% of the total, for 89 MB of resident memory. The two readings together are the mechanism: what accumulates is mapped executable images, not heap, and only the cache clear releases them.

The kernel limit is not theoretical. A previous node's sampler recorded 65,271 mappings against a limit of 65,530 while a worker was compiling, which is the same bound the abort lands on.

The fix

nova.jax.config.release_compilation_caches() clears every JAX staging and dispatch cache, collects, and records a CompilationRelease with the executable counts either side and the number of objects collected, so the release is measurable from the process rather than inferred. It is the same private release the threshold-driven bound_compilation_retention uses, now reachable unconditionally.

The known-states module calls it from its case fixture, before building a machine it has not built yet:

def get(name):
    if name not in built:
        release_compilation_caches()
        built.add(name)
    return table(name)

The condition is deliberate. A case already built is returned without releasing, because releasing there would discard the compilation the test is about to use: test_displaced_flux_loop_is_identified runs on the Solov'ev case the recovery test already built, and must not recompile it.

A count-based ceiling cannot do this work. One machine is a handful of executables against a ceiling of 1024, so the repository's existing retention hook never fires for a four-test module; the quantity that runs out is mappings, which no executable count reports.

The fixed tree in one process

With the fix, the same command over both cases that abort on the base tree runs them both in one process: two dots, no abort, where the base tree dies on the second. The full module was then run with the four slow cases selected. Under the module's own @pytest.mark.timeout(3500) guard, the third case (ITER) reached the guard: the fixed-tree arm logged two passes and then Timeout, and the guard's bound is the near neighbour of the first case's own measured cost (3,266.66 s at the previous node), so a cold per-host compilation cache pushes a case over it. That is a property of the guard rather than of the abort, and it is why the recorded full-module arm at 269ee501a repeats the run with the guard disabled and the four cases unguarded. That arm ran all four cases in one process in 7473.98 s and finished with pytest's line 1 failed, 3 passed, 5 warnings in 7473.98s (2:04:33): Solov'ev in 1755.21 s, MAST in 1648.29 s, ITER in 3747.39 s, and the displaced case in 312.28 s. No case aborted. ITER's cost is what the guard measures against, and 3747 s exceeds the guard's 3500 s floor on this cold per-host compilation cache, so the guard, not the case, is what the earlier arm stopped on.

The one failure is not the abort. The displaced case ended with jax.errors.JaxRuntimeError: INTERNAL: Failed to materialize symbols while loading a program, and the run's warnings name persistent-cache entries it could neither read nor write. That is a catchable exception raised from a corrupted or unreadable cache entry on this host, distinct from the native abort: the abort terminates the process with no Python frame, and this one names a program and continues. The release makes a case re-read a machine's programs from the persistent cache instead of retaining them in memory, so a bad entry on that path now surfaces as this error where it would previously have been skipped; the entry state is the thing to repair, not the release. That case then run alone on the same tree, at c6f8ac302 and with the release still in its fixture, ends with 1 passed, 3 deselected, 3 warnings in 1428.03s (0:23:48): the same code path passes in a fresh process, so the four-case arm's failure was transient cache state rather than the release.

The fast population the default lane actually runs is unaffected. The default marker selection over tests/test_equilibrium_magnetics_fit.py ends with 46 passed in 5.14s at the base revision e28db604e and with 46 passed in 5.06s at the head c6f8ac302, with the worktree's own nova package on the path in the second run: the same 46 tests pass either side of the change, so the release costs the fast lane nothing.

The parallel arm: no abort, three timeouts

The same module under -n 8, on a 16-core and 60 GB allocation at head 50200153d, ran all four slow cases in one job with no Fatal Python error line anywhere in its log, and ended with pytest's line 3 failed, 1 passed in 3543.31s (0:59:03). That log (~/.cache/nova-s29/abort-gate/n8.log) carries no revision header of its own; the arm ran at 50200153d. The three failures are test_known_state_recovery[solovev], test_known_state_recovery[iter] and test_displaced_flux_loop_is_identified, and all three are the module's own guard: Failed: Timeout (>3500.0s) from pytest-timeout. The guard is what the parallel arm runs into, and three workers carried the four cases. Each was compiling and solving a machine at once on the same sixteen cores, so every case still working when the 3500 s guard fired was reported as a timeout in the same second the run ended; the one case that finished inside the guard passed.

This is the distinction the whole node turns on. The abort ends the process with no Python frame and no per-test result, and the parallel arm produced a per-test failure with a named reason for each case, a passing case, and a summary line. The earlier attempt under this worker's own 24 GiB step was killed by that ceiling instead (EXIT=137), which was an out-of-memory of the approach rather than evidence about the abort; the dedicated allocation is what made the arm measurable.

What changed

nova/jax/config.py gains release_compilation_caches and the private _release_compilation_caches it shares with bound_compilation_retention, and lists the new function in __all__. tests/test_equilibrium_magnetics_fit_known_states.py imports it and releases before each new machine in its case fixture. tests/test_jax_config.py pins the release: one clear per call, the recorded counts, and the history the release appends to.

No assertion was weakened and no case was removed. The measurement's cost is unchanged apart from the release itself, which is one cache clear per new machine.
