The census read pins the production mesher's count

tests/test_imas_iron_read.py::test_census_mesh_matches_previous_read builds its own census polygons by executing scripts/sheet_tile_census/measure.py's description.iron_segments loop against the WEST dictionary pin, then meshes each raw iron_core outline with the production nova.biot.magnetisation._mesh. Both the script path and the comparison oracle call that same mesher, so the previous len(actual) == len(expected) > 0 could not see a change in cell count or partition. The test now asserts the measured count, the per-segment partition in a comment, and a SHA-256 digest over the ordered polygon vertices.

Why 1694, not the 1696 of the earlier fragment

The same six outlines at the same spacing give 1696 cells through scripts/prototypes/iron_magnetisation/magnetisation.py::mesh and 1694 through nova.biot.magnetisation._mesh: the counts differ only in the sixth segment (244 against 242). The census script still imports the prototype mesh, so its own assert count == {0.08: 1696} is a prototype-mesher pin; the read test substitutes the production mesher, so its pin is 1694. This is not a regression and no mesher is changed here.

Negative control

Changing the test's own spacing from 0.08 m to 0.07 m on both sides leaves the script polygons and the oracle in agreement but meshes 2135 cells, so the restored pin fails while the unmutated test passes: 17 passed, 1 failed with assert 2135 == 1694, EXIT=1. The mutant was reverted before the delivered commit. Unmutated, the module passes 18 tests and the scoped gate over it plus tests/test_artifacts_carry_no_worktree_paths.py passes 19.
