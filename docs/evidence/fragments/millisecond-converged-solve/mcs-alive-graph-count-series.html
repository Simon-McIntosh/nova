CUDA executable-graph lifetime across distinct programs

The prior release claim was reviewed and withdrawn. A fresh no-program settled-reread attempt found that the current XLA log surface emits no count on demand.

Twenty-program result

Titan job 1280456 at revision 82f26d0a reported no_growth_observed: the alive count was 1 at program 1 and 1 at program 20 across 20 distinct programs. Graphs therefore do not accumulate per compiled program, and the alive count is not process-cumulative across programs in this ladder.

Whether dropping an executable releases its graph is not measured. Job 1280456 reported 2 alive after dropping the handles and graphs_released_after_drop −1, but that is not a demonstrated release. The command-buffer-disabled arm logged no count events at all: its reported 0 is an absence of lifecycle events, not a measured zero.

A later --analyze-existing pass at a9c29fa7 changed the counting logic and reported after-drop 0, released 1, and executable_scoped_not_process_cumulative. Those post-hoc values are withdrawn: the pass chose the first destruction event in the drop interval, which was ordinary execution churn, not a settled reading. The receipt preserves these values as withdrawn and uses the Titan job's own no_growth_observed result as its active verdict.

Fresh Titan job 1280468, running commit 021e72442, emitted before_drop, dropped ten handles, cleared caches, synchronized, executed zero programs, then emitted settled_reread. XLA emitted no count between those markers; the next count was logged at process teardown. The instrument therefore produced no settled count or verdict. In these runs, XLA logs a count only on a graph lifecycle event; the settled reread found none before its marker.

A successor needs an on-demand runtime count query that can log after synchronization without dispatching a graph, followed by a completed two-arm job.
