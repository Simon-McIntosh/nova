What the identity evidence does and does not show

The passing guard for the weight branch is the vertex primal-JVP row tests/biot/test_vertex_term_tangents.py::test_tangent_matches_primal_jvp, which passes at both arms in the gate above. The two passing test_truncated_tangent_fails_identity rows show something narrower: each computes the identity under a deliberately truncated tangent and asserts the resulting error exceeds SCAN_TOLERANCE, so a pass shows that a broken tangent is caught by the comparison. It does not show that the shipped tangent agrees with the base JVP, because the row that would show that (test_tangent_matches_base_jvp) fails at both revisions.

A run of test_tangent_matches_base_jvp[edge_terms] under NOVA_TANGENT_TRUNCATION=1 (job 1307547) failed with EXIT=1 and the same primal bits differ assertion. Since that row already fails at the base revision on the same assertion, the mutation run cannot discriminate and is recorded as such. The control that does discriminate is the vertex primal-JVP row under the same mutation: the shipped head passes it, so the mutated head must fail it. That run is submitted with the gate job 1307573.

Before and after walls, and the negative control

One four-core all_debug job measured the shipped configuration (job 1307534, CPU, MAST batched over 13 sections): the baseline revision's wall is 98.0895 ms and the head's is 98.4359 ms, against a bound of 93.185 ms at 0.95 of the baseline. The head is 0.35% slower, so the benchmark's throughput assertion fails. That is the expected outcome of the arm this node chose: the near-band selection was retained unchanged after the branch-share diagnostic showed no saving, so no wall improvement was delivered to measure.

Forcing the near-band selection to evaluate every target (--force-all, job 1307535) reports before_wall_ms=97.9847 after_wall_ms=99.1203 bound_ms=93.0855 and fails the same assertion with EXIT=1. Because the unmutated arm fails that bound as well, this control shows that the assertion fires and prints its before wall; it does not discriminate the mutation from the shipped arm, and it is recorded here as such rather than as a passing gate.

A first pair of runs (jobs 1307531 and 1307532) measured the after arm from the main checkout instead of the worktree, because the launcher set no PYTHONPATH; both were discarded and repeated with PYTHONPATH=$SLURM_SUBMIT_DIR, and only the repeated runs' numbers appear above.
