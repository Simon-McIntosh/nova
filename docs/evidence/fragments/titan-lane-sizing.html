The titan rung now defaults to two cores and 24G, so eight P100 cards can hold eight jobs

The P100 node (partition titan, 98dci4-gpu-0002) carries eight cards against twenty cores. Measured on 2026-11-14, every core on the node was allocated with only four of eight cards in use, because a job taking four cores leaves half the devices idle. The launcher's titan rung defaulted to four cores, which is the sizing that produced that state, and to the shared 64G memory default.

scripts/nova_lane/run.sh now resolves core and memory defaults per rung: --dry-run (dry run) prints four cores and 64G for h200, two cores and 24G for titan, and seven cores and 64G for cpu. An explicit --cores or --mem still wins on every rung, and the --mem=0 refusal is unchanged. Both sbatch constructions — the dry-run listing and the real submission — read the per-rung value, so the printed line and the submitted line cannot disagree.

The full lines, including the payload argv, are in dryrun_all.log in the run directory named by this record's manifest. Eight cards at two cores each is sixteen cores, inside the node's twenty, so eight concurrent jobs fit where four did before.

Test arms

Both arms run tests/test_nova_lane_launcher.py in a fresh process with -rfP. The baseline arm at 76fb8b84e76eabc8000abaf772f847a2cf6d9a4f reports 14 passed, exit 0. The after arm at this change's head reports 18 passed, exit 0. Added failures: 0.

The four cases the change adds are the titan sizing and the two override paths. Run against the unmodified launcher in a scratch tree, the titan sizing cases fail — test_dry_run_titan_defaults_to_two_cores_and_24g and test_dry_run_keeps_24g_only_on_titan, both 2 failed — which is what the titan default being four cores and 64G looks like from the test's side.

The declared negative control restores rung_cores for titan to four and runs the titan-default case: 1 failed, 17 deselected, exit 1, naming test_dry_run_titan_defaults_to_two_cores_and_24g — an id the after arm passes.

What this record does not measure

No job was submitted on either lane. The submission path is exercised by the dry run and by the launcher's own fallback test with a stubbed sbatch, so the --mem and --cpus-per-task values reaching a real allocation are inferred from the constructed argv, not observed on a node.
