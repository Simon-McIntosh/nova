§1 — Goal and throughput budget

Reconstruct the full MAST L2 catalog — all 11,573 shots, every timestep — in ~1 hour on the 8×H200 node. This is nova's short-term capability goal and the design driver for the batched solver family: nova is expected to do large-scale GPU solves and labeling work as a first-class function, not as an afterthought.

Scope (owner rescope 2026-08-21): the H200 throughput work also delivers a capabilities demo on the DIII-D competition dataset — the batched pipeline run end to end on the second onboarded machine (stage L2b below) — so the throughput claim is demonstrated as machine-generic capability rather than a MAST-only artifact.

The budget, using the locked scope (all L2 shots) and a slice census to be pinned in stage L0: at an estimated 300–600 equilibrium timesteps per shot the catalog is roughly 3.5–7 M slices; one hour therefore demands ~1,000–2,000 slices/s aggregate ≈ 125–250 slices/s per GPU. Today's reference point is the ambix CPU spine at 6.8–10.6 s per slice end-to-end (spine_bench v0 heldout set) — a factor of ~104 per device. That factor is plausible precisely because the whole solve was rebuilt fixed-shape and vmap-safe: the ambix FSA GPU capability probe already ran batch-1024 flux-surface kernels in ~5 ms with ≤1.1×10−13 CPU disagreement, and nova's jitted operator/topology stack pins batched==per-slice at 10−10. The gap to close is architectural (batching the Picard loop and the IO), not numerical.

§2 — Solve architecture

Per-slice pipeline, all stages fixed-shape and batched with a leading slice axis:

  1. Seed: ReconstructMoment (centroid-order disc seed + gated quadrupole) from the sensor signature — cheap, well-conditioned, embarrassingly batchable.
  2. Solve: ReconstructProfile — the measurement-constrained free-boundary solve (profile ladder n_pressure/n_diamagnetic, soft priors incl. the harmonic annulus anchor and passive columns), Picard/Newton iterated to a fixed iteration budget with a converged mask (fixed shape — non-converged slices are masked, never branched on). The batched-Newton work explored in ambix (docs/batched-newton-accelerator.html, docs/differentiable-solve-accelerator.html) is the accelerator reference.
  3. Label: nova's JAX topology/connectivity stack (nulls, LCFS, masks, flux-surface bins) — already batched and pinned batched==per-slice.
  4. Persist: ψ grids (optionally decimated), profiles, boundary, labels, convergence diagnostics → zarr label store via nova.io, standard-name keyed.
  • Sharding: single-process jax.sharding over 8 devices (data-parallel over the slice axis) as primary; per-GPU SLURM array over shot ranges as the robust fallback. Nova currently has zero multi-device code — this plan adds it.
  • Batching unit: slices are pooled across shots per campaign (one MD version → one operator set → one compiled solve); shots differ only in input rows, so cross-shot pooling keeps batches full.
  • IO: inputs pre-staged through nova.io ingest (coil currents, sensor signals, Ip per slice — kB/slice, not the raw store) into solve-ready zarr shards; H200 node-local staging so the solve never waits on the WAN mirror.
  • Precision: fp64 baseline (H200 fp64 is strong); a mixed-precision variant is an optimisation decision taken only against measured accuracy deltas on the parity gate.

§3 — Stages

  1. L0 — census + single-slice parity. Pin the exact slice count (the denominator of the goal); jitted ReconstructMoment/ReconstructProfile match the eager path on the spine_bench heldout set to tolerance. Deliverable: the real throughput requirement and a parity gate.
  2. L1 — single-GPU batched throughput. vmap'd solve at batch 256–4096 on one H200; measure slices/s vs batch, identify the knee; profile Picard iteration count distribution (the fixed budget must cover the tail without wasting the bulk). Gate: ≥ the per-GPU target on flat-top slices.
  3. L2 — 8-GPU scaling + IO pipeline. Sharded solve + streamed input shards + async zarr writes; sustained aggregate ≥ 1,000–2,000 slices/s over a multi-campaign rehearsal (≥ 100 shots). Gate: scaling efficiency ≥ 80% of 8× and no IO starvation.
  4. L2b — DIII-D competition-dataset capability demo (owner rescope 2026-08-21). Run the batched solve end to end on the DIII-D competition corpus through the digest-pinned onboarded machine description: flux functions extracted from the labeled maps with the corpus kA·turn conductor currents (the magnetics-free forward route diiid-forward-onboarding validated), moment seed → profile solve → topology labels → labeled zarr store, on the H200. Deliverable: named shots and frames with side-by-side solved and labeled maps and their difference field, throughput and convergence receipts beside the MAST ladder numbers, and the labeled DIII-D demo store. Constraint: the demo runs the same code path as the MAST ladder — no machine-specific solver fork.
  5. L3 — full catalog run. The production run: all shots, all slices, labeled store persisted + a quality report (convergence rates, residual distributions, per-campaign breakdown) — the catalog becomes nova's labeling substrate.

Done-when (plan): L3 complete — full-catalog labeled equilibrium store produced in a wall-clock hour-scale run on the 8×H200 node, with the quality report and rerun recipe committed — and the L2b DIII-D competition-dataset demo record published with its receipts and side-by-side figures.

§4 — Compute constraints (SDCC)

  • The H200 node (98dci4-gpu-0003, partition betelgeuse) requires --reservation=gpu_0003_grpA (ReqResv=YES); the reservation holds CPUs only — all 8 H200s are requestable through it. Filling the whole server is by agreement with the group-B team; check sinfo -p betelgeuse -o "%l" before long runs.
  • The 1-hour target conveniently matches debug-queue discipline, but betelgeuse is not a debug partition — verify the time limit before the L3 run; chunk by campaign if needed (the solve is trivially resumable at shard granularity).
  • TMPDIR=/tmp on compute nodes; input shards staged node-local before the run.
  • The interim imas-codex embed server may hold one H200 while titan is drained — L3 scheduling coordinates around it (7-GPU runs are fine; the ladder numbers scale linearly).

§ Decisions

What counts as the "full MAST catalog" for the 1-hour goal?

User selection 2026-07-24: the hard target — every FAIR-MAST level-2 shot, every magnetics timestep. Sizes the batched-solver design; the training-grade subset falls out as a filter on the labeled store, not a smaller run.

Multi-GPU strategy: single-process jax.sharding over 8 devices (one compiled program, best batch pooling, new machinery for nova) vs per-GPU process array over shot ranges (zero new JAX machinery, robust, slightly worse pooling)? Recommendation: measure L1 first; take sharding only if the single-program path is clean, else the process array is a perfectly good L3 vehicle.

Output format for the labeled catalog: standard-name-keyed zarr label store (nova.io native, streams well, feeds ambix training directly) vs equilibrium IDSs per shot (IMAS-interoperable, heavier) vs both (zarr primary + IDS egress on demand via nova.io)?

Fixed-iteration-budget policy for the batched Picard/Newton loop: one global budget sized to the tail (simple, wastes bulk throughput), or a two-pass scheme (short budget for all → re-solve the non-converged residue with a long budget)? Two-pass is the likely winner if the iteration-count distribution from L1 is heavy-tailed.

Which machine fidelity is required before the equilibrium throughput ladder starts?

The catalog solve is axisymmetric. Full TF winding paths, calibrated 3-D ripple and signed 3-D diagnostics belong to a separate fidelity programme.

Proceed with catalog geometry, supported magnetic diagnostics, measured toroidal-field reference and provenance-typed nominal passive parameters. Detailed TF geometry and non-axisymmetric calibration do not gate census, parity or throughput work.

GATE TRANSFERRED: this plan's parity prerequisite moves from spine-efit-parity to efit-forward-parity. The reason is a scope correction rather than a re-planning preference. spine-efit-parity's frozen-six gate drove ReconstructProfile.least_squares_map through newton_krylov - a whitened least-squares fit to measured magnetics with a hard measured-current equality - so it inferred the flux functions rather than being given them and scored a fitted state against EFIT. Its verdict is a real result about an inverse reconstruction, and it FAILED ten of twelve metrics with converged_fraction at exactly zero, but a fit failing to converge says nothing about whether the Grad-Shafranov fixed point reproduces a reference equilibrium. Holding a catalog of forward solves on a reconstruction result is holding it on the wrong evidence. efit-forward-parity runs the demonstration that actually gates this work: ForwardProfile given a reference's own pprime/ffprime and conductor currents, free-boundary fixed point, no measurement anywhere in the path, compared field-to-field and moment-to-moment. It is itself gated behind efit-map-inversion (prove the reference is read correctly), efit-flux-decomposition (prove the external field can serve as a free-boundary condition) and equilibrium-metric-parity (prove the derived-quantity chain agrees, so an I_p or l_i disagreement is not ambiguous between a different field and a different way of measuring it). The catalog therefore stays held, on better-founded evidence and behind a shorter measured path - the four-plan ladder's critical path is 5.3 worker-hours.
