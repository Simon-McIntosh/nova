§1 — Objective

Nova's magnetic model must build the MAST machine from a proper machine-description IDS set — not from ambix's ad-hoc per-campaign geometry tables. This plan defines and authors that set: DDv4-native (DDv4 is COCOS 17), keyed to the IMAS Standard Name conventions, versioned by discrete physical-configuration shot range, and validated end-to-end by building nova operators from it and reproducing the sensor forward model the Ambix vacuum baselines already pinned. It also delivers the data maps and transformations that carry the FAIR-MAST / efm source quantities onto DDv4 semantics — the ingest side of the same contract.

This is a multi-session program — the stages in §4 are deliberately sized so no single session attempts the whole set. The dependent mast-catalog-gpu-solve plan consumes the result: Machine.build from MAST MD → biot operators → batched reconstruction of the full catalog.

§3 — Conventions: DDv4, COCOS 17, Standard Names

  • DDv4-native authoring. The MD is written once, in a pinned DDv4 version (decision below), with ids_properties/version_put carrying it; consumers open with the matching dd_version — never auto-converted.
  • COCOS 17 is the target convention (DDv4's). The source side was identified, not assumed: the catalog audit measured MAST source COCOS 3 across both forward- and reversed-field cohorts. The 3→17 transform scales ψ by 2π without a sign flip, preserves Ip and Bφ, flips q, and scales flux derivatives by 1/(2π). Every map records the source COCOS id and the exact transform applied (sign flips on ψ/Ip/B_φ/q, 2π factors), and a round-trip test pins each one.
  • FAIR-MAST's IMAS dd-path metadata is untrusted for signs. The catalog carries dd-path tags, but this was early tagging work on the FAIR-MAST side: the tags are useful as candidate path hints for the maps and must never be taken as evidence of sign convention or COCOS. Sign/COCOS resolution is done empirically on our side — ~/Code/imas-codex/imas_codex/cocos/ provides the machinery (calculator.py: Sauter & Medvedev CPC 184 (2013) Table-I parameters + COCOS determination from equilibrium quantities, Eq. 23; transforms.py: convention-to-convention transforms; loaders.py: IDS/EQDSK equilibrium loading). The audit loads sample shots, computes the implied COCOS from consistent (ψ, Ip, B_φ, q) combinations, and pins the verdict with tests.
  • Standard Names. Signal and MD quantities key to the IMAS Standard Names (ISN machinery + ISNC catalog, per the locked io-contract-home decision in nova-spine-refactor): the maps are authored against ISN's published schema, missing names are contributed to the catalog fork (as beta_normal was), and nova.io's resolver serves them. Facility-specific name maps (efm/FAIR-MAST → standard name) live with the mapping layer, not inside nova.

§4 — Stages (one session each, roughly)

  1. Inventory + COCOS audit. Enumerate every geometry/sensor quantity the ambix tables and FAIR-MAST L2 store carry; identify source COCOS and units per quantity; produce the map skeleton (source path → DDv4 path → standard name → transform). Deliverable: a research doc with the full quantity ledger + the campaign-fingerprint inventory (which campaigns need distinct MD versions).
  2. pf_active + wall + tf. Author the coil/limiter/TF IDSs for a pilot campaign; nova Machine.build compiles them through the MachineGeometryReader seam; coil-to-sensor and coil-to-grid operators reproduce the ambix geometry-table operators to tight tolerance.
  3. magnetics. Sensor set with orientations/areas + per-campaign validity; vacuum-shot forward model (coil currents → predicted sensor signals) matches the ambix vacuum-campaign pins.
  4. pf_passive. Passive element set; PassiveCircuit L matrix from the MD matches the ambix two-section flux-linkage build; calibrated-R provenance referenced.
  5. Campaign fan-out + registry. Generate MD versions for all campaigns in the catalog (automated from the stage-1 fingerprints); store per the registry decision below; document the pulse-range → MD-version keying.
  6. Ingest maps for the solve inputs. The catalog solve's per-slice inputs (coil currents, sensor signals, Rogowski Ip) mapped through nova.io with standard-name keys and COCOS transforms; round-trip validated on a pilot shot set.

Done-when (plan): all six stages landed; a MAST shot can be taken from FAIR-MAST source to a nova operator set + solve-ready input bundle using only the MD IDSs and the maps — no ambix geometry tables on the path.

§5 — Validation gates

  • Operator parity: MD-built biot operators vs ambix geometry-table operators — element-wise agreement to a stated tolerance on a pilot campaign, then per campaign.
  • Vacuum forward model: coil-only shots reproduce measured magnetics to the ambix vacuum-campaign residual levels (the strongest end-to-end test of geometry + orientation + signs).
  • IDS validity: every authored IDS passes validate() in the pinned DDv4; every map has a COCOS round-trip test.
  • Reconstruction smoke: ReconstructMoment on a handful of flat-top slices lands the boundary within the tolerance the ambix disc-read cohort established.

§ Decisions

Which DDv4 version to pin for the MD authoring (and therefore for every consumer open)? Latest stable at stage-2 time is the default recommendation; the pin is recorded in the MD registry and in the maps.

Top of the DD chain (3.22.0 -> 4.1.1) and present in the installed imas-python 2.3.0, so it is writable today without an AL upgrade — both verified. Pinning newest 4.x rather than 4.0.0 matters specifically because the pf_passive/loop/element subtree the MAST passive description depends on is DDv4 lifecycle ALPHA; the closer the pin sits to head, the less alpha churn between authoring and consumption. Changes if: a 4.2.x lands before stage 2, or a required pf_passive path changed shape between 4.1.0 and 4.1.1.

Where do the authored MD IDS files live and how are they versioned? Candidates: GHCR OCI artifacts via ORAS (matches the norma corpus pattern — immutable digests, campaign tags, CI-pullable); in-repo under a size budget (MD is small — likely <10 MB total); or a dedicated mast-md repository.

SDCC can pull it, MEASURED not assumed: ghcr.io answers from BOTH login and compute nodes (HTTP 401 unauthenticated, DNS 140.82.121.34, verified 2026-07-27), so a job can fetch the MD from inside a SLURM allocation. An earlier inference that compute nodes had no network was WRONG — the failed resolve was UV_OFFLINE=1 already set in the shell environment, and pypi.org returns 200 from a compute node. The norma corpus already proves the pattern on this machine (digest-verified ORAS pulls to ~/.local/share/norma/<tag>/, `gh auth token | oras login`, a programmatic resolver in nova.assembly.provenance.corpus to model on); the firewall constraint recorded for norma is SMB (ports 445/139, the //io-ws-ccstore1 share) and does not touch HTTPS. The deciding argument against in-repo is CHURN rather than size: five machine descriptions now, and the fingerprint still has to be extended to cover the passive structure, so the set will be regenerated more than once and immutable digests keep that out of git history. Changes if: CI runs anywhere without a GHCR token — the set is small enough (<10 MB) that in-repo wins immediately.

Campaign → MD-version keying: one MD per campaign fingerprint (the ambix geometry-signature approach carried over), or one MD per named campaign with the fingerprint as a consistency check? Determines how many MD versions the registry carries and how consumers select one from a shot number.

User directive 2026-07-30: a machine description identifies the underlying physical machine geometry and its real changes, not a filament, element, or mesh discretization applied by past codes. Canonicalize equivalent representations before comparing configurations. Diagnostic positions and sensitive-axis orientations are part of the physical identity. Configuration changes must be expressed as discrete shot ranges and a boundary is admitted only when conductor geometry, passive geometry/topology, limiter/wall geometry, TF configuration, or diagnostic placement/orientation actually changes. Raw per-shot fingerprints and alternating mesh counts are evidence to explain, not registry identities.

Where do the MAST facility maps (efm/FAIR-MAST path → standard name → COCOS transform) live? The io-contract-home decision puts facility maps with the mapping layer (codex emits facility maps against ISN's schema); the pragmatic near-term options are the imas-codex MAST map set, an ambix-side plugin table, or a maps/ tree beside the MD registry.

The io-contract-home decision already puts facility maps with the mapping layer, and the two hardest jobs both live there: standard-name resolution (10 of the 40 ledger rows need names contributed through the ISN/ISNC fork flow, which codex owns) and the COCOS transform machinery (imas_codex.cocos, which needs an e_Bp fix regardless — determine_cocos infers e_Bp from a |psi| > 0.5 Wb magnitude heuristic and returns COCOS 7 for 3,923 of 4,000 TRANSFORMED shots because median max|psi| after x2pi is 0.332 Wb; small low-field machines break it, so e_Bp must be measured or declared per source, never inferred from magnitude). Splitting the map from either would put the source of truth for a sign convention in a third place. Changes if: md-registry ends up in-repo, when a maps/ tree beside it beats a cross-repo dependency on the ingest path.

Do missing physical parameters stop machine-description progress?

Several parameters are absent from catalog geometry but can be initialized from defensible material or engineering priors and refined experimentally.

Passive resistance is seeded from nominal steel or Inconel properties and refined from MAST vacuum runs. The same loop applies to other identifiable parameters. Generated values remain explicitly provisional until held-out evidence promotes them.

Does axisymmetric equilibrium require full installed TF winding geometry?

Detailed TF paths matter for ripple and non-axisymmetric error fields, while the axisymmetric reconstruction consumes the R-Z machine, magnetic constraints and toroidal-field reference.

Full TF winding geometry is a 3-D fidelity requirement, not a prerequisite for advancing the axisymmetric equilibrium and catalog solve lanes.
