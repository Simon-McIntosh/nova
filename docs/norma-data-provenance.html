§1 — Objective and scope

The recorded coil-fit corpus is among the most valuable data nova touches: it is the measured, as-built alignment of ITER's toroidal-field coils during SSAT and in-pit assembly. Today those measurements live only as opaque .xlsx downloads on a Windows/IO share, the fits that consume them leave no durable provenance, and there is no way to prove that a fit produced last year still reproduces today. This plan designs the full system that fixes all three, and that travels with the assembly code when it extracts to the norma repository (the assembly-metrology sibling of nova; see nova-spine-refactor).

Three coupled goals:

  • Provenance. Every fit ever performed becomes an immutable run record keyed by the git commit hash of the code that produced it (plus a dirty flag), the resolved dependency lock, the content digests of every input, and the hash of the fit configuration. Given a result, you can always answer "which code, which data, which settings produced this?".
  • Persistence. The measurements are versioned in a git-safe, human-diffable canonical form at full float precision, with the bulk corpus content-addressed in an OCI registry (GHCR via ORAS — locked in nova-spine-refactor) so nothing valuable lives only in a spreadsheet on one laptop.
  • Testing. A two-tier replay suite unit-tests past fits across the complete dataset: the fast tier re-runs every recorded fit with current code and compares to its stored goldens within 1 µm; the on-demand tier reconstructs the recorded commit's environment to prove the record itself is faithful.

This plan depends on nova-spine-refactor (the §2a characterization harness and the branch restructure are its foundation) and reuses that harness's canonicalization, tolerance-class and manifest machinery rather than reinventing them.

The design introduces one transaction boundary — a transcoder that is the single place spreadsheets enter or leave the system. On ingest it reads openpyxl cell values (full float precision, never display strings) and emits the canonical form (§3); on egress it can rebuild a workbook for interchange. Everything downstream — fits, tests, training — reads only the canonical form. The transcoder is also exactly the fixture-seeder the characterization harness needs to unblock the currently-skipped sector.fit/pit.gaps lanes.

§3 — Canonical git-safe format ✓ landed 2026-07-24

✓ landed 2026-07-24 — long-format CSV locked and implemented. Original rationale (retained). The .xlsx are zip blobs: opaque to git diff, conflating measurement data with presentation, and merge-hostile. The canonical form is long/tidy text — one row per atomic measurement — so a change to a single fiducial shows as a single changed line in review. Proposed columns (validated against the real workbook in §2's followup):

  • sector, coil, phase (assembly phase / sheet), feature (fiducial or ILIS point id), axis (x/y/z or r/rphi/z), value (float64, full precision), units (mm), and the source keys idm_doc, version, private.

Hard requirements on the format, whichever encoding is chosen (see the canonical-format decision):

  • Lossless round-trip xlsx→canonical→xlsx at full float precision, proven by a round-trip test (bit-exact on the numeric cell values, never on display strings).
  • Deterministic serialization — sorted keys, fixed float formatting (repr-round-trippable), stable row order — so re-emitting an unchanged dataset yields a byte-identical file and an empty diff.
  • Content-addressable — a sha256 over the canonical bytes is the digest the run record and the ORAS registry reference.

Long-format CSV is the most diffable but verbose; Parquet is compact and exactly typed but binary (needs a CSV sibling or an ORAS-only home to stay git-friendly). The choice is a locked-later decision; the schema above is format-independent.

§4 — Provenance model and run records ✓ landed 2026-07-24

✓ landed 2026-07-24. RunRecord implemented in nova/assembly/provenance/runrecord.py exactly per this section (fit_id, code_git_sha+dirty, uv_lock_sha256, input_digests, fit_config_sha256, outputs with tolerance classes, env, operator, timestamp) with capture_environment() and a whole-document content digest; YAML round-trip via deterministic yamlio. Commits 011235eb, 5ceb2f84; 57 provenance tests green. Full record: §2–§6 landed.

Original specification (retained). Every production alignment emits an immutable run record — a small JSON document (an extension of the characterization harness's manifest entry) that is the single source of truth for "how this fit was produced":

  • fit_id — stable identifier (sector · phase · campaign · sequence).
  • code_git_sha + code_dirty — the exact commit the fit ran on, and whether the working tree was dirty. This is the commit-hash key the whole test system turns on.
  • uv_lock_sha256 — digest of the resolved uv.lock, pinning the dependency closure (numpy/scipy/scikit-learn/… whose last bits move a fit).
  • input_digests — sha256 of every canonical input consumed (the measurements, the nominal ILIS cloud), so inputs are pinned by content, not path.
  • fit_config_sha256 — digest of the declarative fit configuration (§5).
  • outputs — canonical output artifacts (positions, gaps, deviations, ILIS planes) with their per-quantity tolerance class and sha256, stored in ORAS by digest.
  • env — single-thread BLAS flag + key package versions; operator, timestamp.

Records are append-only and content-addressed: a fit is replayable by construction — restore the lock, check out the sha, pull the input digests, re-run, compare within tolerance. The records live beside the goldens and are pushed to the registry; the small, stable reference set is committed in-repo so history is legible without the registry.

§7 — Testing past fits (two-tier, commit-hash keyed) ✓ landed 2026-07-24 (both tiers)

✓ Both tiers landed 2026-07-24. Tier 1 (commit 36e1c5e8): registry-wide current-code regression, pilot green with ~1e-12 headroom vs the 1 µm gate. Tier 2 (commit 64780f2e): five-stage historical replay (sha-worktree, verified lock, frozen uv env rebuild, subprocess re-run, shared compare) with visible per-stage degradation, opt-in via NOVA_TIER2_REPLAY=1 — full pass end-to-end (3 passed, 31 s) against the clean-tree pilot record recaptured at 2e575939 (e46be651). Fit-parameter history manifest landed alongside (a23ef791): 85 workbooks, 265 fit sheets, 512 fits with 10 mined parameter epochs. Full records: §7–§8 landed, §6/§7 completion wave.

Original specification (retained). The registry enumerates every fit ever recorded — each an immutable run record (§4). The suite iterates the whole registry; "complete dataset" means the full enumeration, with a representative subset in the fast lane and the full set in the nightly / extraction gate.

  • Tier 1 — current-code regression (fast, CI default). For each record, re-run the fit with current code, the record's pinned inputs (pulled from ORAS by digest) and its fit-config, and compare outputs to the record's canonical goldens at the tolerance table (1 µm on mm; per-quantity elsewhere). Green ⇒ current code reproduces every historical alignment within measurement noise. The stored code_git_sha documents which code produced the original; a divergence is triaged by diffing HEAD against that sha — the commit hash makes the regression actionable, not just red.
  • Tier 2 — historical replay (on-demand, audit / extraction gate). Reconstruct the recorded environment: git worktree add at code_git_sha, rebuild from the recorded uv.lock, re-run, and confirm the record reproduces. This proves the record itself is faithful and that the sha is meaningful. It is expensive (old wheels, old interpreters) and runs selectively.

Honesty about feasibility ("if possible"). Very old commits may not rebuild — a wheel or interpreter may be gone. Tier 2 therefore degrades gracefully and visibly: a record that passes Tier 1 but whose historical environment cannot be reconstructed is reported as "reproduced by current code; historical env unreconstructable", logged in the run record, never silently skipped. The invariant we can always hold is Tier 1: current code reproduces the stored goldens within 1 µm. All of this reuses the §2a harness's canonicalization, tolerance and manifest code — a run record is a manifest entry plus {git-sha, uv.lock hash, fit-config hash, operator}.

§9 — Branch and repository model (and the planning snag)

Current branch setup (after nova-spine-refactor §2, on Simon-McIntosh/nova):

  • main — the live 1.x line and the default branch. The assembly tree (nova/assembly, nova/structural) lives here and assembly work continues here uninterrupted. Carries the reckon plans.
  • legacy/v1 + tag v1-assembly-baseline — the frozen goldens-green baseline, branch-protected (no force-push, no deletion).
  • develop — the 2.0 physics-spine line, cut from the baseline; the assembly tree is deleted here.

Which branch the norma work runs on: main. The assembly code and the recorded corpus live on main; main is the live line where assembly work continues; and develop is actively deleting the assembly tree, so it is the wrong home. All the work in this plan — transcoder, canonical format, run records, fit-config files, the replay suite — is authored and committed on main until norma extracts to its own repository (by git filter-repo from main/legacy/v1, carrying full history), after which it continues on norma's own main and this plan is re-homed there via reckon-sync.

The planning snag, and how we avoid it. The reckon docs-server serves the working-tree plan HTML of the registered checkout as canonical. If that checkout switches between main and develop, the served plan state flips — and an uncommitted plan edit on the wrong branch silently corrupts canonical state. The rule that removes the hazard:

  • Plans live on main only. All plan authoring and updates happen while the registered checkout is on main. Commit and push plan edits in the same session (a binding reckon rule) so live state never depends on an un-pushed file.
  • Do develop (2.0 core) code work in a separate git worktree (git worktree add ../nova-develop develop) — never by switching the reckon checkout's branch. Code lands on develop in its own tree; plans stay on main.
  • Norma work needs no switching at all: it and its plan both live on main, in one tree. That is the whole reason the norma work runs on main.

§ Decisions

Canonical git-safe encoding for the measurement dataset. Long-format CSV/TSV (maximally diffable, verbose, needs disciplined float formatting) — recommended for the in-repo reference sets; Parquet + a CSV sibling (compact, exactly typed, but binary — the CSV carries the diff); or JSON-per-fit (self-describing, nested, noisier diffs).

Locked 2026-07-24 at implementation: long-format CSV, one row per atomic value, repr-round-trip float formatting, LF/UTF-8/minimal quoting; YAML sidecar per unit for provenance and egress layout. Byte-identical round-trip and determinism proven by the transcoder test suite; sha256 over the CSV bytes is the content address the run records and registry reference.

What lives in-repo vs ORAS-only. Reference fixtures + goldens in-repo and the full corpus + historical outputs in ORAS by digest (recommended); everything in ORAS with only digests in-repo; or everything in-repo (rejected earlier as repo-bloating, but listed for completeness).

Locked 2026-07-24 as executed: 7 canonical reference units (latest public per sector + the private _#7 v9_4 fit fixture, 7.9 MB diffable text) committed in-repo; the full 85-unit canonical corpus + the verified source snapshot live outside the repo and go to GHCR by digest via the staged ORAS driver. Everything referenced by sha256 so items can move homes without breaking records.

Past-fit testing strategy. Two-tier — fast current-code regression against goldens plus on-demand sha-worktree historical replay (recommended); current-code regression only (cheaper, does not prove the record's own env); or full sha-checkout replay for every record (most rigorous, often infeasible for old envs).

Locked 2026-07-24: two-tier as specified in §7 — Tier 1 current-code regression over the run-record registry at the tolerance table (CI default), Tier 2 sha-worktree historical replay on demand with visible degradation when an old environment cannot be rebuilt. Tier-1 foundation + pilot records are the in-flight §7/§8 work; Tier 2 is a queued followup.

Declarative fit-configuration file format (schema-validated; hash enters the run record). YAML (readable, comments, ubiquitous) or TOML (stricter typing, no ambiguity)?

User direction 2026-07-24 ("use yaml for manifests"): YAML for all manifests, fit configurations, run records and sidecars, emitted exclusively through the deterministic canonical-YAML io (sorted keys, block style, repr-round-trippable floats) so every YAML artifact is byte-stable and hashable.
