§1 — nova-cocos as a workspace member

nova/io/cocos.py is 224 lines and imports only dataclasses, math and typing, yet the only way to get it today is to install nova, whose floor is Python 3.14 and whose dependencies include h5py, netCDF4, pyarrow, xarray and zarr. imas-ambix's facility plan (jt60sa-facility-mint) needs these factors in a slim engine, imas-alambic, that has to install into the JT-60SA analysis server's Python 3.12. That plan does not allow a second copy of the factor table, so the table has to become installable without the rest of nova.

This section makes nova a uv workspace whose first member is packages/nova-cocos/: distribution nova-cocos, import package nova_cocos, requires-python = ">=3.12", no runtime dependencies, built with hatchling like the root. Its version comes from the same owner as the root's: dynamic = ["version"] with hatch-vcs reading this repository's git tags ([tool.hatch.version] source = "vcs" with the root's version_scheme, and raw-options pointing at the repository root). The member never carries a static version, so the workspace has one version number and it cannot drift. The contents of nova/io/cocos.py move into nova_cocos unchanged in behaviour. Every public name (CONVENTION_DIGITS, the transformation constants, TRANSFORMATIONS, ConventionError, Convention, convention, identify_convention, conventions, ConventionTransform, convention_transform, transform_factor) is importable from nova_cocos. nova-stella declares nova-cocos as a dependency with a workspace source. nova's own importers (nova/imas/mast_solve_inputs.py, nova/equilibrium/topology.py, nova/io/sourcemap.py, nova/equilibrium/contour_tree.py and the five test modules) switch to nova_cocos. nova/io/cocos.py stays only as a re-export of nova_cocos's public names, because imas-ambix imports nova.io.cocos in four places through an editable path dependency, and removing the module now would break that checkout. §2 removes it.

The worker may not edit imas-ambix. If imas-ambix no longer resolves against the changed nova, the node stops and reports blocked, naming the resolver error, and does not land.

Done-when: uv build --package nova-cocos writes a pure-Python wheel whose METADATA reads Requires-Python: >=3.12, has no Requires-Dist, and carries the same Version as a root build at the same commit. That wheel installs into a clean uv venv --python 3.12 environment, where python -c "import nova_cocos; print(nova_cocos.transform_factor('psi_like', source=11, target=17))" prints the same value nova prints today. nova.io.cocos.transform_factor is nova_cocos.transform_factor holds. nova's COCOS-covering tests (tests/test_io_cocos.py, tests/test_transport_cocos.py, tests/test_contour_tree_conventions.py, tests/test_io_sourcemap.py, tests/test_mast_solve_inputs.py) add no failures against the stated base. imas-ambix still resolves against this worktree's nova. imas-ambix's own checkout resolves the main nova, not this worktree, so the check copies imas-ambix's pyproject.toml and uv.lock into a scratch directory, points the nova-stella source at this worktree, makes its other relative sources absolute, and runs uv lock --dry-run there, which exits 0.

§2 — Retire the nova.io.cocos re-export

Once imas-ambix imports nova_cocos directly (jt60sa-facility-mint §2), nothing imports nova.io.cocos, and the re-export is removed so the table has one import path. Done-when: grep -rn 'nova.io.cocos' nova tests in nova and grep -rn 'nova.io.cocos' imas_ambix tests packages in imas-ambix both return nothing; nova/io/cocos.py is gone; the §1 COCOS tests add no failures.
