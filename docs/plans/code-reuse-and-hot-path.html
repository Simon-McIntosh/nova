§0 — Why this plan exists

The lead consolidated nova on 2026-11-21 into four focused sprints and asked on 2026-11-22 for a fifth on reuse, because the tree carries many thousands of lines that duplicate one another and the route a production solve takes is not readable from the code. Measured on main at 2026-11-22:

treePython linesfiles
nova/208kabout 520
benchmarks/291k378
scripts/249k—
tests/202k—

Since 2026-08-01, nova/ gained 175k lines and lost 36k. Of nova/equilibrium's 66k lines, the forward route is spread across fixed_point.py (5.9k), forward_operator.py (4.2k), topology.py (4.1k), reduced_newton.py (3.6k), forward.py (3.3k) and support_read.py (3.0k), and no document says which of them a production solve executes. The 2026-11-13 H200 profile counted about 12,500 kernel launches per slice; a route nobody can name is a route nobody can shorten.

Ownership. This plan deletes and records; it does not rewrite the hot path. Sprint S28 owns the forward solve and is changing those files now, so §5 hands it a register of duplicates and S28 decides and lands each collapse. Sprint S30 owns nova/imas, which is out of scope here. Code that a plan in held sprint S32 owns is kept: the lead ruled on 2026-11-21 that held work is parked, never discarded.

§1 — The measured hot path

A stored record names every module and function the two production routes execute, measured rather than read:

  • the public forward solve, under the H200 slice-profile fixture that S28 re-runs, executed here on CPU on all_debug;
  • the inverse fit inside the equilibrium iteration, under the MAST known-state recovery test.

Done when:

  1. The record lists, for every module under nova/, the lines executed by each route against its total, and the union; a machine-readable copy sits beside the evidence fragment docs/evidence/fragments/code-reuse-and-hot-path/hot-path-map.html.
  2. The public solve entry, which both routes must reach, reads nonzero executed lines on each.
  3. The record states the revision measured, and the measurement ran on all_debug as one job.

Negative control: a module imported by nothing on either route reads zero executed lines in the same measurement, so a map that marks everything reached fails.

§2 — Census of benchmarks and scripts

Every Python file under benchmarks/ and scripts/ receives one verdict, stored in one record:

  • keep: imported by kept code or tests, run by a live gate, lane or test, or owned by a plan in S28–S32;
  • delete: reached by none of those, whether uncited or cited only by an evidence record;
  • merge: one of several drivers doing the same measurement, naming the driver it folds into.

Done when:

  1. The census covers every file, and the sum of lines per verdict equals the measured total of both trees.
  2. Each delete verdict names every evidence record that cites the file and the revision that record ran at, and that revision resolves (git cat-file -e on that revision joined to the file's path exits zero).
  3. Each merge verdict names the driver it folds into, and that driver is itself classified keep.

Negative control: a driver a live test imports, forced to a delete verdict, is refused by the census and named.

§3 — Delete and merge benchmarks and scripts

Apply the §2 verdicts in batches small enough to review, each batch one node. Done when, for each batch:

  1. Every deleted path is absent at the head, and no file at the head imports or names it (grep every deleted path, including tests and AGENTS.md).
  2. The suite delta against the batch base adds no failures, run on all_debug.
  3. The batch record states the lines removed, and the running total across batches.

Negative control: a kept file that still names one deleted path makes the absence check in (1) fail and report that path.

§4 — Delete unreached library modules

Modules under nova/ that §1 shows unreached by either route, outside nova/imas, not imported by kept tests, and not owned by a live or held plan, are deleted. Done when:

  1. Each deleted module was unreached in §1 and no kept file imports it; a module a live run's worktree imports is held back and named.
  2. The suite delta adds no failures, on all_debug.
  3. The record states lines removed per package.

Negative control: a module §1 shows reached, offered for deletion, is refused by the check in (1) and named.

§5 — Register of duplicates on the hot path

A record, not a code change. It lists every place where two or more implementations on or beside the §1 route compute the same quantity (a read, a factorisation, a topology query, an operator assembly). Done when:

  1. Each entry names the implementations, which one each route executes per §1, and their agreement on a stated input within a stated tolerance, or the measured disagreement.
  2. Each entry proposes the one to keep and the lines removable, and S28's coordinator has answered it: accepted for an S28 node, or declined with a reason.

Negative control: one entry's comparison rerun with a deliberately perturbed input to one implementation reports a disagreement beyond the stated tolerance.

§6 — The hot path, written down

nova/equilibrium/AGENTS.md names the one public forward route and the inverse route, module by module, as measured after the §5 collapses S28 accepted have landed. Done when:

  1. The section lists the modules each route executes and matches a fresh §1 measurement at the head.
  2. Every module the section names exists at the head.

Negative control: adding to the section one module the routes do not execute makes the comparison in (1) fail and name it.

§ Decisions

May a benchmark or script that produced cited evidence be deleted from main?

Git keeps the driver at the revision the evidence ran at, so nothing is lost; a driver a live gate or test still runs is kept.

After §6, should a test fail when the public forward solve executes a module outside the documented route?

§6 writes the measured route into nova/equilibrium/AGENTS.md with no enforcing test; S28 is still reshaping those files, and a guard would make every collapse edit the document in the same commit.
