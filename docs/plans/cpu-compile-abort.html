Why this plan exists

Four independent measurements have died the same way while compiling on a CPU debug partition, and between them they hold up three plans. The process raises LLVM compilation error: Cannot allocate memory many times over, then allocateMappedMemory failed with error: Cannot allocate memory, then Failed to satisfy suballocation request for a few hundred bytes, and finally LLVM ERROR: Unable to allocate section memory! before aborting with SIGABRT and exit 134. Nothing in the payload names a cause a reader can act on, and the scheduler reports the step as ended rather than as failed.

Memory size is already excluded. Tripling the request from 64 G to 180 G moved the abort by nineteen seconds, and the scheduler recorded peak resident memory of 28.7 and 30.1 GB against that raised ceiling. A run cannot be short of memory and fail to place 129 bytes while using a sixth of what it asked for. Whatever is exhausted is not the allocation.

There is no GPU lane to escape to. The quality-of-service that governs the shared H200 caps this account at four cards and 650 GB, and the local model serve holds all four cards and 600 GB of that with no time limit. A correctly shaped single-card job pends indefinitely. So for as long as the lane that runs the fleet is up, every heavy measurement has to compile on CPU, and this abort is what stops it.

§1 — Name what is exhausted, before proposing anything

The failure message says a mapped section could not be placed, which is consistent with the process running out of memory mappings rather than memory. Both the login node and the debug nodes carry the kernel default of 65,530 mappings per process, and a compilation that emits many small sections can reach it; overcommit is heuristic rather than strict, so a refusal at a few hundred bytes is not a size refusal. That is a hypothesis and it has never been measured. It was offered by one worker and correctly labelled untested, and this section exists so it stops being repeated as if it were a finding.

Done when. One debug allocation runs the smallest driver that aborts, with a sampler recording the process mapping count from its own /proc entry at a fixed interval until the abort, and the record states the peak count beside the limit, the count in the last sample before the abort, and the resident memory at the same instants. The verdict is one sentence: the mapping count did or did not reach the limit. If it did not, the record names what else the sampler saw move, and the hypothesis is retired in writing rather than left in circulation.

§2 — Take the cheapest remedy the measurement admits

The remedies differ by cause and they are not equally cheap, so the choice is a decision below rather than a foregone conclusion. If mappings are exhausted, the kernel limit is not ours to raise on a shared node, so the useful levers are on our side of it: fewer sections to place, or a compile that does not happen at all. The persistent compilation cache is the second of those and it already exists, which makes a cache miss the most likely reason a given driver compiles in the first place. The program-size work on another plan is the first, and it is slower.

Done when. The chosen remedy is applied to the smallest failing driver and that driver completes in one debug allocation, with the before and after recorded as the same measurement rather than as two anecdotes. Where the remedy is a cache warm, the record states which program keys were missing and how they came to be missing, because a cache that silently does not cover the lane's own programs is the defect rather than the workaround.

§3 — Say it is a compile abort, at the moment it happens

Every one of the four jobs reported the same way to whoever read it next: a worker that stopped, with an empty or truncated artifact and a scheduler step that looks ended rather than failed. Two coordinators attributed it to the allocation and raised the memory request, which is the wrong remedy and cost two more allocations to disprove. The lane already has a guard that reads its compilation cache and prints a contract; it is the right place to recognise this.

Done when. A run whose payload aborts with the section-memory signature is named as a compile abort in its own log line, distinct from a failed test and from an allocation that ran out of memory, and the line says that raising the memory request does not address it. A committed case feeds the guard a captured log carrying the signature and asserts the classification, and a second feeds it an ordinary out-of-memory kill and asserts the two are not conflated.

§ Decisions

Which remedy does the fleet take for a driver that aborts in compilation on CPU?

Deliberately left open until §1 reports, because the remedies are not equally cheap and the measurement chooses between them. A cache warm is hours and changes no code; reducing the emitted program is the bucket-floor work on the millisecond plan and is measured in days; waiting for the GPU lane means stopping the local serve, which is the engine the whole fleet runs on. If §1 finds the mapping limit is not reached, none of these is the answer and the section is re-opened rather than a remedy being chosen anyway.

Lead ruling 2026-09-20, in two steps that are both taken. The root remedy is to reduce the emitted program: the solve compiles to 400 to 900 MB because it is unrolled where it should loop, and the lead's design ruling is stronger than a scan, that these processes are never to loop at all and are to be designed as efficient maps. That is forward-solver-route-integrity section 2, moved to the front of its plan and put on the strongest lane. Until it lands, the interim step is the one the abort node found: run each certificate row in its own process so no process loads more than it can map, which stays under the cap without touching the solver. Warming the cache is not a remedy, because a hit loads the same oversized program; reclaiming a card sidesteps the mapping cap without touching the size.

The measurement changes what the remedy choice is about, so the options above should be read against it. The binding quantity is not the total mapping count but the size of one program load, between 16,789 and 17,620 mappings. Against a cap of 65,530 that is room for three loads and no more, whatever else the process does. The certificate asks for four.

Two consequences for the options. Warming the cache is only a remedy if a cache hit loads a program with materially fewer mappings than a compile does, and nobody has measured that; the mappings come from the section allocator, so a hit may well cost nearly the same and the option would then be no remedy at all. Reducing the emitted program acts directly on the step and is the bucket-floor work already on the millisecond plan. There is also a third shape the original options missed, and it is the cheapest thing to try: the second run completed four loads because it returned sixteen thousand mappings before its fourth, so releasing a program between rows, or running each row in its own process, stays under the cap without changing the program at all. That is worth measuring before choosing, because it needs no new machinery.
