CPU solve viability

Lead judgment 2026-09-01: the CPU's inability to finish one shot-pair solve in three hours reads as a bug, not a performance gap — the JAX-traced program's numpy shape should remain viable on CPU. Deliberately backlog: not scheduled to a sprint, recorded here so the anomaly and its freshest evidence survive until it is worth chasing.

§1 — The symptom, with its evidence frozen

SLURM job 1260726 (rigel, 16 CPUs, 64 GiB, generate_topology_visuals.py --cache-only --regenerate-mast-shot 22086) ran to its 3 h TIMEOUT still inside the first stage, before MAST_STATES_READY — two Newton–Krylov solves (the dual-branch portfolio plus the margin-graded mixed arm) for MAST 22086/43. Three anchors: (a) utilisation — at 1h35 wall the batch step had accumulated 2h28 CPU, about 1.5 of 16 allocated cores, so the program was not using the machine; (b) history — the same producer completed the committed seventeen-row campaign at roughly a day of lane time (~25–50 min/arm), so a >3 h single pair is a regression against its own record, not a constant; (c) the H200 reference — width-32 batch solves complete in ~37.5 s and the trip-quantum receipt (docs/figures/solver-trip-orchestration/trip-quantum.json) shows the per-trip cost is compiled mask-reconciliation and re-linearization compute, which XLA-CPU should execute at a sane ratio to the GPU, not >300×.

§2 — Hypothesis census

Ranked by prior evidence, to be measured not argued: (1) telemetry callbacks serialize the CPU loop — the solve gained per-trip telemetry after the committed bank's revision, and its jax.debug.callbacks (the same ones that crashed the GPU-only launch by demanding a local CPU device) force a host synchronization per invocation inside the trip loop; on CPU that turns a compiled loop into a host round-trip per trip per member. (2) Scan dispatch overhead on CPU — the banked 7.6 µs/iteration H200 scan latency has a much larger CPU counterpart, multiplied across GMRES inner scans. (3) Thread configuration — XLA-CPU intra-op threading may be pinned to one or two threads by environment or by the launch recipe, consistent with the 1.5-core reading. (4) A float64 CPU kernel pathology in one of the trip sub-stages. Hypothesis (1) is cheaply separable: the telemetry is flag-gated at the call site, so one CPU arm with telemetry off against one with it on is the discriminating pair.

§3 — The measurement

One bounded CPU profiling arm on a compute node: a single 22086/43 diverted-branch solve with (i) telemetry on vs off, (ii) XLA-CPU thread count swept over {1, 8, 16}, (iii) a callback census (count × mean host time) from the profiler trace, and (iv) the per-trip wall time compared against the H200 trip quantum to state the honest CPU/GPU ratio for the same compiled stages. Done-when: a receipt names the dominant CPU cost with its measured share, states whether the pre-telemetry CPU cost is recovered with telemetry off, and either closes the anomaly as understood-and-accepted or hands a one-line fix target to a followup. The falsifier for hypothesis (1): telemetry-off fails to recover at least half the gap.

§ Decisions

What is the default compute pattern for Nova forward solves and their kernel, carrier and compilation caches?

The paired per-trip forensics on solver-convergence-regression (commit 4e0d9588) showed CPU and GPU states agreeing inside float64 reduction-order noise at every staged sub-stage of the 22086/43 pure solve, so a CPU leg is no longer needed as a numerical cross-check of the H200. Meanwhile two CPU pathologies cost hours today: the 3 h non-finish of job 1260726 recorded in this plan, and a 47-minute single-core cold response build inside the EFIT reproduction gate (job 1260961) that never reached its first solve.

Lead decision 2026-09-01: with the CPU/GPU comparison exonerated, the default pattern for every forward-solve lane is to build once on the H200 (machine geometry, Biot response carriers, topology operands, the persistent XLA compilation cache) and reuse those caches everywhere afterwards; no lane cold-builds a response or recompiles when a persisted artifact exists, and CPU legs are not run for cross-backend validation. The CPU viability question in this plan remains a bug to fix (a traced program that should run on CPU no longer does), not a validation requirement.

Fresh evidence from the regression forensics (docs/figures/solver-convergence-regression/backend-divergence.json): at revision a4bec44f (30 Aug) the 22086/43 pure arm solved on CPU in 38 minutes on a rigel node with 16 CPUs and JAX_PLATFORMS=cpu (job 1260944, COMPLETED 0:0), i.e. within the historical 25-50 min/arm envelope, with the per-trip telemetry callbacks compiled in. So the >3 h pathology of job 1260726 is either HEAD-side (commits after a4bec44f) or specific to the generate_topology_visuals producer (dual-branch portfolio plus mixed arm), not intrinsic to the telemetry or to the traced program at a4bec44f. That narrows the §2 census: hypothesis (1) telemetry callbacks is weakened on CPU too (not only on GPU), and a HEAD-versus-a4bec44f CPU pair through benchmarks/backend_divergence_forensics.py is the cheapest discriminator, ahead of the thread sweep. A second, distinct CPU issue surfaced today in the EFIT reproduction gate: a cold single-threaded Biot response build (coils plus 103 passive loops to the native grid) ran 47 minutes on one core on the H200 node without reaching a solve, while the banked parity runs load the same response from a persisted carrier in 5 ms. That one is a cache-reuse discipline failure, now covered by the locked h200-build-cache-reuse-default decision, not a solver bug.
