§1 — The measured basis, and what the cache already solved

Owner commission 2026-08-20. A cold design-matrix build costs 1,214 s on the coarse 566-cell fixture and 2,952 s on the fine 1,069-cell fixture on CPU under the exact-kernel defaults (+5.9%/+5.2% over the retired hybrid — the one-time price of Urankar-exact-everywhere). The semantic fixture cache already removed this cost from routine work: warm loads read 0.27 s and 0.82 s, bitwise. So this plan is not about routine solves — it is about the consumers that generate new configurations, where every configuration pays a cold build.

The arithmetic is device-shaped. The heavy stages evaluate elementwise fp64 special functions — Bulirsch cel with bounded iteration counts, the graded arsinh residual chains, and the shared ninth-order harmonic channel — over roughly 10⁷ source–target pairs across nine kernel blocks with moment companions. That is embarrassingly parallel work with no data-dependent shapes once cel runs at a fixed iteration count. On H200-class fp64 throughput the kernel stages should compress from tens of minutes to the seconds-to-tens-of-seconds class; the host residue (clip topology, carrier assembly) is small. The production kernels are today deliberately host NumPy — the forward-AD route through the flux antiderivatives was measured out at 12.2 GiB per target and every JAX import was removed from that API — but that measurement convicted differentiation through the antiderivative composition, not plain evaluation; plain evaluation is the port target and gradients are a separately gated follow-on (§5).

Hardware and access are already established: the H200 node (98dci4-gpu-0003, partition betelgeuse) requires --reservation=gpu_0003_grpA, which reserves host CPUs 15–29 and 47–61 and makes all eight GPUs requestable. Running the existing CPU build on those host cores buys only modest parallelism and spends the reservation's scarce resource; the value is in the device port, not the node's CPUs.

§3 — Design constraints

  • One code path, two devices. The port is a single-source JAX implementation of the kernel evaluation that runs on CPU and GPU by runtime placement — never a parallel device kernel family beside the NumPy one, per the standing no-wrappers/no-parallel-modules discipline. The NumPy implementation is replaced where it lives once the port passes its gates; until then it is the verification reference.
  • fp64 everywhere, fixed shapes, fixed iteration counts. cel and the residual chains run at pre-measured bounded iteration counts so the evaluation traces once; no data-dependent control flow reaches the device.
  • Compute provenance in cache identity. A device build is not a bitwise CPU build — the banked cross-environment lesson (a login-node GPU versus a CPU compute node is two code generators) is binding. The semantic cache key gains a compute-provenance field, verification pins compare per provenance, and no cross-device artifact ever masquerades as its sibling.
  • Numerical parity across devices (owner ruling 2026-08-21, superseding the drafted tolerance-based form). The GPU-built matrices must be close to byte-identical to the CPU build: element-wise agreement within a small ULP bound everywhere, byte-identical wherever the path is arithmetic-only, with the prototype measuring and reporting the full ULP distribution and byte-identical fraction (device transcendental intrinsics differ in last ulps, so the measured distribution is what the owner reviews at go/no-go). Each device additionally re-runs the Richardson pin set; the compute-provenance cache field stays until byte-identity is proven.
  • Memory by construction. Whole-pair-array evaluation of ~10⁷ pairs × nine blocks in fp64 sits comfortably inside the H200's HBM; if a configuration outgrows it, the evaluation chunks at fixed shape rather than falling back.

§4 — Work items

  1. Consume the build profile. Take the stage decomposition from the recovery ladder's profiled build benchmark and rank the port targets by measured share; no porting starts against unprofiled stages.
  2. One-block prototype on the H200. Port the flux G₀ block alone: correctness against the host block at the stated tolerance on the coarse fixture, and measured device throughput. This is the go/no-go gate — the projected full-build time and the CPU-lane check decide whether the full port proceeds (decision port-go-threshold below).
  3. Full nine-block port with companions, replacing the NumPy evaluation in place, with the fixed-iteration cel and residual chains pinned per device and the complete suite green on the CPU lane.
  4. Cache provenance integration: the compute-provenance key field, per- provenance verification, and a cold H200 build of both recovery fixtures published to the shared store beside their CPU siblings.
  5. Geometry-gradient feasibility, re-measured. jacfwd through the ported evaluation (plain kernels, batched targets) with peak memory per target measured against the banked 12.2 GiB AD failure — a measurement node, not a commitment; its number decides whether the inversion consumer gets its differentiable build, and that adoption belongs to the coil-geometry-inversion plan.

§5 — Acceptance gates

  • Device blocks reproduce host blocks within the stated tolerance on both recovery fixtures, and the Richardson pin set passes per device.
  • Cold device build wall time measured on the H200 for both fixtures, with the profiled stage decomposition attached — the target class is minutes, and the measured number is the deliverable, not a pass/fail line invented in advance.
  • The CPU lane does not regress beyond a pre-registered bound when the single-source implementation replaces NumPy — measured on the same staged-snapshot protocol the exact-kernel benchmark banked.
  • Cache provenance proves no cross-device contamination: a CPU consumer never warm-loads a device artifact or vice versa, pinned by test.
  • The gradient feasibility number (peak memory and wall time per target for jacfwd through one block) is banked with its verdict stated in mechanism terms.

§ Decisions

Which substrate carries the device kernel evaluation? Recommendation: single-source JAX replacing the NumPy evaluation in place — one code path serving CPU and GPU by runtime placement — because a CuPy or hand-CUDA fork would create the parallel kernel family the no-wrappers discipline forbids, and JAX is already the solve-side substrate so the build inherits jit/vmap and the future gradient path for free.

Owner ruling 2026-08-21: single-source JAX replacing the NumPy evaluation in place - one code path serving CPU and GPU by runtime placement, per the no-parallel-modules discipline, inheriting jit/vmap and the future gradient path.

What prototype result authorises the full port? Recommendation: the one-block H200 prototype must project a full nine-block fine-fixture build under two minutes AND the single-source CPU evaluation of that block must hold within 1.5× of the NumPy stage time — otherwise the port is declined on measurement and the plan closes with the prototype banked, because the cache already covers every consumer except per-gradient-step rebuilds.

Owner ruling 2026-08-21, revising the drafted time-parity form: the go criterion is a projected full fine-fixture build under two minutes AND numerical parity of the built matrices across devices - the GPU-built matrices must be close to byte-identical to the CPU build. Encoded strictly: element-wise agreement within a small ULP bound everywhere, byte-identical wherever the path is arithmetic-only, with the prototype measuring and reporting the full ULP distribution and byte-identical fraction (device transcendental intrinsics differ in last ulps, so the measured distribution is the deliverable the owner reviews at go/no-go). CPU-lane build time additionally must not regress materially, reported beside the parity numbers rather than gating alone.

Does this plan deliver geometry gradients, or only measure their feasibility? Recommendation: measure only — bank the jacfwd memory and time per target on the ported blocks and hand the adoption decision to coil-geometry-inversion, which owns the consumer — because the banked 12.2 GiB failure was measured on a different composition and the port changes the arithmetic enough that commitment before measurement would repeat the original mistake in reverse.

Owner ruling 2026-08-21: this plan measures jacfwd memory and time per target on the ported blocks and hands adoption to coil-geometry-inversion, which owns the consumer; commitment before measurement would repeat the original AD mistake in reverse.
