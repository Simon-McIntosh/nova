§1 — The metric layer is testable on its own, and has never been tested

Given one flux map, two codes should compute the same safety factor, the same volumes and the same flux-surface averages. That comparison isolates the derived-quantity chain completely: no solver runs, no sources are prescribed, no boundary condition is imposed. Both answers exist for the same input — nova computes its record from the stored map, EFIT's own values sit beside it in the same file — so every disagreement is attributable to one code's post-processing rather than to a difference in equilibrium.

That property is what makes this rung worth its own plan rather than a section of the forward demonstration. efit-forward-parity compares I_p, β_p and l_i between a solved map and a reference map — but those are metrics, so a disagreement there has two possible causes and no way to separate them: the solve produced a different field, or the two codes measure the same field differently. Validating the metric layer first collapses that ambiguity, which is why this plan blocks the forward one.

Nova already computes most of this, which sets the shape of the work. nova/equilibrium/flux_surface_geometry.py carries a FluxSurfaceGeometry record read from one converged flux map, landed at b0af2d23 with 13 columns measured 5–130× inside pre-registered tolerances:

GroupNova's record carries
coordinatespsi_norm, poloidal_flux, toroidal_flux, rho_tor, rho_tor_norm
volumes and areasvolume, area, volume_derivative, volume_flux_derivative
field and windingfield_function, safety_factor
flux-surface averagesinverse_square_radius, gradient_rho, gradient_rho_squared, gradient_rho_squared_over_radius_squared
scalarsboundary_rho_tor, vacuum_field, reference_radius, axis_flux, boundary_flux, magnetic_axis

So this is mostly a comparison, with implementation confined to whatever the reference computes and nova does not. That balance is worth stating up front because it is the opposite of the usual assumption: the risk here is not missing machinery, it is unexamined agreement.

§5 — The transport consumer, which is why this is a capability

This set is the geometry input of the transport forward solve, not only a validation artifact. flux-function-forward-equilibrium §5 already declares the flux-surface-averaged geometry record — V′, the ⟨1/R²⟩ and diffusion-coefficient metrics, F and q on the toroidal-flux coordinate — a public output contract of ForwardProfile, consumed by flux-function-forward-transport and supplied at both interval endpoints so the moving-grid term is correct.

So validating these columns against an independent code, on real machine data rather than manufactured fixtures, is what lets the transport work stand on them — and it is what makes the decomposition and metric routines reusable for training one-dimensional transport equations in the competition entry, where the geometry has to be derived from stored equilibria rather than from nova's own solves. A metric validated only against nova's own analytic fixtures is validated against nova's own conventions; this rung is the first time an outside code checks them.

§ Decisions

What tolerance does a paired metric have to meet? The existing record's columns were landed 5–130× inside pre-registered analytic tolerances, but a cross-code comparison on real data has no such basis and the reference is not ground truth.
