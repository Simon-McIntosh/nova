§1 — Why, and what already exists

ForwardProfile is validated today against one reference (DINA 135011/7, read live from a workstation imasdb) plus analytic fixtures. That proves the solve; it does not defend it: one machine model, one producing code, one time slice, and a data source that exists only on hosts with that imasdb. The imas-efit validator pipeline already curates exactly what a defensible lane needs — independent equilibria from non-EFIT++ codes, bundled with the machine inputs that produced them — in an OCI store at ghcr.io/iterorganization/efitpp-test-data (current tag v0.0.14, 96 layers, 285.9 MB, layer identity via the org.opencontainers.image.title annotation, source of truth tests/data-manifest.json, per-dataset dd_version authoritative). Its validation section carries 23 equilibrium-only references whose code key separates simulated/code-match cases (DINA, CORSICA, ASTRA, Selene) from experimental reconstructions (NICE, LIUQE, EPM/EPQ, EQH) — the owner's scope is the former only.

Two store facts shape everything downstream. Tags are mutable and whole-bundle: oras push replaces the tag's entire content, so nova must pin the manifest digest (sha256:7d96e70a9da74f231ab9ead5f87909cd6c394965d4900489f2e8b7a4424988c2 for v0.0.14) or individual layer digests, never a tag. The supported pull is whole-bundle (286 MB via efit pull); a nova cross-section instead fetches single layers by digest with oras blob fetch (~16 MB for the core set), which means nova writes a small fetch shim rather than reusing imas-efit's CLI. GHCR is reachable from SDCC login nodes; credentials exist in ~/.docker/config.json; anonymous readability is unverified, so assume a token.

§2 — The cross-section

§3 — Fetch, pinning, and storage

The fetch extends nova's existing content-addressed cache; it is not a parallel shim. nova/imas/machine_artifact.py already owns a digest-addressed local cache with per-file sha256 verification and no-clobber publication (_verified_object_root, _verify_directory_files, _publish_directory_no_replace, behind materialize_machine_artifact and resolve_machine_artifact). Those primitives are machine-agnostic, but the module holding them is retired by machine-description-retirement. So rung 1 lifts them into one machine-agnostic store under nova/database/, and machine_artifact.py imports them back with its behaviour and its tests unchanged. The validator fetch is the store's second consumer: one function that fetches an OCI layer by digest (oras blob fetch), verifies it and publishes it into the store. The retirement then deletes only the machine-description parts and leaves the store in nova. The pinned case record extends tests/data-manifest.json, which already carries per-case dd_version, cocos, machine and shot for the transport-geometry lane, with each case's layer digests, rather than adding a second manifest format. The net new public surface is the store module and the fetch function. The availability gate reuses the skip pattern in tests/test_equilibrium_forward_reference.py and adds nothing public.

Each fetched case is converted NC→HDF5 the way imas-efit's nc2hdf5 does: a per-case directory with master.h5, read through imas.DBEntry("imas:hdf5?path=…", "r", dd_version=…) at the per-dataset DD version from the pinned record. Validator modules skip cleanly when the store is unreachable, and the mutable tag never appears in code. The store-strategy decision is locked to republishing under a nova-owned content-addressed store. Pinning by blob digest is unchanged by that, because an unchanged blob keeps its digest. The push itself is an owner action with the owner's GHCR credentials; no worker publishes.

§4 — The gate architecture

Adapt the imas-efit comparator's structure, not its code: per-quantity absolute bands in physics units checked into the test module (its LOOSE band is the cross-code floor — axis 0.20 m, I_p 200 kA, ψ scalars 5 Wb, q95 2.0), with scale-aware relaxation for extensive quantities (I_p at 1.5% of |I_p|, ψ family at 5% of the gauge-invariant flux depth — an absolute 200 kA floor is tighter than legitimate cross-code agreement on ITER while correct on TCV). The ψ₂D map compares [0,1]-normalised over the domain (absorbing gauge and 2π but deliberately not sign) with an absolute cross-section area guard beside it, because normalisation absorbs gross contraction — imas-efit's area check is what caught two of its own rails 17–43% low. Three imas-efit lessons carry over verbatim: q_axis/β_p/l_i are extracted and reported but not gated (cross-code they differ by 0.4–0.55 on good equilibria); reference-free containment gates run even when the comparison does (axis inside wall, axis inside its own LCFS, LCFS area ≥ half its bounding box, minor radius floor); and bands only ever tighten. Nova adds what imas-efit cannot: the solve's own receipts as gates — conservation residuals within registered tolerances, the current ledger exactly zero outside declared support, the normalisation record absolute, and the non-contraction pin (the NK route holds equilibria whose map eigenvalue exceeds one). Per-case figures land with the first passing run: the coil geometry + reference-boundary overlay and a p′/FF′ panel per case (both one matplotlib pass over data already fetched).

§5 — Sequencing and exclusions

Rungs, each independently landable: (1) the fetch shim + pinned manifest + analytic smoke rung; (2) CORSICA 130506 end-to-end — fetch, build the machine from the input bundle's own IDSs, solve all four slices under the shipped defaults, gate at the adapted LOOSE band, land figures; (3) DINA 105027 and ASTRA 131046 (the 256×257 reference is the resolution contrast); (4) the band-tightening study — where nova's deviations sit against LOOSE/MEDIUM per quantity, and which quantities can promote (the existing 135011/7 module's tolerances already sit between the two); (5) optional breadth per the open decision. This plan copies data and builds gates; it does not modify the solve (deviations become findings, not tuning), does not consume experimental reconstructions, publishes nothing from a worker (the republication store-strategy chose is an owner push), and does not port imas-efit's comparator code wholesale — the bands and structural rules are re-derived in nova's own test idiom with the receipts alongside.

§ Decisions

How does nova reference the equilibria? Recommendation: consume the imas-efit store by pinned layer digest now; revisit a nova-owned content-addressed store only if redistribution consent is obtained and the imas-efit tag proves unstable.

Does the first landing include a second machine? Recommendation: land the ITER trio first; add the TCV DINA pair as rung 5 once the gates are proven, for the machine-scale contrast.

extend to all other supported machines and codes. we should run a validate run on a mid-rampup and flat-top slice for every variant. The nova coilset should be built from the source IDSs that the validators specify but can and should be cached locally. for the reconstruction validations remember that we are not validating the reconstruction (from mesurments), we are validating forwardprofile based on what the reconstruction code returned, this is a far easier problem and lets us validate the code correctness without any inference. this also widens our scope well beyond the ITER only cases, this is great. We use imas-python to load the data, it should handle maps automatically, but we need to be very careful with the transformations between versions to ensure that no data that we rely on is lost. the validators then serve a dual purpose, the verify the DDv3 load path at the same time as the forwardprofile reconstruction.
