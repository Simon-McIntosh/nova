§1 — Nova is a physics solver; producing data is not its job

Nova grew a description-packaging layer because something had to carry the MAST geometry and nothing else did. That layer is now three separable things, and all three are better served elsewhere: a bespoke registry schema with its own digest scheme, a content-addressed artifact cache with an OCI reference helper that nothing publishes through, and a machine-specific builder that loads one machine's shot into IDSs. The map-driven producer in imas-ambix replaces all three generically, so this plan removes them rather than maintaining a second implementation.

The geometry is not what is being retired. The conductor and sensor description — including the restored P4-lower loop positions that made all 44 described loop positions unique and lifted the solve-input join from 39 to 43 of 46 reconstruction loops — is real, validated physics and migrates intact into the MAST map. What goes is the wrapper around it.

§2 — Why the digest scheme in particular has to go

physical_digest was built to answer "is this the same machine?" as a single global question. For a machine whose geometry changes across and within campaigns that question has no answer, which is why the scheme has needed a coordinated cutover every time the description moved — each one touching the packaged registry, five or more digest pin files, a published tag, and a downstream consumer's pinned constant. The replacement asserts determinism, partition consistency and visible change instead, all of which remain true of a machine that moves.

Retiring the scheme also retires the outward republication step that never ran. It was authorised, and then investigation established there was nothing to republish: the artifact tooling writes a local content-addressed cache, oci_artifact_reference takes its repository from the caller with the only concrete string in-repo being a test placeholder, and the account's twelve container packages include no machine-description package. The correct disposition is retirement, not execution.

Nova keeps what it is for: the Green's-function kernels, the geometry parametrisation and solver, the calibration package, and the frame and biot machinery that consume a description someone else produced.

§4 — Sequencing and the consumer coupling

This plan cannot start before the producer serves MAST descriptions, which is why it depends on the ambix plan rather than merely following it. The coupling to fix in the same beat is real and currently silent: the consumer imports nova.catalog.mast_geometry.MachineGeometryRegistry directly and pins a digest constant, while its dependency on nova is a git SHA that has drifted 202 commits behind. A deletion here breaks that import unless the consumer moves with it.

Done-when: every surface in the §3 inventory removed with the geometry verified equivalent through the producer beforehand — the same 44 unique loop positions and the same 43-of-46 join, demonstrated numerically, not asserted; the consumer's geometry source and identity test migrated in coordination; the outward republication followup retired with its reason recorded; and the full suite green at its accepted failure set with no new failure.

§ Decisions

Clean deletion in one beat, or a deprecation window where both the registry and the producer serve descriptions?

§ Followups

Demonstrate description equivalence through the producer before deleting anything

The gate that makes the removal safe rather than hopeful: drive the ambix producer's MAST map and show it yields the same description nova's registry serves today — all 44 described loop positions unique, the solve-input join at 43 of 46, and the conductor geometry numerically identical. A demonstrated equivalence is what turns the §3 inventory from a deletion into a migration. Nothing is removed under this followup.
