§1 — What the code already requires

The optional-JAX story is fiction, and a worker lost twenty-five minutes proving it. Twenty-one modules under nova/ import JAX at module scope, and sixteen of them are nova/equilibrium/ — including forward.py (the public ForwardProfile), profile.py (ReconstructProfile), topology.py, fixed_point.py and connectivity_boundary.py. The physics spine cannot be imported at all without JAX. Only one guarded import exists in the whole package (nova/jax/config.py), so there is no fallback path to speak of.

But the extra that would declare it pins the wrong thing. The jax extra is jax[cuda12]>=0.5 on linux, so "declare JAX" and "pull ~2.5 GB of CUDA wheels" are currently the same request. That is why the plain runtime ended up duplicated inside the test extra instead: test pins its own jax>=0.5, which is the only reason uv run --extra test works at all. Two pins for one dependency, and neither named honestly.

§2 — Three extras, each naming one thing

ExtraCarriesWho needs it
jaxjax>=0.5 — plain, no CUDAanyone importing nova.equilibrium
gpujax[cuda12]>=0.5 on linuxGPU hosts only
testnova[jax] transitively — no second pinthe test lane

test must keep resolving JAX, or this change re-breaks what it is fixing. Deleting the pin outright would make uv run --extra test stop supplying JAX — the exact failure that motivated the work. The dependency is therefore moved, not removed: test depends on nova[jax], which drops the duplicate pin while leaving every existing --extra test invocation working unchanged.

JAX stays out of [project.dependencies]: a bare import nova and the frame, biot and IMAS surfaces do not need it, and forcing it on every install would trade one dishonest declaration for another.

Done-when: uv run --extra test resolves JAX with no CUDA wheels on a CPU host and the equilibrium suite passes; --extra gpu is what selects the CUDA build; no extra pins JAX twice; the installed jaxlib variant is reported for both compositions.

§4 — The declared surface is right and the default install still misses it

This plan's own objective is unmet in the environment that does most of the work. Its summary undertakes that "no environment is missing a dependency the code imports unconditionally". The extras are now correct — jax carries the portable runtime and gpu the CUDA build, with no second pin — but neither is selected by a bare uv sync or uv run, and nova/equilibrium imports JAX unconditionally across sixteen modules. So a fresh checkout still cannot import the equilibrium package until someone remembers a flag.

The cost is measured rather than hypothetical: six workers across two sessions have lost a cycle to ModuleNotFoundError: No module named 'jax' or to the sibling symptom where an unsynced interpreter reads valid PEP 758 syntax as a repo-wide SyntaxError. The failure is loud, plausible, and points at committed source, so the natural response is to "fix" correct code or to reimplement the import locally — which for a measurement node silently substitutes a second source of truth for the quantity under test.

Owner direction: put JAX in the default-installed dev group, so every uv sync and uv run picks it up without a flag. Dev groups are not published in wheel metadata, so this changes nothing for downstream consumers. The entry must reference the existing jax extra rather than restate >=0.5 as an independent range — a second pin is exactly what this plan's earlier rung removed.

Deliberately not folded in: whether the sixteen unconditional imports mean JAX should be promoted to a main dependency, or be guarded so the package imports without it. The dev group fixes the development and agent path; it leaves a wheel install of nova.equilibrium still broken without the extra. Promoting to main would force a heavy dependency on assembly-only and imas-only consumers, so that is a packaging trade-off with a real cost either way and belongs in its own decision.

Done-when: a fresh worktree that has run only uv sync with no extras imports nova.equilibrium.conservation and nova.equilibrium.stencil_mesh successfully and reports its resolved jax version; the same holds for a bare uv run python -c invocation; pyproject.toml declares the JAX version range in exactly one place, evidenced by a repository-wide count of occurrences; and the resolved distribution count is reported for a no-extra sync and for --extra gpu so it is visible that the CUDA build is still opt-in and did not become the default.

§ Followups

Declare the GPU extra where the H200 lane installs from

The gpu extra now exists but nothing yet selects it: the H200 lane and any CUDA-enabled worker environment still install through whatever composition they used before, so a device run can silently land on the CPU jaxlib — which is exactly what made three of this sprint's speedup figures CPU-only. Point the GPU install path at --extra gpu and record the resolved jaxlib variant, so a device claim is verifiable from the environment rather than assumed. Owned by the catalog plan because that is where the device lane is defined.
