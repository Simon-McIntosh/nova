§1 — The whole suite cannot currently finish in one process

Two independent attempts to run the full lane died at the same place, and the second one diagnosed it. A 20-minute run reached 62%; a one-hour run reached 76% and then made no progress for about 18 minutes. Two py-spy snapshots showed the main thread parked permanently in threading.Thread.start(), reached from ThreadPoolExecutor.map in nova.catalog.mast_geometry.scan_catalog, via tests/test_mast_catalog_geometry.py::test_catalog_scan_resumes_from_atomic_fingerprint_checkpoint. No executor worker thread was ever created.

The same test passes in 16.79 s from a fresh process. So this is not a slow test and not a hang in the catalog logic itself — it is process state accumulated by earlier tests in suite order that leaves thread creation unable to proceed. That distinction is what makes it fixable here rather than in the catalog's algorithm.

Why this is worth a plan rather than a shrug. While it stands, no full-lane pass/fail count can be obtained in one process, so every claim of "full suite green" in this repository is either sharded, partial, or inherited from before the deadlock appeared. The gate that found it had to fall back to process sharding and record that its figures do not attest to the monolithic lane's health.

§2 — Work items

  1. Make the scan survive a thread-starved process. Establish what exhausts thread creation by that point in suite order — leaked executors, unjoined threads, or a resource limit — and make scan_catalog execute correctly regardless: a single-worker scan runs inline rather than through an executor, and any executor it does create is deterministically shut down. Fix the leak at its source when the source is nova's own; where the leak is a test's, close it there.
  2. Prove the lane completes. One monolithic pytest -m "slow or not slow" run reaches a final summary with counts, on the same SHA class that previously deadlocked.

Done-when: the deadlocking test passes in suite order in a monolithic run; the full lane emits final passed/failed/skipped counts in one process; the mechanism that exhausted thread creation is named in the evidence record rather than worked around silently.

§3 — Bound the compilation retention, now that it is named

The owner is measured, so the repair is no longer a guess between candidates. A frozen monolithic run holds 4,221 live executables and 212 retained native-only XLA-class threads at abort, and heap plus anonymous native mappings explain 97.9% of its RSS growth. The paired control settles what it is not: Python-managed threads grew by 14 against 212 native, so Python executor leakage is excluded, and configured PID ceilings were excluded earlier.

Two facts constrain what a repair may be. jax.clear_caches() returned 2.5 MiB of 892 MiB, so cache eviction at a call site is not a repair — it addresses about 0.3% of the retention. And the abort moves when the lane changes: it has already relocated from test_x_mask_excludes_cells_beyond_null_heights to test_batched_primary_points_match_per_slice, both compiling under backend_compile_and_load. So a fix pinned to either test name would be measuring the lane's current shape rather than bounding the resource, and a third site will appear as the suite grows.

The lever is therefore the retention itself: cap or evict compiled-executable and native-thread retention across a long-lived suite process, so the count stops growing without capping the number of tests. Isolating the JAX-heavy tail into its own process remains available as the fallback, but it is explicitly second choice — it buys a count by giving up the single-process property §1 exists to obtain, and would leave the accumulation unbounded for any future long-lived process.

Done-when: live-executable count and retained native-thread count are sampled across a frozen monolithic run and both stay under a stated ceiling to the end of the run instead of growing monotonically; the run reaches a final pytest summary and its passed/failed/skipped/xfailed counts are banked with the frozen SHA the provenance stamp requires; and if a ceiling cannot hold without shrinking coverage, the measured reason is recorded and the tail-isolation fallback is taken deliberately rather than by default.

§4 — Fifty failures the monolithic count made visible

The count exists, and it is not green. The first monolithic run reports 50 failed against 5,655 passed. That number could not be seen before: while the lane could not finish, every failure past the abort point was invisible, and the only prior figure — 3 failures against 5,657 passed — came from a process-sharded run that is now explicitly labelled unattributable in BASELINE.md.

So 50 against 3 is not yet a regression, and must not be reported as one. Three readings are live and they are not equivalent: the sharded run's per-shard processes may simply never have reached these tests; sharding may have masked failures by giving each shard a fresh interpreter, in which case some of the 50 are suite-order effects rather than defects in the tests themselves; or genuine regressions landed in the intervening commits. The first two are properties of the old measurement, the third is a property of the code, and only a comparison run can separate them.

The failures stay enabled while this is settled. A failing test in a lane summary directs effort; a disabled one is invisible, and the whole point of obtaining the count was to stop working blind.

Done-when: each of the 50 failures is classified as a suite-order effect, a pre-existing failure the sharded run never reached, or a genuine regression with the commit that introduced it, by re-running the failing ids in a fresh process and comparing against their in-suite result; the classification is banked with counts per class against the frozen SHA; and BASELINE.md records the monolithic figure as the reference the next run is compared to, superseding the unattributable sharded entry.
