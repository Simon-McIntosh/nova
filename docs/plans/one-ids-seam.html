nova's generic IMAS layer, written 2022–2024, is the capability: the machine, equilibrium, active and passive coil, and magnetics readers, and the dataset writer. From August 2026 about 39 machine-specific modules and roughly 30k lines grew beside it under nova/imas (mast_*, diiid_*, machine_*). They author machine data, convert conventions, and in places feed the solver directly. This plan makes IMAS the only interface. A separate ingest workspace member authors each machine's data and writes DDv4, COCOS 17 IDSs once. nova reads those IDSs and writes its equilibria only through the generic layer, and holds exactly one convention.

§1 — The overlap census

The stored code review of nova/imas on 2026-11-22 (report code-review/213417e86321) found five modules nothing imports and one triplicated boundary comparison. It did not map the machine-specific modules against the generic layer. This section does. The census is a committed, executable import-graph scan, not a hand-written list. It recomputes each module's class and importers from the tree, carries each row's destination, and renders the research record docs/research/imas-seam-census.html that §2 to §4 read. §6's import guard reads the same scan.

Destinations are by class, not by name. A module classed as machine authoring or publication moves to the ingest member, whatever its name. A generic reader stays in nova. A machine-named module that does generic work is generalised by the §3 or §4 node that moves its machine. An unreached module is deleted by §2.

Done when:

  • The scan emits one row per Python module under nova/imas, plus one row per module in nova/, scripts/, benchmarks/, apps/ or tests/ that imports a mast_*, diiid_* or machine_* module. It states the file count its rows equal, and a committed test fails when a module under nova/imas has no row. Each row names its class (generic reader, generic writer, machine authoring or publication, machine analysis, convention conversion, unreached), its importers inside the solver packages (nova/equilibrium, nova/transport, nova/biot, nova/frame, nova/circuit), and its destination: stays, moves to the ingest member, generalised by §3 or §4, or deleted by §2.
  • Every row that duplicates a capability names both implementations as path:line. Where the imas-ambix map producer (imas_ambix/data/machine_maps, description_identity.py) covers the same machine description, the row names it too. The record also names, per machine, the reference shot whose IDSs §3 and §4 compare: the shot the machine's current forward-solve tests use.
  • Negative control: the same importer scan run over nova.imas.dataset reports its known importers, so a zero elsewhere means absent rather than missed.

§2 — Delete the unreached modules

The review named five modules under nova/imas that nothing in nova/, tests/, scripts/ or apps/ imports: decimate.py, fuse.py, transient.py, toroidal_field_coil.py and waveform.py, 636 lines between them. Git is their archive; the landing line names the deleting commit so any of them can be revived. This section deletes every module the §1 census classes unreached, so it waits on the census. contour_tree_layout.py is unreached but is cited as a design sketch in docs/evidence/contour-tree-topology-authority/reuse-map.md, and its census row decides it.

Done when:

  • Every module the §1 census classes unreached is gone, at least the five above, and the census scan over nova/ tests/ scripts/ apps/ benchmarks/ returns no reference to any deleted module name.
  • The suite adds no failures against the base revision.
  • Negative control: the same scan over nova.imas.dataset reports its importers.

§3 — MAST authoring moves to the ingest member

The ingest member is a uv workspace member under packages/nova-ingest, beside the existing members. It may import nova; nova never imports it. Each MAST row of the §1 census goes to the destination its row names. The existing machine-description authoring and publication path moves into the member. It is not reimplemented there, so the tree keeps one author per machine. This section may be cut into several nodes along the census's groups.

Done when:

  • Every MAST row whose §1 destination is the ingest member is in the member, and exactly one module in the tree authors the MAST description IDSs. No module left in the nova package is named mast_*, imports the member, or imports a module the census moved there. No consumer in apps/, scripts/, benchmarks/ or tests/ is left importing a moved name.
  • The member writes the MAST machine description (active coils, passive structures, magnetics and wall) for the §1 reference shot to an IMAS entry once. nova's generic readers read that entry, and every array the forward solve consumes is bit-identical to the array the base revision builds for the same shot.
  • The nova suite and the member's tests add no failures against base. Negative control: a coil turn count perturbed in the written entry fails the identity comparison.

§5 — nova holds one convention: COCOS 17 on DDv4

nova already states its internal convention once, as COCOS 17. What is still owed is a deletion. nova imports the sixteen-convention COCOS algebra (packages/nova-cocos), and it carries its own DD3 read path, which translates DD3 equilibria on the way in. Both leave nova. The algebra moves into the ingest member and packages/nova-cocos is removed. The DD3 read path is deleted from nova: converting a DD3 source becomes ingest work, done once when the source is written as a DDv4 entry, and nova reads only DDv4, COCOS 17 entries.

The algebra has consumers outside the nova package: four import sites in imas-ambix across two distributions (the ambix application and packages/imas-alambic, which declares nova-cocos as its own dependency), plus nova's own dependency declaration and workspace member list. Every one moves to the ingest member in the same landing beat, through an imas-ambix node for the ambix sites, so nothing resolves against a missing package.

Done when:

  • packages/nova-cocos is gone, from the tree, from nova's declared dependencies and workspace members, and from both imas-ambix distributions' dependencies and lock. The convention algebra exists once, in the ingest member, whose COCOS tests pass with the same count they pass with at base. Nothing in the nova package imports the algebra or reads a DD3 entry. The existing test that nova's convention is stated once still passes.
  • The member converts CORSICA 130506/6 (DD3, COCOS 11) into a DDv4 entry. nova's generic equilibrium reader reads it, and ψ, Ip and the boundary equal the values today's translate-on-read path returns, within 1e-12 relative. DINA 105014/1 and 105013/1 are refused by name at ingest, as they are today.
  • Negative control: nova's reader, handed the unconverted DD3 entry, refuses it by name. The nova suite adds no failures against base.

§6 — The solves read and write only through the generic layer

The forward and inverse solves take machine data only through the generic readers and write their equilibria only through nova/imas/dataset.py. imas-efit reads the result back, and that is the independent check that the written IDS means what nova meant.

Done when:

  • A committed test fails whenever a module under nova/equilibrium or nova/transport imports a nova.imas module the §1 census does not class as a generic reader or writer. Negative control: one planted import of a non-generic module turns it red.
  • A forward solve of one MAST and one DIII-D reference slice, and one inverse solve, each write their equilibrium through dataset.py as DDv4, COCOS 17. imas-efit's equilibrium read recovers ψ on the grid, Ip and the boundary equal to nova's in-memory state within 1e-12 relative.
  • Negative control: an entry written with ψ negated fails the imas-efit comparison.

§ Decisions

Where does machine-specific authoring live?

machine-description-retirement planned to replace the MAST surfaces with the imas-ambix map producer. §1 names the producer wherever it covers the same description.

A separate uv workspace member under packages/ , which nova cannot import, so the seam holds by construction.

How many coordinate conventions does nova hold?

nova runs internally in COCOS 17, but it imports a sixteen-convention table and translates DD3 reads.

nova must hold only one COCOS: 17, on DDv4. Conversion from any other convention or DD version happens once, at ingest.

What happens to modules nothing reaches?

The lead's consolidation also ruled "park, never discard" for plans.

Unreached code is deleted, and the landing names the deleting commit so it can be revived. "Park, never discard" governs plans, not dead code.
