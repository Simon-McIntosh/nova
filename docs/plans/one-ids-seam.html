nova's generic IMAS layer, written 2022–2024, is the capability: the machine, equilibrium, active and passive coil, and magnetics readers, and the dataset writer. From August 2026 about 39 machine-specific modules and roughly 30k lines grew beside it under nova/imas (mast_*, diiid_*, machine_*). They author machine data, convert conventions, and in places feed the solver directly. This plan makes IMAS the only interface. A separate ingest workspace member authors each machine's data and writes DDv4, COCOS 17 IDSs once. nova reads those IDSs and writes its equilibria only through the generic layer, and holds exactly one convention.

§1 — The overlap census

The stored code review of nova/imas on 2026-11-22 (report code-review/213417e86321) found five modules nothing imports and one triplicated boundary comparison. It did not map the machine-specific modules against the generic layer. This section does. The census is a committed, executable import-graph scan, not a hand-written list. It recomputes each module's class and importers from the tree, carries each row's destination, and renders the research record docs/research/imas-seam-census.html that §2 to §4 read. §6's import guard reads the same scan.

Destinations are by class, not by name, and every class has exactly one:

  • Machine authoring or publication moves to the ingest member, whatever its name. That includes the machine-generic publication path and the DDv4 publication floor in machine_artifact.py, which move with their refusal test. The content-addressed cache primitives in that module, which describe no machine, stay in nova.
  • Generic reader or generic writer stays in nova.
  • Convention conversion moves to the ingest member under §5. A module converts when it maps between conventions or DD versions: it imports the COCOS algebra for a transform, derives a COCOS value from a DD version (directly or through a helper such as nova.io.sourcemap's DD-to-COCOS mapping), or translates DD3 data.
  • Convention statement is the one module where nova states its own convention, COCOS 17. It converts nothing, so it stays in nova; §5 rewires it in place to literal values and removes its algebra import.
  • Machine analysis (adjudications, screens, comparisons) stays on the solver side of the seam but carries no machine name. The §3 or §4 node that moves its machine generalises it: it reads through the generic readers and is named by what it does. Where it reads a machine source directly, that read moves to the member, which writes the quantity into the IDS the analysis then reads. A machine-named module that does generic work is generalised the same way.
  • Unreached modules are deleted by §2.

Done when:

  • The scan emits one row per Python module under nova/imas and per mast_*, diiid_* or machine_* module anywhere else in the nova package (for example nova/catalog/mast_geometry.py, nova/media/sources/mast_efit.py, nova/scripts/diiid_machine_artifact.py). It adds one row per module that imports one of them, in nova/, scripts/, benchmarks/, apps/, tests/ or the imas-ambix source and tests, and one row per module anywhere in those trees that imports the COCOS algebra (nova_cocos), derives a COCOS value from a DD version through any helper, or converts between DD versions, so the convention classes are classified wherever they live. It states the file count its rows equal, and a committed test fails when a module under nova/imas has no row. Each row names its class (generic reader, generic writer, machine authoring or publication, machine analysis, convention conversion, convention statement, unreached), its importers inside the solver packages (nova/equilibrium, nova/transport, nova/biot, nova/frame, nova/circuit), and its destination by the class rule above: stays, moves to the ingest member, generalised by §3 or §4, moves under §5, rewired in place by §5, or deleted by §2.
  • Every row that duplicates a capability names both implementations as path:line. Where the imas-ambix map producer (imas_ambix/data/machine_maps, description_identity.py) covers the same machine description, the row names it too. The record also names, per machine, the reference shot whose IDSs §3 and §4 compare: the shot the machine's current forward-solve tests use.
  • Controls: the same importer scan run over nova.imas.dataset reports its known importers, and the convention scan reports nova/equilibrium/convention.py as the convention statement and nova/io/ingest.py and nova/io/signalstore.py as convention conversion through the sourcemap helper, so a zero elsewhere means absent rather than missed.

§5 — nova holds one convention: COCOS 17 on DDv4

nova already states its internal convention once, as COCOS 17, but it draws that statement from a sixteen-row table. nova imports the sixteen-convention COCOS algebra (packages/nova-cocos), and it carries its own DD3 read path, which translates DD3 equilibria on the way in, and a DD3 write path: the sample writer defaults to DD 3.39.0 and applies the COCOS 11 flux factor on the way out. All three leave nova. The algebra moves into the ingest member and packages/nova-cocos is removed. The DD3 read path is deleted from nova: converting a DD3 source becomes ingest work, done once when the source is written as a DDv4 entry, and nova reads only DDv4, COCOS 17 entries. The CORSICA reference values the member's conversion is compared against are captured from the translate-on-read path at the base revision, before that path is removed. Every nova writer, the sample and pulse-design writers included, writes DDv4, COCOS 17 only; a DD3 entry for a consumer that needs one is written by the member from nova's DDv4 entry.

This is a rehoming, not only a deletion. nova keeps COCOS 17's own signs and exponent, stated once as literal values where nova states its convention today. Eleven nova modules and thirteen test files import the algebra now. Each is rewired to those literal values or, where it converts between conventions, moves to the member or goes with the DD3 read path. The DD-to-COCOS mapping in nova.io.sourcemap goes the same way, and so does every derivation of a convention from a DD version in its consumers nova/io/ingest.py and nova/io/signalstore.py: nova reads only DDv4, COCOS 17 entries, so those modules take the fixed convention, and the signal store's cache group stops keying on a derived one. The test that nova states its convention once keeps its single-site assertion. Its comparison of nova's values against the algebra's COCOS 17 row moves into the member's tests, the one place that may import both.

The algebra has consumers outside the nova package: four import sites in imas-ambix across two distributions (the ambix application and packages/imas-alambic, which declares nova-cocos as its own dependency), plus nova's own dependency declaration and workspace member list. Every one moves to the ingest member in the same landing beat, through an imas-ambix node for the ambix sites, so nothing resolves against a missing package.

Done when:

  • packages/nova-cocos is gone, from the tree, from nova's declared dependencies and workspace members, and from both imas-ambix distributions' dependencies and lock. The convention algebra exists once, in the ingest member, whose COCOS tests pass with the same count they pass with at base. Nothing in the nova package or nova's tests imports the algebra, derives a convention from a DD version, reads a DD3 entry or writes one: every nova writer's default and only output is DDv4, COCOS 17, and the DD3 write-sign test moves to the member or goes with the path. §6 — The solves pass only through the generic IMAS layer

The forward and inverse solves take machine data only through the generic readers and write their equilibria only through nova/imas/dataset.py. imas-efit reads the result back, and that is the independent check that the written IDS means what nova meant.

Done when:

  • A committed test fails whenever a module under nova/equilibrium or nova/transport imports a nova.imas module the §1 census does not class as a generic reader or writer. Negative control: one planted import of a non-generic module turns it red.
  • A forward solve of one MAST and one DIII-D reference slice, and one inverse solve, each write their equilibrium through dataset.py as DDv4, COCOS 17. imas-efit's equilibrium read recovers ψ on the grid, Ip and the boundary equal to nova's in-memory state within 1e-12 relative.
  • Negative control: an entry written with ψ negated fails the imas-efit comparison.

§7 — nova's flux functions carry the COCOS 17 sign at their owner

One convention means the flux functions too. nova's owner of the flux-function relation documents p′ as −dp/dΦ and computes jφ = −2π(R p′ + FF′/(μ0 R)), and the flux functions the map extraction publishes carry the same negated derivative. The COCOS 17 relation is p′ = dp/dψ, FF′ = F dF/dψ and jφ = +2π(R p′ + FF′/(μ0 R)). dd-cocos-ingest measured this by two independent routes (record flux-function-sign) and left the owner fix open as f-ddc-006, which this section carries. That followup waited on a cut-cell split; the cut-cell plan has since been superseded, so this section waits only on §5, which settles where nova states its convention.

The sign and the derivative convention move together, at the paired sites the record lists: the map extraction's published derivative; the convention module's docstring, current density and two flux-function integrators; the edge-consistency, DIII-D EFIT, MAST EFIT media and operate readers, or whatever §3 and §4 left of them; and the internal producers (source, continuation, analytic single-null, the profile bases, and the scripts that call the owner). The profile reader's flux_derivative_scale already carries the plus sign and stays.

Done when:

  • tests/test_flux_function_sign.py::test_nova_owner_matches_the_cocos_17_relation passes, and its strict xfail marker is removed.
  • The certified forward-solve rows and the analytic oracles keep their published magnitudes, judged by delta against base, and every expectation whose sign flips is named beside the producer that flipped it.
  • Negative control: one producer left on the old sign fails its COCOS 17 test.

§ Decisions

Where does the COCOS 17 flux-function owner fix (dd-cocos-ingest f-ddc-006) go?

It falls under one convention but was open in S21.

§7, after §5, so it lands in S30 with the convention work without pushing §5 past three clauses.

Where does machine-specific authoring live?

machine-description-retirement planned to replace the MAST surfaces with the imas-ambix map producer. §1 names the producer wherever it covers the same description, and that plan's open inventory folds into §3 and §4.

A separate uv workspace member under packages/ , which nova cannot import, so the seam holds by construction.

How many coordinate conventions does nova hold?

nova runs internally in COCOS 17, but it imports a sixteen-convention table and translates DD3 reads.

nova must hold only one COCOS: 17, on DDv4. Conversion from any other convention or DD version happens once, at ingest.

What happens to machine-description-retirement, whose ambix-producer route the ingest-home decision replaced?

Its removal inventory was still open: the MAST registry, mast_geometry, mast_solve_input_ids, machine_artifact's MAST paths, the DIII-D publication script, and their nova and imas-ambix consumers.

Its open inventory moves into §3 and §4 and the plan closes as superseded, so nothing is dropped and one plan owns the move.

What happens to modules nothing reaches?

The lead's consolidation also ruled "park, never discard" for plans.

Unreached code is deleted, and the landing names the deleting commit so it can be revived. "Park, never discard" governs plans, not dead code.
