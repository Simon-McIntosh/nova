§ Decisions

response-build-route

The 5768 s cold-construction figure decomposed to the host-side exact polygon route on a CPU node (see s2 comments). The shipped device-kernel-build plan landed exact Urankar Green matrices on device: Urankar-exact everywhere including the far field, seconds-to-tens-of-seconds class on the H200 with provenance-keyed caches and compiled geometry gradients.

Lead decision 2026-09-01: fast does not mean inaccurate. The carrier on the new support is built from the exact Urankar integrals evaluated through the device-kernel fast path (device-kernel-build), not the host-side polygon assembly; the host exact polygon route remains available as the equivalence referee. Expected H200 build cost is seconds-class, so the 5768 s cold-CPU bound is not the budget. The digest-pinned durable cache and launch-plus-harvest discipline stand unchanged.

The full stored axes are the default response grid; the stride grid is deprecated but stays loadable

The stored-axis stride grid (33 by 33, 1126 by 101 response) and the full stored axes (65 by 65, 4262 by 101) are both pinned in benchmarks/mast_response_carrier_warm.CARRIER_GRIDS. Measured 2026-09-22: the stride grid loses convergence on edited frames in a way the full axes do not reproduce, and 223 JSON receipts plus 12 HTML records resolve through the coarse identity 1d2c4a2b.

Lead 2026-09-22: the coarse grid is a convergence foot-gun, so it stops being the default and carries no new work. It is deprecated rather than deleted because deleting the carrier file would orphan all 235 records that resolve through it, turning a complete provenance chain into dangling references, which is the opposite of the reproducibility case for defaulting to the fine grid. The full-axis grid is identity 75029bb0, digest eaa48962, shape (4262, 101).

The prescribed-response build runs through the traced tile kernel, not the host polygon kernel

nova.imas.mast_vacuum_response built the carrier by calling nova.biot.polygon.polygon_greens once per winding-pack section. That kernel is NumPy with a Python loop over target blocks and in-place assignment: it cannot take a traced array and cannot reach a device, which is why the published carrier build ran with slurm_job_gpus 0. nova.biot.tiledassembly ships the traced equivalent and nothing called it.

Measured on one P100 over 938 sections and 1126 targets: 1599.74 s host against 2.912 s compile plus 4.3338 s kernel, so 369.1x on the steady launch and 220.8x once the single compile is paid, with one compile serving 270 tiles. Validated elementwise against the published carrier, because the pins do NOT check response values: the semantic identity digests input arrays and the stored response digest is self-consistent, so a changed kernel passes every loader check. Maximum absolute difference 3.597e-16 against a peak element of 8.424e-06 on 98.5 percent of elements, every value finite. Note for implementers: a batched tile does not respect TilePlan.peak_bytes, so its shape is declared from the measured high-water curve; asking plan_tiles for one returns the whole pair space and the device refuses the 236 GiB that implies.
