Why this plan exists

The lead set the target on 2026-10-28: a converged forward solve in under 1 ms of run time, with compile paid once. Compile matters less if it happens once per code revision and machine shape. Today it happens constantly, and run time is three orders of magnitude off.

Two measurements on one H200 established where the present route stands. Both are recorded on converged-forward-solve §4: solve-wall-breakdown and read-derivative-prototype.

The cost is launches and repeated work, not arithmetic. The October lean-map study (sub-millisecond-forward-design) found the same thing: the ideal memory read floor of its operands is 0.017 ms. The route also differentiates the ULP-precise analytic Biot kernels twice to build the read's Hessians. That one choice makes the point-jet program expand from 146 to 100,579 instructions in XLA's splitter, and costs 95 s of cold compile, or 306 s with the moment-field Hessian repair. A quadratic fit over each hex cell's stencil gives the same derivatives in a program that compiles in 0.3 s and runs in 0.4 ms over every node. Its accuracy is not yet proven.

imas-efit's fast path is the comparison. It precomputes response rows once per run and applies them as BLAS matvecs. Its flux update costs about 5 ms per Picard iteration at 65×65 and about 12 ms at 129×129, on one CPU thread (derived figures, 2026-10-28), with no per-iteration differentiation and one boundary flood per iteration.

This plan builds a production forward path to that shape:

  • operators precomputed per machine at fixed shape;
  • a read that tracks its stationary points;
  • a Newton step with no per-step autodiff, built from a few large fused kernels;
  • batched slices.

The analytic kernels stay as the reference oracle that every section is judged against. Both paths stay viable (decision both-routes-viable). The fast path is added as a new SolveRoute value in nova/equilibrium/solve_request.py. It is reached through the existing ForwardSolveRequest → ForwardProfile.solve → ForwardSolveReceipt seam, which today cannot choose a second numerical route; §4 opens it to one. The present route stays selectable, tested, and passing its own certificate rows. Nothing in this plan removes it.

The owners this plan extends. nova already has one deep module with the contract this plan wants, and it is not yet wired into the route measured above. nova/equilibrium/support_read.py does one read and one booking per step: read (:78) solves the axis and X-points warm-started in the bounded row window, read_and_book (:130) does the whole step's support work, and SupportOperands (:27, assembled by from_rows at :44 from topology.BiotMomentCoupling and an ExteriorField) holds the jet rows and the exterior. The row window is fixed_points.RowCache, maintained by maintain_rows (fixed_points.py:413), with the warm-started stationary-point Newton in fixed_points.solve (:646). The cell-local quadratic fit already exists as stencil_nulls._quadratic_fit_matrices (:412) and _fit_selected_cells (:378). The compile key is forward._request_compilation_cache_key (forward.py:2731), which feeds _configure_solve_compilation_cache. Each section below extends these owners. None introduces a second operand container, read, fit or cache.

Not in this plan. converged-forward-solve keeps the certificate route and the analytic map. This plan's work does not depend on that route's open repairs. The moment-field Hessian repair and kernel-compile-barrier §2 are paused, and they resume only if this plan needs them as the oracle.

§1 — A per-machine operator bank at fixed shape, compiled once

The bank is support_read.SupportOperands extended, not a new container. It holds every operator the step applies, precomputed from the analytic kernels once per machine and mesh and stored as dense device arrays, with the row window kept by fixed_points.RowCache:

  • coil and passive response to the grid;
  • plasma-cell response to the grid;
  • the boundary and wall operators;
  • the cached coupling operand the read samples.

The mesh is padded to a small set of shape buckets, so a machine maps to one bucket and two geometries in one bucket share one program. The step program takes every operator as a traced argument and captures no constants, so a geometry change inside a bucket never recompiles. The bucket enters the existing compile key, forward._request_compilation_cache_key, rather than a second cache. The bank is built through the existing content store. It adds no second store.

Done when:

  1. The bank for the diverted 550-cell certificate builds once, and loads in at most 1 s on an H200. Its operators reproduce the analytic map at the certificate's analytic state within 1e-10 relative.
  2. A second geometry in the same shape bucket runs with zero new compilations, counted by the compilation log. A geometry in a different bucket compiles exactly once.
  3. The bank's device memory per shape bucket is recorded, and the 550-cell bucket leaves room on one H200 for a batch of 16 slices, with the headroom stated.

Negative control: capture one operator as a closure constant, and a same-bucket geometry change compiles again. The bank is applied through a minimal matvec program for this measurement; the full step program and its compile bound belong to §3.

§2 — A read that tracks its stationary points, once per step

The present step reads twice through nova.equilibrium.topology.read, once inside the map and once standalone, and each read rebuilds the contour tree. support_read.read already avoids that: it calls topology.read_at_stationary_points on points that fixed_points.solve warm-starts, and builds no contour tree or null census. No production route calls it, though (only tests/test_support_read.py and tests/test_tracked_read.py do), and its cost has never been measured. This section wires support_read.read into the fast route in place of both present reads. It measures it, then makes it fast, using stencil_nulls._quadratic_fit_matrices for the cell-local fit:

  • It takes flux derivatives from a cell-local quadratic fit, read from the §1 coupling operand, only in the cells that hold the tracked axis and X-point and the cells a Newton iterate enters. Each such cell evaluates only its own fit, so no jets are averaged across cells. Both whole-mesh costs, the own-node fit (fixed_points.sampled_coefficient) and the Bell coefficient rebuild (fixed_points.field_from_jets), are now paid only on a rebuild step: since 72717729a, support_read.read runs them under jax.lax.cond(rebuilt, …) and threads tracking through read_and_book.
  • It refines the magnetic axis and the X-point by a few Newton iterations on the cell-local fit, starting from the previous step's positions. On the first step it starts from the analytic stationary points. It admits the saddle when it lies inside the vessel and its Hessian is indefinite. This is the section's own saddle branch: read-derivative-prototype found that no present read, the oracle rows included, admits an X-point at the diverted certificate states.
  • It rebuilds the connected-domain decision only when a tracked point leaves its cell, or the limited/diverted ownership changes, and it reports that rebuild.

The 107.8 ms per call across 61,330 launches belongs to the present topology.read, not to support_read.read. The solve-wall-breakdown device trace splits it as follows:

  • 18.4 ms in the contour tree's while-loop body;
  • 17.9 ms in a separate reads' while-loop body;
  • 39.6 ms in fusion kernels the trace does not attribute;
  • 29.4 ms in device memory copies, which the trace attributes to the read returning host-side data.

Replacing topology.read with support_read.read removes the tree. Whether the rest goes depends on support_read.read's own cost, so the section first decomposes its warm wall before changing it: the fixed-point solve, read_at_stationary_points, the fit, and any host transfer. The copies are removed only if the read returns a device-resident result that the step consumes on the device. Changing only the derivative source does not remove the present read's cost: read-derivative-prototype measured 141–144 ms per call. The prototype's 0.51–0.72 ms per call is the fit over all 1,743 nodes, which only a rebuild step pays. The 0.2 ms bound below holds only for that steady state. A rebuild step is measured separately and is not held to it. Accuracy is judged against the locked decision precision-budget.

Done when:

  1. At the limited and diverted 550-cell trial and converged states, the magnetic axis is within 5e-4 of the minor radius of the extremum of the analytic flux, and the boundary flux is within 1e-4 of the flux span. The X-point is judged against the saddle of the analytic flux at the diverted trial and converged states. Both references are located by a direct Newton solve on the analytic ψ of the certificate state, independent of any read code. This holds at all four states, including the two where the oracle's own axis reference is refused (the limited trial and the diverted converged state, per read-derivative-prototype). Neither the present read nor its harness is the reference, so no instrument the section changes can decide its own clause. Only a read that reports itself valid and qualified meets the clause (the valid flag support_read.read returns). The present gate reports every read at the limited trial state invalid, even though the analytic ψ has a contained extremum there. The section repairs that gate inside support_read and records why it refused.
  2. The warm steady-state read, with no rebuild, costs at most 0.2 ms per slice on an H200 at the 550-cell diverted state, batched over 16 or more slices, with the batch-1 wall tabled beside it (decision read-bound-per-slice). The read returns its result on the device, and the record tables kernel launches and host–device copy bytes per call, with the copy bytes zero. The record also tables support_read.read's warm wall by stage at the base and at the head, and a rebuild step's wall.
  3. A field change that moves the X-point out of its cell triggers the rebuild, which is reported. A field change that does not move it triggers no rebuild.

Negative control: average the fit across cells, as the prototype did, and the axis error exceeds the budget.

§3 — A Newton step with no per-step autodiff

The step is built around support_read.read_and_book and the §1 bank. It forms its Jacobian from the §1 operators and closed-form booking derivatives. It does not trace a JVP per column, and it applies the Jacobian either as one dense block or matrix-free inside a Krylov solve, whichever the measurement favours. A relative linear residual bounds the update's relative error only by the matrix's condition number times that residual. A Krylov solve therefore sets its tolerance from an estimated condition number of the Newton matrix, so that their product is at most 1e-8, and the record tables the estimate. A dense solve has no such tolerance. The map, booking and solve are fused into a small fixed number of kernels per step. The 735.7 ms Jacobian block and the 166.2 ms map are what this section removes.

Done when:

  1. One fast step's update agrees with the present route's Newton update from the same iterate within 1e-6 relative, so both solve the same linear system. This is checked at the 550-cell states where read-derivative-prototype records the present read as valid: the limited converged state and the diverted trial state. At the limited trial state the present read is invalid and yields no finite update, so it is not a reference there. That comparison needs no converged present-route state. From the diverted 550-cell certificate seed, the fast step reaches a solved-equation residual of at most 1e-10. Its converged state is within the locked precision budget of the analytic oracle. The present route's step count and terminal residual from that seed are tabled beside it, whether or not the present route converges there.
  2. The warm per-step wall, excluding the read, is at most 0.5 ms on an H200, with kernel launches per step counted and at most 100. The step program's cold compile, in a fresh process with the cache disabled, is at most 60 s, and its executable is under 50 MB.
  3. The step's Jacobian-vector product agrees with central differences of the step residual within 1e-6 relative, at a trial state and at the converged state.

Negative control: drop the booking-derivative term, and the Jacobian check fails.

§4 — A converged solve under 1 ms, batched, against the oracle

This section assembles §1 to §3 into one solve. It is warm-started from the previous slice, steps until converged, and is batched over slices on one device. Its result is judged against the analytic oracle on the certificate rows. It enters through the existing route-dispatched seam (forward.py, the _ACCELERATED and _REDUCED route sets) as a seventh SolveRoute value. Nothing is retired by this plan, because decision both-routes-viable keeps the present route. The present route would be retired once the fast route passes every certificate row the present route passes and the lead decides it, which is outside this plan.

Done when:

  1. Warm, the converged solve costs at most 1 ms per slice on one H200 at batch width 16 or more on the 550-cell diverted certificate. The batch-1 wall and the per-stage split are recorded beside it.
  2. The fast route is selectable as a SolveRoute value through ForwardSolveRequest. Over the limited and diverted certificate rows at about 550, 2,000 and 5,000 cells, the fast route converges to a residual of at most 1e-10 and every fast-route state is within the locked precision budget of the analytic oracle. The present route is held to no regression rather than convergence: each of its rows ends with the same convergence status and terminal residual (within 1e-12 relative) as at the base revision, since several of those rows stall on the present route today (certificate-550-convergence, certificate-diverted-stall). The section fails if any fast-route row misses or any present-route row changes.
  3. The record tables nova's per-iteration wall beside imas-efit's flux-update and whole-iteration walls at the nearest grid sizes, with the source of each figure.

Negative control: perturb one bank operator by 1e-3 relative in a scratch copy, and the precision check in clause (2) fails on the fast route while the present route's rows stay unchanged.

§ Decisions

What precision does the production path owe the analytic oracle?

Lead decision 2026-10-28: the tighter budget, stated as ratios of machine size rather than absolute lengths, since this is a forward solve and measurement error does not enter. Magnetic axis and X-point within 5e-4 of the plasma minor radius (1.0 mm at ITER's a = 2.0 m), boundary flux within 1e-4 of the flux span, and a solved residual of at most 1e-10. A ULP-level budget is what set the cost of the present route.

Both forward routes stay viable

<p>The fast path is added beside the present route, not in place of it. The request seam today admits one numerical route.</p>

<p>Lead decision 2026-10-28. The fast route becomes a new <code>SolveRoute</code> value selected through <code>ForwardSolveRequest</code>. The present route stays selectable and tested. §4 holds it to no regression on the certificate rows (same convergence status and terminal residual as at base), not to a convergence it does not reach today.</p>

Is the tracked read held to 0.2 ms per call or per slice at batch 16?

<p>On the H200 the tracked read is 1.225 ms per call over 805 launches, and the warm stationary-point solve alone is 0.63–0.82 ms in 55 launches, so launch fusion cannot bring a single call to 0.2 ms.</p>

<p>Lead decision 2026-10-29. §4's 1 ms target is per slice at batch 16 or more, so the read is held to 0.2 ms per slice batched over 16 or more slices, with the batch-1 wall tabled beside it.</p>
