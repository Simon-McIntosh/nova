both-tilings-one-operator

Lead direction 2026-09-08, and it supersedes an earlier coordinator summary that wrongly said hex should be the default with a rectangular path retained only where needed. Four parts, all binding. BOTH ROUTES STAY OPEN: hexagonal and rectangular are both to remain possible, hex is the default carrier, and rectangular is a first-class path rather than a fallback tolerated where hex fails. EQUAL ON THREE AXES: same order, same accuracy, same speed. That rules out adapting one tiling into the other's representation at run time, because the adapter costs speed on whichever side pays for it, so both routes could produce answers and still fail the requirement. TRACEABILITY AND BATCHABILITY ARE NOT NEGOTIABLE: fixed shapes, no data-dependent branching or data-dependent shapes inside the transformed region, and no host-side dispatch on cell geometry. A method that unifies the tilings by branching on mesh type fails this even with correct arithmetic, because it breaks the compiled batch. ONE INTERACTION, ONE MATMUL, which is the crux: in the lead's words an optimum run should only need to matmul a single interaction, and carrying two grids means two operators when one would suffice. The cost of the present split is therefore OPERATOR duplication rather than code duplication. WHAT THIS REJECTS: two kernels behind a dispatch, two operators summed, and any per-tiling specialisation surviving into the traced program. WHAT IT ADMITS: a single kernel whose cell geometry enters as DATA rather than as STRUCTURE, which is the same discipline already applied when profile tables moved out of static operator identity into stacked member leaves, so one compiled program serves every member with the shape fixed and the values varying. That precedent is the closest design template in the tree.

WHY THIS PLAN EXISTS: THREE NODES HIT ONE SEAM IN A SINGLE DAY, and two questions the lead asked are unanswerable because of it rather than incidentally. THE MEASURED FACTS, all from 2026-09-08 and all traced rather than asserted. The current-moment path runs profile solve, into the operator's normalised current moments and observation, into the support partition and profile support, into the atomic mesh traced clip, into the partitioned current moments and the coupling conversion, and it NEVER reaches the bicubic arc moment correction or the twelve-node arc rule at any point. The curved path runs flux-surface geometry extraction, into the surface clips, the tensor spline fit, the cell coefficients and the bicubic arc correction, takes rectangular regular-cell inputs, and is consumed by flux-surface geometry alone. They are not merely separate but UNBRIDGEABLE as built: no callable or data conversion connects atomic polygon cells to the tensor-cell arc correction while preserving same-cell identity, so the chord-versus-curve accuracy comparison and the two-route cost profile could not be produced at all. The affine round trip met the same wall from the other side: the EFIT extraction route requires a rectangular flux lattice while our forward receipts are unstructured hex maps flagged unavailable-non-tensor-product, so the route we apply to source data cannot be applied to our own solutions, and every profile extracted from EFIT by it has never been validated against a case whose answer we know. WHAT THE MOMENT PATH DOES TODAY, which is the asymmetry the plan must remove. The separatrix crossing on each atomic edge is a LINEAR interpolation of flux along that edge; the clipped support is the polygon through those crossings; its area and first and second moments are then computed ANALYTICALLY for that polygon, exact for a cellwise-linear current density; and the clipped cell is fanned into triangles under DEGREE-FIFTEEN Duffy quadrature. So we integrate to degree fifteen over a boundary that is first order. The shipped curvature work measured the trade once and found that clipping against the arc moves the EXTREMUM to second order while improving AREA only from second to third, so the gain for current moments may be modest; nobody has measured it on this path because nobody can.

Find the outboard singularity in the off-axis coupling path

The first work item, because it is a live numerical defect and because its answer constrains the unified kernel. THE EVIDENCE. On the exact-oracle Solovev cases the flux error is not distributed: the top five percent of error nodes form ONE COMPACT PATCH on the outboard half around the midplane while the inboard side and both vertical extremes stay clean, and the solved boundary is displaced inside the reference over the same region. The magnetic axis error is 13.352807 mm at 110 cells and 30.247708 mm at 300, GROWING with resolution, which is a pointwise defect sampled more often rather than a discretisation converging. Both are drawn in the forward-gs-contour-evidence document. WHAT IS ALREADY ELIMINATED, so do not repeat it. The near-collinear cancellation in the edge logarithm was real and is repaired: the guard tested gap greater than exactly zero, which protects only the measure-zero case while the arcsinh difference cancels as the field point approaches an edge line, and it now uses a rationalised form with the branch boundary proven to agree within four units in the last place. That repair CANNOT explain the patch, because both repaired sites sit in the axis field selected only where the radius is exactly zero, and the patch is outboard. Start instead from the OFF-AXIS counterpart that actually serves those evaluations. ONE LEAD FROM THE LEAD, and it may be the whole answer: a reactor-scale Solovev trial should never touch the machine axis at all, because it is unphysical. Both sides of a where are evaluated, so an axis-only expression is computed for every point and discarded, and if it produces non-finite values off-axis that poisons gradients even where the forward value looks correct. Establish whether the axis branch is being evaluated on these cases and whether it returns finite values off-axis. THE DISCRIMINATOR THE LEAD ASKED FOR: solve the same problem on a rectangular grid at matched resolution and compare error maps. Same patch on both means the kernel is at fault independent of tiling, which is the strong result and the one that most constrains this plan. Draw everything as line contours on shared levels, never painted scatter. Fix at the core: no wider guard, no epsilon clamp, no added resolution. Prove the repair on the evidence that motivated it, the patch reducing and the axis error ceasing to grow, with the six certificate residuals before and after.

One clip and one moment method over both tilings, with geometry as data

The plan's centre. Build a single clip and moment path that serves a hexagonal and a rectangular tiling alike, with the cell geometry entering as DATA rather than as structure: fixed shapes, vertex counts and supports padded to a capacity, no data-dependent branching, no host dispatch on mesh type, and nothing per-tiling surviving into the traced program. The design template already exists in this repository and should be started from rather than reinvented: profile tables moved out of static operator identity into stacked member leaves so one compiled program serves twelve members with the shape fixed and the values varying, and the batch fixture that proves it now varies every quantity the contract calls member data. Apply the same treatment to cell geometry. THE ACCEPTANCE IS THE LOCKED DECISION, all four parts. Both routes produce answers, at the SAME ORDER, the SAME ACCURACY and the SAME SPEED, so report order, accuracy and wall for both tilings at matched resolution side by side, and note that an adapter converting one tiling into the other at run time fails this by construction because it costs speed on whichever side pays. The path stays traced and batchable, proven by lowering the unified route and showing no mesh-type branch in the lowered code. And a run carrying both meshes forms and multiplies ONE interaction operator, proven by counting operators and total matmul cost rather than by inspection. TWO QUESTIONS THAT BECOME ANSWERABLE ONLY ONCE THIS EXISTS, and which are currently blocked for exactly this reason: what accuracy a curved support buys over the chord on the same cut cells, and what each route costs. Carry them as sections here rather than as separate work, since both died on the absence of a same-cell comparison. The chord itself is not assumed wrong: the shipped curvature measurement found the arc moves the extremum to second order while improving area only from second to third, so a modest gain for current moments is a legitimate outcome and should be reported plainly if that is what the numbers say.

Extract flux properties from hex and current support from rectangles, through the one path

The second half of the lead's direction, and the half that closes the EFIT seam. Today the flux-function extraction requires a rectangular flux lattice while our forward solves produce unstructured hex maps carrying an explicit unavailable-non-tensor-product status, so the affine route we apply to source EFIT data cannot be applied to our own solutions at all. That is why the only exact validation available was sampling a closed-form analytic flux onto a rectangular lattice, which recovers the constant pressure derivative at binary64 noise but leaves the other carrying a UNIFORM SECOND-ORDER RADIAL-STENCIL BIAS at worst relative deviation 8.851872538089174e-5, within but not far within the measured operator composition floor of 1.1765249977300346e-3 of span. DELIVER BOTH DIRECTIONS. Flux properties, including the flux-surface geometry metrics the curved path currently owns, extractable from a hexagonal mesh. Current support extractable on a rectangular grid. Neither by interpolating one representation into the other, because an interpolation injects the error these measurements exist to bound and was explicitly declined for that reason. THE PROOF THAT MATTERS: run the affine round trip on our OWN forward solution, which is impossible today, and report whether it recovers the prescribed flux functions to the operator floor. If it does, the route is validated against a case whose answer we know for the first time. If it does not, the excess is the extraction's own error and every profile taken from EFIT by that route carries it. Also settle the radial-stencil bias while the machinery is open, since a uniform offset with a named mechanism should be removable rather than tolerated.
