Forward-solve memory ledger

The present route's memory is not the operator matrices. On one DIII-D frame the operands are 10.4 MB of dense arrays, and the ForwardProfile.solve call that follows them grows host RSS by 9.58 GB in a single phase. Everything before the solve — the interpreter, the machine description and the profile build — accounts for under 2.4 GB.

§1 — What was measured, and on what

The producer is benchmarks/diiid_forward_gs_match.py, run through one frame's profile build and one present-route solve. The row is d3d_shot_00000a10ac.parquet, eligible frame 29, at the producer's registered grid stride of 2, which gives a 33×33 lattice of 1,089 nodes. The instrument is benchmarks/forward_solve_memory_ledger.py; it prints and flushes a begin line before each phase starts, so a phase that dies silently is still named, and an end line with the wall time, host RSS before and after, and peak RSS (resource.getrusage(RUSAGE_SELF).ru_maxrss).

Rung and device. Every number below was measured with JAX_PLATFORMS=cpu on node 98dci4-gpu-0003 under SLURM job 1304001 at revision 8173f9418. The device arm's numbers are recorded separately in §6; they are not mixed into this table.

The solve is split into trace and lower, compile, first execute and warm execute for a flux-map program, and the present-route solve is then a phase of its own, because ForwardProfile.solve traces and compiles a different, much larger program than flux_map does on its own.

§4 — The operator bank for the same shape

The bank builder cannot take this producer's shape, and the refusal is a type, not a size. support_read.SupportOperands.from_rows takes a topology.TopologyGeometry — the hex mesh carrying sample_points, from which it derives the unique node set and the sample index — and rows built from a topology.BiotMomentCoupling and an ExteriorField. The DIII-D producer carries neither: ForwardProfile.operator.grid is a FluxTarget whose attributes are coordinate, external, internal, node_number, null, plasma_target, plasma_target_r, plasma_target_z, source_target. Handing it to the builder on this frame raises, verbatim:

AttributeError: 'FluxTarget' object has no attribute 'sample_points'

So the bank's builder is reached with a different operand family and a different point set. That is the finding the brief asked for, and it is why no bank byte count is tabled beside the present-route owners: the comparison that is measured is the one that matters for the memory question — the dense operator arrays this producer already carries are 10.4 MB, so a bank of the same operators could not be the 9.58 GB. What the bank changes is the program that consumes them, and that is fix 1 in §8.

§5 — The spawn-pool OOM

A worker process that has imported the producer module and built nothing else holds 0.672 GB resident, of which 0.467 GB is the interpreter, nova and jaxlib and 0.205 GB is the producer module's own import. The task on top of that import is the machine description (0.68 GB) plus the operands (0.11 GB) plus profile build (0.77 GB transient), and then the solve's 9.58 GB.

Ten such workers each rebuilding the operands and each compiling a solve program is therefore at least 6.7 GB of import floor alone on a CPU node, or 43.8 GB on a GPU node, where one worker's import alone is the 4.38 GB measured in §6. Adding the solve, one GPU worker that reaches it holds 22.28 GB: ten of them is 223 GB, which is past titan's 256 GB once the launcher and the input data hold anything at all. That is the OOM on titan, and it is not the conductor matrix: the pool does not fail because one worker is large, it fails because the per-worker solve program is 9.58 GB on CPU and 15.91 GB on the H200 rung, and it is traced and compiled again in every process. The 26,500 × 24 conductor matrix that ran out of memory is 5.1 MB as an array.

§7 — The display coupling

Yes — the display coupling can be served from the bank's own response builders, evaluated at display points, instead of each producer's per-point kernel. nova/equilibrium/display_flux.py's DisplayCoupling is a pair of callables: plasma(points) returns the uniform, radial and vertical moment columns at (n, 2) target points, and external(points) returns the conductor response there. That is exactly what a SupportOperands carries, at mesh nodes rather than at display points: rows is the moment-blocked source response and exterior the external jet.

The change is to build the same rows at the display coordinate set and contract them with the booked moments — fixed_points.maintain_rows(geometry, coupling, exterior, points, …) builds the rows for arbitrary points through fixed_points.stack_jet and the module's _row_program, and support_read.nodal_jets(operands, moments) contracts them. A display grid is then one more row window kept in fixed_points.RowCache, built once per machine and reused for every frame, rather than a kernel evaluated point by point at 0.083 s and 0.022 s per point. The owner modules are nova/equilibrium/display_flux.py and nova/equilibrium/fixed_points.py.

§9 — What this does not settle

The 9.58 GB on the CPU rung and 15.91 GB on the H200 rung are measured as phases, not yet split inside them. The array census and the solve program's memory_analysis() were written by no job that reached its time limit, so they are the next reader's first measurement rather than a conclusion of this record. The statement "the phase costs 9.58 GB" is about where the memory is allocated, not which of lowering, compile or execution holds it. A follow-up that takes the census at intervals while the solve phase runs will answer that; the probe already emits a begin line per phase, so the phase is named even when a job is stopped at its limit.

The probe now writes its ledger as each phase lands. Both measurement jobs in §6 were stopped at their wall limit after the present-route solve and before the single end-of-run write, so the census, the memory_analysis() and the serialized executable size they had already computed were lost with them. benchmarks/forward_solve_memory_ledger.py now rewrites ledger-<arm>.json atomically at every phase boundary — before a phase starts and after it ends — and once more from a SIGTERM handler, following the partial-receipt pattern of benchmarks/compile_host_memory.py. A stopped run therefore leaves every phase it reached, the phase still in flight, and the reason it stopped (stop_signal), with completed: false distinguishing a partial ledger from a whole one. Measured on the CPU rung: an identical run interrupted at its wall limit leaves no ledger at the pre-repair revision and a ledger naming every phase it reached at this one.
