Research input

In-vessel obstacle loops and the limiting boundary

nova's topology read lets an in-vessel obstacle loop supply the limiting contact. On a two-loop field whose flux peak on the obstacle exceeds its peak on the outer ring, the published boundary lands exactly on the obstacle's inboard face (0.25, 0), distance 0.000 m, and does not touch the outer ring (0.250 m away). The same field read without the obstacle moves the boundary to the outer ring, proving the instrument reports the difference. On the real TCV 77549 wall IDS the published boundary lands on the single limiter unit at distance 0.000 m. No defect is found in this node's scope, so no fix is named.

The read path that builds terminals from more than one ring

Three files carry the multi-ring wall from authored geometry to the limiting contact:

  • nova/equilibrium/topology.py:2405 TopologyGeometry.from_cells(cells, sampling_vertices, wall_units) concatenates every supplied wall unit into one flat wall_points/wall_following/wall_unit triple (assembly at :2453-2460, stored at :2528-2530; fields at :2395-2397). Each unit keeps its own closure: the concatenation is per unit and a unit's last vertex follows its first, so a ring is never joined to a neighbour. Every unit is handed to the contour mesh as kind="vessel" (:2480-2481), so an in-vessel obstacle is part of the vessel polygon rather than a material hole in it.
  • nova/equilibrium/contour_tree_mesh.py:306 build_contour_mesh builds the clipped carrier. _occupiable_geometry (:86-108) unions every kind=="vessel" unit and subtracts only non-vessel material units; _inside_wall_units (:118-150) returns inside_vessel & ~material. Because from_cells marks every unit vessel, the triangulation domain is the union of all rings and an obstacle interior is not carved out.
  • scripts/prototypes/fast_map_production/kernel.py:247 read decides the boundary. It rebuilds candidate points from geometry.wall_points (:285-307), evaluating each wall edge at both endpoints and at its quadratic flux peak, then selects wall_index = argmax(wall_scores) (:382) and sets the boundary to wall_points[wall_index] (:387). wall_scores combines each contact's own tangency level with the axis bottleneck that reaches it (_wall_effective_level, :111-120).

Statement. An obstacle loop disjoint from the outer wall can supply the limiting contact. The wall candidate set at kernel.py:285-307 is built from every unit in geometry.wall_points with no per-unit filter, and the argmax at :382 ranks all of them by the same effective level. An obstacle whose flux peak exceeds the outer ring's is therefore selected on its own merit; nothing in the read privileges the outer ring, and nothing requires the winning ring to touch another ring.

One consequence of the kind="vessel" labelling at :2480-2481 shows up downstream and does not change this answer. Because every unit is passed as vessel, the contour tree's occupancy domain includes the obstacle interior, so the clipped triangulation bridges the obstacle opening rather than respecting it as a wall gap. The boundary decision does not depend on that mesh — it reads wall_points directly — so the measured behaviour is correct, but a caller relying on the contour tree to treat an obstacle as a hole would not get one. This is recorded under follow-ons, not as a limiting-boundary defect.

Two-loop field

Outer ring RING is the coverage fixture's square [-0.5,0.5]² with a radial slit at R=0.5; the obstacle is an in-vessel rectangle R∈[0.25,0.45], Z∈[-0.15,0.15], placed off-axis so domain_rings assigns the axis to the outer ring alone. The field is ψ = −(R²+Z²) with the read on (RING, OBSTACLE). Its signed peak (which the read maximises under σ) is −0.0625 on the obstacle's inboard face at (0.25, 0) against −0.25 on the outer ring at (0.5, 0), so the obstacle is the nearer wall and should limit.

Real multi-unit wall: TCV 77549

The brief expected TCV 77549's wall IDS to be a multi-unit wall. It is not: opened at DD 4.1.0 the IDS carries one wall description with exactly one limiter unit of 512 vertices (wall_units_from_ids reads the same single unit), so no in-vessel obstacle loop exists to exercise on this pulse. The absence is verified rather than assumed — the check sees the 512 vertices, so it is a genuine single unit and not a truncated read. There is accordingly no obstacle to ignore or cross in this data; what the slice does establish is that the read honours the lead's rule on a real machine wall on a limited boundary.

Owner and fix

The read neither crosses nor ignores an in-vessel obstacle on the geometry measured, so this node names no defect and proposes no change. Had it ignored the obstacle, the owner would have been scripts/prototypes/fast_map_production/kernel.py:285-307 (candidate construction) and :382-387 (selection), where a per-unit filter on geometry.wall_points would have excluded the obstacle's edges; had it crossed, the fix would have belonged at the wall-contact selection the same lines plus topology.py:2453-2460, where per-unit closure is carried. Neither is needed: the candidate set is already unit-blind by construction, which is exactly what lets an obstacle supply the contact.

The one observed subtlety, recorded for follow-on work and not a limiting-boundary defect: from_cells tags every wall unit kind="vessel" (topology.py:2480-2481), so the contour mesh's occupancy domain (contour_tree_mesh.py:86-108) admits the obstacle interior rather than subtracting it as a material hole. The boundary decision is unaffected because it reads wall_points directly, but any consumer that needs the contour tree to treat an obstacle as a hole will not get one.
