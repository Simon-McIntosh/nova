Single-evaluator state machine design

The forward solve traces one operator read once per request path and pays for every copy in the optimised HLO. This document fixes the design that will carry the read through one traced body serving the residual, merit, acceptance, recovery, reconciliation and Jacobian-vector requests, and it corrects the mechanism the preceding refusal record proposed: the copy count follows the number of traced call sites, not the wrapper around them. It is the design input for the implement node dispatched against millisecond-converged-solve §2.

§1 — What the preceding refusal established

Run r-20260916T205958834556-msc-single-evaluator-state-machine refused to restructure the evaluator seam inside a sixty-minute fence and delivered findings instead (plan comment). Four findings carry into this design unchanged:

  • The multiplicity is a post-optimisation phenomenon. A jax.jit-wrapped callee is one callee at StableHLO lowering; three direct call sites become three bodies only after XLA's inliner. Any measure of "one body" must therefore read the optimised HLO, never StableHLO and never Python object identity.
  • The two read-qualification passes in _fixed_design_read are not redundant — the second pass admits a rescue-derived material set — so no local de-duplication exists inside the body.
  • The residual-shadow read and the map read are requested on different states, so they cannot be co-produced without changing what is read.
  • reduced_newton.py carries its own copies of the same seam (residual_from_external, _fixed_design_read, normalised_current_moments) and must ride the same machine, or it re-introduces the copies the machine removes.

The census that bounds the prize is committed: a known-present sentinel finds 120 traced copies of ForwardFluxOperator.normalised_current_moments (forward_operator.py:3051) and 36 copies of ForwardFluxOperator._fixed_design_read (forward_operator.py:2454) in the optimised HLO of both solve rungs, and the same census attributes the three largest source-attributed bodies of the remaining 210 MB executable to repeated topology-read and clipped-evaluation code (program-census report).

The semantics bar comes from the frozen-topology interim, which cut 300-cell instructions by about 69 percent and still changed all four certificate terminal states, including a 2.2199809164994903e-03 single-null movement and a non-finite candidate residual. Any restructure of this seam is judged by bit-identical certificate rows, never by instruction count alone.

§2 — The measured mechanism: copies follow traced sites

The design question is not which wrapper defeats the inliner; it is what creates a copy at all. A five-arm reproducer answers it directly. One traced body carries a single marker instruction (a sine on a distinctive width) and is reached from one, three and three call sites under four wrapper forms. Every site input is a traced function argument, so nothing constant-folds; the marker is counted in the dumped optimised HLO by parsing every computation block of the module.

Three readings, each of which changes the design:

  • The counter has a working positive control: direct shows three known-present copies in one computation, and one shows one, so the count tracks the site count linearly. This control is load-bearing, because a first run of this reproducer reported zero everywhere: with literal inputs JAX folded the whole program to a constant block, and the absence of a marker read exactly like a clean result.
  • A wrapper does not deduplicate across call sites. lax.switch is inlined like a plain call (three marker instructions in one computation), and a while_loop is not inlined but is still traced once per site (three separate marker-bearing computations). Choosing between switch and while_loop per call site therefore cannot produce one body; the body's copy count is fixed by how many times the body is traced, which is fixed by how many call sites exist.
  • One body is obtained by having one call site. The machine arm — a single loop that carries the request list and dispatches on a dynamic tag inside its own body — yields one marker instruction in one computation while serving all three requests.

§3 — The design

Each decision below states its reason. The reasons are the part the implement node is bound by; the code shapes below are the intended spelling, not a literal patch.

D1 — The request set rides one machine invocation, not one call site per request

Decision. Per solve, the seam exposes one traced entry point: a machine that takes the request list as data and returns the request list's answers. The six request kinds — residual, merit, acceptance, recovery, reconciliation and Jacobian-vector — are elements of that list, not independent call sites.

Reason. The measurement above is decisive: copies are created by traces, and a trace happens per call site. Building the machine as a request dispatcher that is still invoked once per request kind reproduces the 120-copy census whatever wrapper it uses internally. Only a single invocation carrying the requests as data collapses the count.

D2 — The tag is dynamic loop state, and it selects among the read's outputs

Decision. The tag travels as a loop-carried value and is dispatched inside the loop body. It is never a Python or literal constant at the call site, because a constant tag is a static input and specialises the body per site — the same specialisation that produced the observed copies.

Reason. The heavy read is unconditional inside the loop body and shared by every request; the tag selects which of the already-computed read outputs — which mask, which moments, which scalar reduction, in which combination — form the returned request value. Requests that differ only in their post-processing of one read therefore cost one body and one read, and the residual, merit, acceptance, recovery and reconciliation requests are exactly of that shape.

Consequence the implement node must respect. The Jacobian-vector request is not a post-processing of the primal read, so it cannot be a tag case in the same loop body without dragging the tangent computation into the body (see D4). It follows the same machine at the transform level, not the same loop iteration set.

D3 — vmap sits outside jax.linearize

Decision. The batched boundary is vmap(linearize(machine_body)): each member's linearisation point is its own state, and the machine body inside the linearise is the single-member body.

Reason. linearize(vmap(machine_body)) requires the machine's data-dependent control flow to be batched, because the loop condition and the trip count are per-member; batching them forces masked iterations to the slowest member and changes the loop's semantics rather than its arithmetic. With the vmap outside, the body is traced once inside the linearise and the transform batches that one trace, so the multiplicity stays at one while each member keeps its own convergence path.

What must be checked at the implement gate. That the JVP path's traced body is the same body the primal path uses — an identical marker count in both, not merely an identical digest of two separately authored functions.

D4 — The residual-shadow read is not co-produced with the map read

Decision. The two reads stay separate requests of the machine. They are not fused into one read that returns both.

Reason. They are requested on different states. The shadow read is requested on the state a trip has just produced — residual_shadow_mask(state, …) has eight call sites in reduced_newton.py, and the one at line 1923 reads the state that kernels["reconstruct"] has just returned — while the map read that forms the residual is taken on the state under evaluation. A co-produced read would have to serve both states, which is a change in what is read rather than a change in how many times it is traced. This node's fence reached no further than quoting the caller; the implement node's first check on this decision is to confirm the state identity at every call site before merging any two of them.

D5 — reduced_newton.py's own seam copies ride the same machine

Decision. residual_from_external (reduced_newton.py:2441), the module's _fixed_design_read use (line 2330) and its normalised_current_moments use (line 350) are requests of the same machine, not additional call sites.

Reason. The census counts copies in the whole optimised program, so a body removed from one call path and left in another leaves the program's copies in place. The refusal record names this module explicitly as carrying its own copies of the same seam; moving only the forward-operator call paths would leave the census unchanged and the executable's third largest attributed body in place.

D6 — The measure that proves one body is a marker census on the optimised HLO

Decision. The implement gate counts, in the optimised HLO of the production solve at 300 cells, (a) the marker-bearing computations reachable from each request path and (b) the instructions of the read body itself, beside the existing sentinel census of normalised_current_moments and _fixed_design_read. The route is the census dump route — the optimised HLO module dump, read as text — never StableHLO and never a Python-side call count.

Reason. The refusal record's first finding: the copies exist only after optimisation, so a lower-only or executed-count instrument can read one and mean three. The census report's sentinel counts (120 and 36) are the same instrument, so the gate compares like with like and its before/after is a single number per body.

§5 — What this design does not settle

  • The tag's granularity is open. Whether the reconciliation request (host-facing scalars) can share an iteration with the residual request or needs its own tag value is a question for stage 2's measurement of trip count, not for this document.
  • Requests that need a state the loop does not carry (a recovery request starting from a restored state, an acceptance request on a trial state) may require the machine to be entered more than once per trip. That is compatible with D1 only while the number of invocations stays independent of the request count; stage 2 must show that shape or report it as a blocker.
  • The 130 MB of unattributed traced code in the executable is not addressed here. The census's instruction-share attribution names the compatibility census, the cut-cell fan quadrature and wall_coordinate as the three largest bodies; whether the machine reaches any of them is unknown, and claiming the 50 MB executable gate from this design alone would be unsupported.
