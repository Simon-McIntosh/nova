Why the topology read tests are red: a device gate, a killed compile child, and a lane slower than the bound

Summary

Each of the sixteen node ids of tests/equilibrium/test_topology_read.py that is red on main was run at the base revision 6cce876e3, at the contour-tree-mesh merge 5d40e0155 and at main 32cb743e97 — one fresh process per id, with the per-test timeout disabled, on one allocation with nothing else in it. The redness has three distinct causes, and none of them is a defect in the topology read itself.

A per-test bound set below the read's cost test_topology_class_and_membership[diverted], test_saddle_support_order[diverted] 359–386 s and 383–419 s at all three revisions against a 300 s bound

The three additional head failures recorded in the brief — test_closed_form_resolution_probe[diverted], test_topology_class_and_membership[limited] and test_saddle_support_order[limited] — do not reproduce. With the bound lifted on a compute node they pass at main in 153 s, 130 s and 132 s, and at the base revision by the same margin in 156 s, 126 s and 131 s. The gate that recorded them ran from the login node, where the same three reads take upward of 300 s.

The fixed_points.py root tangent (merge 100bc5828) changed no test's wall, no test's verdict, and no test's outcome. It lies between the two later revisions measured here and is an ancestor of main, so the main arm exercises its content throughout. No id changes verdict between 5d40e0155 and main; the walls that move do so in both directions and within the spread the same id shows across revisions (126→130, 386→371, 128→132, 383→385). The one apparent exception is examined and dissolved in the shared compile barrier below: the test_biot_moment_point_derivatives error at main is reproduced away by a control run at the same revision.

Method

One sbatch job on --partition=sirius (job 1290186, 12 CPUs, 96 GB, four hours, node 98dci4-clu-5009), with nothing else in the allocation. Each revision was extracted with git archive — never git worktree add — and each id ran in its own process with -p no:cacheprovider -p no:timeout, its own TMPDIR, its own NOVA_TOPOLOGY_EVIDENCE_DIR, and a 2700 s safety stop that never fired. Under -p no:timeout neither the timeout = 300 option in pyproject.toml nor any @pytest.mark.timeout is active, which every log confirms twice over — PytestConfigWarning: Unknown config option: timeout and PytestUnknownMarkWarning: Unknown pytest.mark.timeout. So a timeout observed in that job measures a shortfall against a bound; it can never be an accident of the harness.

Several of these tests stamp their evidence receipt with git rev-parse HEAD, so each extracted tree carries a git directory of its own: a HEAD naming that revision's full commit, with objects/info/alternates at the shared object store. No git verb mutates anything. Every log header records the revision, the tree, the command, and the absolute path of the module actually imported; that path resolves inside the extracted tree and never to the shared checkout.

Four further jobs fill the gaps the first could not, and each is named where its result is used: job 1290213 (one H200 on 98dci4-gpu-0003) measures the three test_kernel_compile_growth ids where their own device gate lets them run; job 1290232 (two ids in parallel, 250 GB) and job 1290248 (one id, 450 GB, nothing else) re-measure test_biot_moment_point_derivatives, which the first job lost to memory pressure.

Cause 1: a device gate inside the measurement child

test_kernel_compile_growth is written to xfail. It carries @pytest.mark.xfail(strict=True, raises=KernelCompileBarrier), whose reason is that the cold read compile exceeds the read's own 60 s / 50 MB qualification clause, over a 900 s child safety stop. On the H200 it does exactly that: job 1290213 reports all three parameterisations green as xfail at every revision, in 686–726 s, with the declared barrier.

On a CPU partition the child dies before it can produce a receipt, because _measure_kernel_compile_growth asserts jax.default_backend() == "gpu". Its evidence log prints KERNEL_COMPILE_INPUT_READY from the line before the compile, then assert jax.default_backend() == "gpu" raises AssertionError and nothing further is written. The parent then fails on assert code == 0, f"kernel compile {arm} refused: {log}" at tests/equilibrium/test_topology_read.py:2496. That is an AssertionError and not a KernelCompileBarrier, so the strict xfail converts it to a hard failure — the strict-xfail contract working as designed. The id is red on the CPU lane by construction, in 10.6–19 s, at every revision.

Cause 2: a shared compile child killed by its allocation

Seven ids take the module-scoped kernel_compile_budget fixture: test_biot_moment_point_derivatives, test_kernel_backed_carrier_read at four parameterisations, and test_null_position_implicit_tangent at two. Each carries @kernel_compile_expected_failure — a strict xfail admitting only KernelCompileBarrier — and @pytest.mark.timeout(660). The fixture spawns one child that compiles the 132-cell Biot harmonic kernel and waits process.wait(timeout=600) for it; over the bound it terminates the child, writes WALL_LIMIT_SECONDS=600, and raises KernelCompileBarrier. The compile is genuinely longer than 600 s at every revision, so the child reaches KERNEL_COMPILE_INPUT_READY and never prints KERNEL_COMPILE_PREREQUISITE_COMPLETE.

That is the condition the xfail declares, and on a node that can carry the compile the id is green: at main, job 1290248 ran test_biot_moment_point_derivatives alone with 450 GB and it xfailed in 615 s, its evidence log ending WALL_LIMIT_SECONDS=600 / EXIT=-15 — the fixture's own terminate, the declared barrier, the strict xfail satisfied. The same id xfails at base (614 s) and at the contour merge (626 s) in job 1290232.

What makes the id red is nothing in the read. It is the allocation taking the child away first. Where the host kills the child outright the evidence log ends EXIT=-9 with no WALL_LIMIT_SECONDS line, the fixture's if code: branch raises RuntimeError: kernel prerequisite exited -9, and a strict xfail that admits only KernelCompileBarrier reports that as an error. Every one of the 21 fixture rows in job 1290186 died that way, at all three revisions, under six concurrent native compiles in a 96 GB allocation; job 1290232 reproduced it for main alone under two concurrent compiles in 250 GB, and then ended OUT_OF_MEMORY.

This is a property of the allocation, not of a revision. The one run that carried the compile at main — job 1290248, one id, 450 GB, no sibling compile — xfails green at the same revision where the two-id job errored. So the biot id is not evidence of a merge effect, and the six remaining fixture ids share the same fixture and the same child, so the same reading applies to them: their redness is the kill, not the read. What this node measured directly is biot at all three revisions; the other six were measured only under the memory pressure that caused the kill.

Cause 3: a bound set below the read's cost

Two ids exceed the configured 300 s bound at every revision: test_topology_class_and_membership[diverted] at 359/386/371 s and test_saddle_support_order[diverted] at 419/383/385 s. Both are already in the base revision's failing list, so no merge introduced them and no merge can remove them: they are a bound whose value sits below the cost these two reads observe on this hardware.

Their [limited] siblings show why the lane matters more than the margin. Measured on a quiet compute node, test_closed_form_resolution_probe[diverted], test_topology_class_and_membership[limited] and test_saddle_support_order[limited] complete in 153–156 s, 126–130 s and 128–132 s — comfortably inside 300 s, at every revision. The same three, run from the login node with pytest-timeout active, each stop at Failed: Timeout (>300.0s). The login-node reading is the outlier: a bound that is safe at 130 s of work on a compute node is roughly half a bound at login-node capacity.

Recommendations

  • Size the lane for the shared compile, and let the fixture admit the kill it does not inflict. The fixture's expected-outcome set covers its own terminate and nothing else, so a host kill — the ordinary consequence of an under-provisioned allocation — reports as an error rather than the condition it is. Widen that set so any death of the child over the bound raises KernelCompileBarrier, and give the lane enough memory for the 132-cell compile to run. Owner file: tests/equilibrium/test_topology_read.py.
  • The three test_kernel_compile_growth ids are red on the CPU lane by construction. Either the child's backend check becomes a skip when no GPU is present, so a CPU lane reports the id as skipped rather than refused, or the ids are marked to run only on the GPU lane. The qualification already has a home — the H200, where it xfails as designed at every revision. Owner file: tests/equilibrium/test_topology_read.py.
  • Set the two [diverted] bounds from the measurement. The worst wall observed is 419 s; a bound of 700 carries a 1.7× margin over it, which absorbs the spread these ids show across revisions while keeping the bound able to catch an unbounded regression. Owner file: tests/equilibrium/test_topology_read.py.
  • Run the topology-read gate on a compute partition, not the login node. Three of the failures recorded against head are that artefact and nothing else; they pass at every revision where the read is meant to run. No test change is warranted for them.
  • The root tangent needs no action from this measurement. It changed no wall by more than the spread within a single revision and no verdict at all, once the run that carried the compile was compared with the run that killed it.

This node changed no test and no source.
