Why the topology read tests are red: a device gate, a shared compile barrier, and a lane slower than the bound

Summary

Each of the sixteen node ids of tests/equilibrium/test_topology_read.py that is red on main was run at the base revision 6cce876e3, at the contour-tree-mesh merge 5d40e0155 and at main 32cb743e97 — one fresh process per id, with the per-test timeout disabled, on one allocation with nothing else in it. The redness has three distinct causes, and none of them is a defect in the topology read itself.

The three additional head failures recorded in the brief — test_closed_form_resolution_probe[diverted], test_topology_class_and_membership[limited] and test_saddle_support_order[limited] — do not reproduce. With the bound lifted on a compute node they pass at main in 153 s, 130 s and 132 s, and at the base revision by the same margin in 156 s, 126 s and 131 s. The gate that recorded them ran from the login node, where the same three reads take upward of 300 s.

The fixed_points.py root tangent (merge 100bc5828) changed no test's wall and no test's verdict. It sits between the two later revisions measured here and is an ancestor of main, so the main arm exercises its content throughout. No id changes verdict between 5d40e0155 and main; the walls that move do so in both directions and within the spread the same id shows across revisions (126→130, 386→371, 128→132, 383→385, 213→286).

Method

One sbatch job on --partition=sirius (job 1290186, 12 CPUs, 96 GB, four hours, node 98dci4-clu-5009), with nothing else in the allocation. Each revision was extracted with git archive — never git worktree add — and each id ran in its own process with -p no:cacheprovider -p no:timeout, its own TMPDIR, its own NOVA_TOPOLOGY_EVIDENCE_DIR, and a 2700 s safety stop that never fired. Under -p no:timeout neither the timeout = 300 option in pyproject.toml nor any @pytest.mark.timeout is active, which every log confirms twice over — PytestConfigWarning: Unknown config option: timeout and PytestUnknownMarkWarning: Unknown pytest.mark.timeout.

Several of these tests stamp their evidence receipt with git rev-parse HEAD, so each extracted tree carries a git directory of its own: a HEAD naming that revision's full commit, with objects/info/alternates at the shared object store. No git verb mutates anything. Every log header records the revision, the tree, the command, and the absolute path of the module actually imported; that path resolves inside the extracted tree and never to the shared checkout.

Two further jobs fill the gaps the first could not. Job 1290213 (one H200 on 98dci4-gpu-0003) measures the three test_kernel_…growth ids where their own device gate lets them run. Job 1290232 (250 GB, two ids in parallel) re-runs test_biot_moment_point_derivatives, which the first job lost to memory pressure, with job 1290248 as a serial high-memory control on the main revision alone.

The setup-error walls are the wall-clock of the whole id, not of the compile inside it: every one of them sits at 213–428 s because the 600 s barrier is reached inside a child that the parent then abandons. The number that matters for these seven is not the wall but the fact that the child never prints KERNEL_COMPILE_PREREQUISITE_COMPLETE at any revision.

Cause 1: a device gate inside the measurement child

test_kernel_compile_growth is written to xfail. It carries @pytest.mark.xfail(strict=True, raises=KernelCompileBarrier) whose reason is that the cold read compile exceeds the read's own 60 s / 50 MB qualification clause, and a 900 s child safety stop. On the H200 it does exactly that: job 1290213 reports all three parameterisations green at 706–726 s with the declared barrier.

On a CPU partition the child dies before it can produce a receipt, because _measure_kernel_compile_growth asserts jax.default_backend() == "gpu". Its evidence log holds one line and one traceback:

KERNEL_COMPILE_INPUT_READY
    assert jax.default_backend() == "gpu"
AssertionError

The parent then fails on assert code == 0, f"kernel compile {arm} refused: {log}" at tests/equilibrium/test_topology_read.py:2496. That is an AssertionError and not a KernelCompileBarrier, so the strict xfail converts it to a hard failure — which is the strict-xfail contract working as designed. The id is red on the CPU lane by construction, and it is red there at every revision in 10.6–19 s.

Cause 2: the shared 132-cell compile barrier

Seven ids take the module-scoped kernel_compile_budget fixture: test_biot_moment_point_derivatives, test_kernel_backed_carrier_read at four parameterisations, and test_null_position_implicit_tangent at two. Each carries @kernel_compile_expected_failure (strict xfail, admits only KernelCompileBarrier) and @pytest.mark.timeout(660). The fixture spawns a child that compiles the 132-cell Biot harmonic kernel and waits process.wait(timeout=600) for it; over the bound it terminates the child, writes WALL_LIMIT_SECONDS=600, and raises KernelCompileBarrier.

The child does not finish at any revision. Its evidence log ends at KERNEL_COMPILE_INPUT_READY — the point immediately before .lower(...).compile() — with no receipt after it, at all three revisions and in every job that ran them. So the fixture's 600 s bound is below the read's cold compile cost on this hardware, and all seven ids are red at every revision for that reason.

What differs between revisions is only how the child dies, and that is what chooses between the declared barrier and a bare error. At 5d40e0155 the child is still alive when the fixture's bound expires: the fixture terminates it, WALL_LIMIT_SECONDS=600 / EXIT=-15 is written, the KernelCompileBarrier is raised, and the strict xfail admits it — the id is green as xfail. At main the child is killed outright before the fixture's bound fires: EXIT=-9 with no WALL_LIMIT_SECONDS line, so the fixture's if code: branch raises RuntimeError: kernel prerequisite exited -9, which is not the declared exception, and the strict xfail turns the id red as a setup error.

A SIGKILL is a memory kill, and the pair that distinguishes it from hardware is the serial high-memory control (job 1290248, one id, no sibling compile, 450 GB). Its result is recorded in the landing fragment. Whatever that control shows, the two things this node establishes are independent of it: the child never completes inside 600 s, and the fixture's expected-outcome set does not cover the way the host takes the child away.

Cause 3: a bound set below the read's cost

Two ids exceed the configured 300 s bound at every revision: test_topology_class_and_membership[diverted] at 359/386/371 s and test_saddle_support_order[diverted] at 419/383/385 s. Both are already in the base revision's failing list, so no merge introduced them and no merge can remove them: they are a bound whose value was chosen below the cost these two reads observe on this hardware.

Their [limited] siblings are a different matter and show why load matters more than margin here. Measured on a quiet compute node, test_closed_form_resolution_probe[diverted], test_topology_class_and_membership[limited] and test_saddle_support_order[limited] complete in 153–156 s, 126–130 s and 128–132 s — comfortably inside 300 s, at every revision. The same three, run from the login node with pytest-timeout active, each stop at Failed: Timeout (>300.0s). The login-node measurement is the outlier, not the compute-node one: a bound that is safe at 130 s of work on compute node capacity is roughly half a bound at login-node capacity.

Recommendations

  • The three test_kernel_compile_growth ids are red on the CPU lane by construction. Either the child's backend check becomes a skip when the backend is not a GPU, so a CPU lane reports the id as skipped rather than refused; or the ids are marked to run only on the GPU lane. The qualification itself already has a home — the H200, where it xfails as designed. Owner file: tests/equilibrium/test_topology_read.py.
  • The fixture bound is below the work it bounds. Raise the fixture's 600 to at least 900, matching the sibling test_kernel_compile_growth safety stop on the same compile; and widen the expected-outcome set so that any death of the child over the bound — its own terminate or the host's signal — reports the barrier it is, rather than surfacing as RuntimeError and turning a declared xfail red. Owner file: tests/equilibrium/test_topology_read.py.
  • Set the two [diverted] bounds from the measurement. The worst wall observed is 419 s; a bound of 700 carries a 1.7× margin over it, which absorbs the spread these ids show across revisions without defeating the bound's purpose of catching an unbounded regression. Owner file: tests/equilibrium/test_topology_read.py.
  • Run the topology-read gate on a compute partition, not the login node. Three of the failures recorded against head are that artefact and nothing else; they pass at every revision when the gate runs where the read is meant to run. No test change is warranted for them.
  • The root tangent needs no action from this measurement. It changed no wall by more than the spread within a single revision and no verdict at all.

This node changed no test and no source.
