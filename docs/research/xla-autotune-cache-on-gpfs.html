Cache measurement · titan jobs 1304315/1304320 · H200 job 1304309 · updated 2026-11-03

XLA autotune cache writes on GPFS

Turning XLA's per-fusion autotune cache off stopped GPFS autotune writes while the persistent compile cache kept serving warm programs. Four arms were measured on one titan P100, then repeated on one H200 NVL: the JAX default on a cold cache, the compile cache cleared with the autotune subtree kept, the persistent cache's XLA caches set to none, and the experimental fusion autotuner disabled by XLA flag. Compile wall, steady solve wall and the files each arm left under its cache root separate the four. Disabling the autotuner leaves twelve autotune files behind; setting the XLA cache to none leaves none.

§1 — What was measured

The target is one row of the certificate driver, tests/test_current_book_fragments.py::test_analytic_certificate_moments[550-diverted]: the six rows of that module exceed the rung's time limit, so the diverted 550-cell row stands for them. The harness is benchmarks/xla_autotune_cache_arms.py. Each arm gets a fresh cache root under node-local /tmp, then runs the row once cold and three more times against the cache the cold pass left. Every pass loads the cache guard as a pytest plugin, which records each program's compile seconds, its cache key, and whether the executable was persisted or read back.

All four arms ran inside one scheduler job on one device: titan partition, node 98dci4-gpu-0002, an Nvidia P100, job 1290668, 2 cores and 8 GB, a 75-minute limit, elapsed 54:59, exit 0. The device matters for reading the numbers: 16 GB of device memory and fp64 throughput well below the drained H200's, so every wall below is read relative to the other arms measured beside it and is never an H200 figure. The two other jobs holding that node throughout are why an arm takes 15 to 20 minutes here against 11 on the two earlier attempts.

§2 — The cache behaves the same in all four arms

The persistent compile cache is what carries the certificate target across passes, and none of the four configurations changes it. Every arm wrote 266 compile entries, then missed all 266 on its cold pass, then settled to 0 or 27 misses on the repeats: (a) 266, 0, 27, 0; (b) 266, 27, 0, 0; (c) 266, 27, 0, 0; (d) 266, 0, 27, 0. The 27 appears in a different repeat slot in different arms, so it is a second small compile set that a repeat re-materialises, not a property of any arm.

That the compile wall is the same eight programs at the same seconds in every arm is the load-bearing negative result. Turning XLA's per-fusion autotune cache off changes nothing the compiler records: the same 266 programs are compiled, the same executable is cached, and the cold pass costs the same. Whatever the fusion autotuner chooses on this target, it does not move compile wall or the cached program set at the resolution this instrument has.

§3 — Arm (d) against arm (c): the two ways to stop the writes are not the same

Both arms stop the per-fusion autotuner, and they leave different amounts behind. Arm (c), which sets the persistent cache's XLA caches to none, wrote 0 autotune entries. Arm (d), which passes --xla_gpu_experimental_enable_fusion_autotuner=false, wrote 12 — against 1423 and 1566 in the two default arms. So the XLA flag does not empty the autotune directory, it removes the fusion records and leaves something else writing there, which matches the pinned directory's contents: it holds GEMM results beside the fusion records. A route that passes the flag but leaves the cache enabled keeps a small, unpruned write path into the directory that took the H200 down.

On wall clock the two arms are not separable here. Compile wall is 76.0 s against 81.0 s, one program's rounding in a set of eight whose total is dominated by a 25-second jit_read. Steady-solve medians are 158.3 s against 191.6 s, but the repeats overlap — (d) 152.4 to 196.4 against (c) 176.6 to 210.3 — and each arm ran at a different point in a 55-minute window on a node carrying two other jobs, so the 33-second gap in the medians cannot be separated from node load at three repeats. The honest reading is that this measurement does not distinguish the two arms on solve wall, and that neither shows a compile-wall penalty.

Recommendation for the plan's fusion-autotuner decision: set the persistent cache's XLA caches to none, rather than passing --xla_gpu_experimental_enable_fusion_autotuner=false. The evidence is (i) the autotuner's benefit is unmeasured on this target — keeping it costs nothing detectable in compile or solve wall, so nothing is given up that this measurement can see; (ii) the write path it opens is the demonstrated cost, five in-flight creates at about 11 s each on GPFS being what drained the H200 on 2026-10-17; and (iii) between the two ways of closing it, the XLA cache setting closes it completely and the XLA flag leaves twelve writes a run. If the flag is chosen anyway, the twelve residual autotune writes per run belong in the decision record, and they are not pruned by anything.

Either choice changes the runtime-versioned cache directory, because _persistent_cache_runtime_identity hashes jax_persistent_cache_enable_xla_caches and XLA_FLAGS into its name, so the pre-warm and the lane must carry the same setting before the identity is computed and the pin must be republished from a new pre-warm.

The H200 repeats the titan picture. The compile wall is carried by the same seven of 259 programs in every arm, and the four arms span 7.0 s of it, 40.0 to 45.0 s, a spread of one program's rounding. Every arm wrote the same 259 compile entries, missed all 259 on its cold pass, then hit 270 with zero misses on each repeat, so the persistent compile cache behaves identically under all four configurations here as it did on titan.

Arm (b) and arm (c) on the H200, and what their difference means per compile miss. Arm (b) recompiles with the per-fusion autotune cache kept: 40.0 s of cold compile wall. Arm (c) recompiles the same 259 programs with the autotune cache disabled: 45.0 s. The 5.0 s between them is the whole of what the warm per-fusion autotune cache buys on a cold compile of this row, and spread across the cold pass's 259 compile misses it is about 19 ms of compile wall per miss. That figure is at the edge of what the instrument resolves: the guard reports whole seconds, and the difference is one second on each of the largest programs (jit_read 11 s in (b) against 12 s in (c), the jit__lambda group a second or two lower in (b)). So the honest statement is narrower than the apportionment suggests — turning XLA's per-fusion autotune cache off costs no more than about 5 s on a 259-program cold compile on this target, and nothing the instrument can see in the steady state, where all twelve repeats across the four arms sit between 77.1 and 86.7 s. What the write path costs is on the other side of the ledger: arm (c) leaves the autotune directory empty and arm (d), the XLA-flag route, still writes 12 entries a run against (a)'s 1354.

Declared negative control. Arm (a) wrote 1354 autotune entries under its fresh root and arm (c) wrote 0, so the harness reached the autotune cache and the file-level comparison is not void; the harness prints NEGATIVE_CONTROL=holds arm_a=1354 arm_c=0 and draws the figure only when the control holds.

Method and reproduction

Harness: benchmarks/xla_autotune_cache_arms.py, one cache root per arm under node-local /tmp, JAX_PERSISTENT_CACHE_MIN_COMPILE_TIME_SECS=0, one cold pass then three repeats, the cache guard loaded per pass with its miss budget raised so the guard reports rather than refuses. Submitted through scripts/nova_lane/run.sh --rungs titan as job 1290668. Receipt with every per-program row: the run directory's titan-arms-3.json; per-pass logs in xla-autotune-arm-logs/.

The harness reads the negative control back from the receipt before it draws: arm (a)'s autotune count must be above 0 and arm (c)'s must be 0. A receipt that fails either prints NEGATIVE_CONTROL=void with the reason and exits 3 without writing a figure, so a chart is never published from a run whose cache was never exercised. Demonstrated on this receipt (holds, exit 0, figure written) and on a copy of it in the run directory with arm (c)'s count set to 5 (NEGATIVE_CONTROL=void, exit 3, no figure written); both logs are the run directory's control-holds.log and control-void.log.
